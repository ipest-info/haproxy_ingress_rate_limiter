# 裸机部署（HAProxy 与 rl-limiter 都跑在本机）

适用场景：**本机的 HAProxy 已经装好并在跑**，要把 rl-limiter 加上去，
两个都直接跑在宿主机上，不进容器。只有配置库用 Docker 起。

一句话：`sudo deploy/bare/rl-limiter.sh install`。

> 与 [docs/04](04-DockerCompose演示.md) 的 compose 演示是两回事。那个是
> 把三台"节点"塞进容器里模拟多机，用来演示；这里是**真的往一台生产机上
> 装**。装机脚本不碰你的 HAProxy 安装，也**不会重写你的 haproxy.cfg**。

---

## 1. 为什么只有数据库进容器

| 组件 | 跑在哪 | 为什么 |
| --- | --- | --- |
| HAProxy | **本机** | 你已经装好了，本文不碰它 |
| rl-limiter | **本机** | 它要摸本机网卡的 tc、本机的 haproxy.cfg、本机的 unix stats socket。进容器只是给这三件事各加一层麻烦 |
| MySQL 配置库 | **Docker** | 数据库进容器没有副作用，还省掉装 MySQL 这一步 |

之前用 host 网络模式把节点塞进容器，等于既要容器的隔离又要宿主机的网络，
两头的坏处都占了：`tune-kernel.sh` 改的其实是宿主机全局的 sysctl、tc 装在
宿主机真网卡上、服务名又解析不了。裸机形态把这些含糊之处全部消掉。

---

## 2. 装之前先确认

装机脚本会逐条实测，缺什么说什么，但先自己过一眼更省事：

```bash
deploy/bare/rl-limiter.sh check      # 只看不改，有问题时退出码 1
```

硬前提（缺了 install 会直接停下）：

- Python ≥ 3.11 且有 `python3-venv`
- `haproxy` 已安装（版本 ≥ 2.8）
- `tc`（iproute2）可用，且**内核有 `sch_htb`**——脚本会在 `lo` 上真加一个
  再删掉来实测，不靠猜。缺了它**完全不会限速**
- systemd、docker

还有一件脚本**不会替你做**的事：`haproxy.cfg` 的 `global` 段里要有

```
stats socket /run/haproxy/admin.sock mode 660 level user
```

那是 rl-limiter 的采样入口。缺了脚本会把这一行原样打出来让你自己贴——
**你的 haproxy.cfg 是生产配置，受管区块之外我们一个字节都不碰。**

## 3. 装

```bash
# 至少要给一个初始后端：库里一个 frontend 都没有时 rl-limiter 会拒绝启动
sudo BOOTSTRAP_BACKEND=10.0.0.21:9000 deploy/bare/rl-limiter.sh install
```

脚本按顺序做九件事，每一步都会说清楚做了什么：

1. **前置检查**（上一节那些），不过就停，不会装到一半
2. 建专用用户 `rl-limiter` 并加入 `haproxy` 组——读 stats socket 靠属组
   授权，所以**服务本身不需要 root**
3. venv 装到 `/opt/rl-limiter`
4. 配置文件 `/etc/rl-limiter/rl-limiter.env`。**已存在则原样不动**（里面
   是你填过的库密码、网卡名）
5. 起配置库容器、等就绪，把本机登记进库
6. 授权：haproxy 配置目录可写 + polkit 允许 reload haproxy
7. 内核参数调优并持久化到 `/etc/sysctl.d/99-rl-limiter.conf`
8. 装 systemd unit
9. **起来之后逐项核对**：进程在不在、socket 通不通、**tc 队列树建了没**

第 9 步是重点。"服务在跑"不等于"限速在生效"——脚本最后会跑一遍
`tc_check.py verify`，把每个 frontend 的类、分类规则、`cburst` 逐条核对
（`cburst` 那一项是[docs/06 §9](06-tc限速方案.md) 那次线上事故的教训）。

### 初始 frontend

库里空着的时候有个先有鸡还是先有蛋的问题：frontend 平时在 Web 控制台上加，
而控制台要服务起来才有；服务又因为"frontends 不能为空"起不来。所以装机时
用这几个变量播一个种子：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `BOOTSTRAP_BACKEND` | 无（**必给**） | 后端，`地址:端口`，逗号分隔多个 |
| `BOOTSTRAP_FRONTEND` | `fe_main` | frontend 名 |
| `BOOTSTRAP_PORT` | `8080` | 监听端口 |
| `BOOTSTRAP_QUOTA_MBPS` | `1000` | 限额（Mbps） |

**它们只在库里还没有这个 frontend 时生效。** 重跑装机脚本不会把你在控制台
上调好的限额冲回默认值——`tools/bootstrap_db.py` 对 frontend 与后端一律用
`INSERT IGNORE`，只有实例的接线信息（socket 路径）才 upsert。

## 4. 装完之后

```bash
deploy/bare/rl-limiter.sh status         # systemctl status
deploy/bare/rl-limiter.sh logs           # journalctl -f
deploy/bare/rl-limiter.sh check          # 体检
sudo deploy/bare/rl-limiter.sh restart   # 改完 env 要重启
```

控制台默认 `http://127.0.0.1:8090`。**它无鉴权且带写接口**（能改限额、改
后端、删 frontend），默认只绑回环；要让内网访问必须改 `RL_CONSOLE_BIND`
并配合防火墙限制来源。

日常改配置都在控制台上做（或直接改库），不用再碰这台机器：

- 改限额 → `tc class change`，**连 reload 都不需要**，存量连接立刻跟上
- 改监听端口/后端 → 渲染进 cfg 受管区块 → `haproxy -c` 校验 → 原子替换
  → reload

日志级别不在 env 文件里，它在库的 `service_config` 表里，改完随轮询热生效：

```sql
UPDATE service_config SET log_level='debug' WHERE id=1;
```

## 5. 配置库

```bash
deploy/bare/rl-limiter.sh mysql-up      # 起
deploy/bare/rl-limiter.sh mysql-down    # 停（数据卷保留）
```

端口只绑 `127.0.0.1:3306`——库里存着各 frontend 的限额，没有任何理由暴露到
网外，而 rl-limiter 就在本机。

建表语句与 compose 演示**共用同一份** `deploy/mysql/init.sql`，只在数据卷
为空的首次启动时自动执行。已有数据卷时升级建表语句要手工执行（比如
`quota_bps` → `quota_mbps` 那次迁移，SQL 在 init.sql 文件头）。

多台机器可以共用一个配置库：每台用自己的 `RL_NODE_NAME`，只读写属于自己
的行。那种形态下库就别绑回环了，另外部署一个 MySQL 更合适。

## 6. systemd unit 里那三项权限

unit 由 `deploy/bare/rl-limiter.service.in` 生成。三项权限对应三件事，缺
一个就有一项功能**静默不工作**：

| 权限 | 干什么用 | 缺了会怎样 |
| --- | --- | --- |
| `AmbientCapabilities=CAP_NET_ADMIN` | 下发 tc 限速 | 服务启动即失败（刻意的——"静默地没在限速"比起不来危险得多） |
| `ReadWritePaths=<cfg 目录>` | 改写 haproxy.cfg 受管区块 | 配置下发一直失败，控制台横幅标红 |
| polkit 规则 | `systemctl reload haproxy` | 改了监听端口/后端但数据面不生效 |

两点细节：

- 放开的是 cfg 所在的**目录**而不只是那个文件——原子替换要在同目录里建
  临时文件再 rename，跨挂载点会失败。
- reload 用 **polkit 而不是 sudo**。走 sudo 就必须把 unit 里的
  `NoNewPrivileges` 改成 `no`，否则内核直接拒绝提权，而这类失败只体现在
  "配置没生效"上，很难联想到那一行。

别直接改装好的 `/etc/systemd/system/rl-limiter.service`——重跑 install
会覆盖它。要改配置改 `/etc/rl-limiter/rl-limiter.env`。

## 7. 卸载

```bash
sudo deploy/bare/rl-limiter.sh uninstall
```

停服务、删 unit 与 polkit 规则。**以下东西刻意保留**，要清请手工来：

- 配置库容器与数据卷（`mysql-down`，加 `-v` 才删数据）
- `/etc/rl-limiter`、`/opt/rl-limiter`
- **网卡上的 tc 限速队列树**：`tc qdisc del dev <网卡> root`

最后这条要留意：**服务停了限速还在**。那是刻意的设计——rl-limiter 宕机不
该导致限速失效——但卸载时得手工清，否则队列树会一直留在网卡上。

## 8. 没做的部分

- **没有做多机批量安装**。脚本是单机的，多台机器请用你们已有的配置管理
  （Ansible/SaltStack）循环调用它；它幂等，重复跑是安全的。
- **没有打包成 deb/rpm**。venv + systemd unit 这套对单机足够，做成包要处理
  升级、依赖、卸载残留，收益不成比例。
- **没有自动改 haproxy.cfg 的 global 段**。stats socket 那一行需要你自己
  加——那是生产配置，自动改的风险远大于省下的那点事。
- **装机脚本本身没有在真实生产机上跑过**。本仓库的开发沙箱内核没有
  `sch_htb`、也没有 systemd（PID 1 不是 systemd），所以 install 的完整
  路径无法在这里端到端验证。已经验过的是：脚本语法、前置检查各分支的
  判定、`bootstrap_db.py` 对真实 MariaDB 的幂等语义（包括"重跑不覆盖运维
  调好的限额"）、以及 rl-limiter 从这样一个库里加载配置并起来。
  **首次上线建议先在一台闲置机器上走一遍 install → check → uninstall。**
