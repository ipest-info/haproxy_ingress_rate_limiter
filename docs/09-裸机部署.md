# 裸机部署（HAProxy 与 rl-limiter 都跑在本机）

适用场景：**本机的 HAProxy 已经装好并在跑**，要把 rl-limiter 加上去，
全部直接跑在宿主机上，不进容器、**没有任何数据库**。

一句话：`sudo deploy/bare/rl-limiter.sh install`。

> 与 [docs/04](04-DockerCompose演示.md) 的 compose 演示是两回事。那个是
> 把三台"节点"塞进容器里模拟多机，用来演示；这里是**真的往一台生产机上
> 装**。装机脚本不碰你的 HAProxy 安装，也**绝不会重写你的 haproxy.cfg**。

---

## 1. 配置模型：两个本机文件

| 文件 | 谁写 | 内容 | 生效方式 |
| --- | --- | --- | --- |
| `/etc/haproxy/haproxy.cfg` | **运维手工编辑** | 负载均衡配置的**唯一权威**：监听端口、模式、后端服务器 | 改完 `systemctl reload haproxy`；rl-limiter 轮询到内容变化自动跟上 |
| `/etc/rl-limiter/config.yaml` | 运维手工编辑；控制台/写 API 改限额时**回写** | stats socket 接线、cfg 路径、**quotas 限额登记**（frontend 名 → Mbps）、可选的**实例总限速** `instance_quota_mbps` | 改 quotas/总限速 5s 内热生效（tc 即时换挡，无需 reload/重启；经 API 改则立即触发重读）；接线字段改了要重启 rl-limiter |

rl-limiter 对 haproxy.cfg **绝对只读**；YAML 在控制台/写 API 改限额时
会被回写（整份校验 + 原子替换，手写注释会丢，见 docs/03 §3.4）。
cfg 里有、quotas 没登记的段只监控不限速
（启动时 warn 一次）；**显式写 0** 同样不限速但不再 warn（运维确认过的
决定，全 0/清空时整棵 tc 队列树被拆掉）；quotas 登记了、cfg 里没有的段被
忽略并 warn（段被删了或名字拼错）。

另有 `/etc/rl-limiter/rl-limiter.env`（systemd EnvironmentFile）放**本机
硬件/运行相关**的环境变量：限速网卡 `RL_TC_IFACE`、控制台
`RL_CONSOLE_PORT`/`RL_CONSOLE_BIND`、写 API 令牌 `RL_API_TOKEN`。

## 2. 装之前先确认

装机脚本会逐条实测，缺什么说什么，但先自己过一眼更省事：

```bash
deploy/bare/rl-limiter.sh check      # 只看不改，有问题时退出码 1
```

硬前提（缺了 install 会直接停下）：

- Python ≥ 3.9 且有 `python3-venv`（推荐 3.11+）
- `haproxy` 已安装（版本 ≥ 2.8）
- `tc`（iproute2）可用，且**内核有 `sch_htb`**——脚本会在 `lo` 上真加一个
  再删掉来实测，不靠猜。缺了它**完全不会限速**
- systemd

还有两件脚本**不会替你做**的事（你的 haproxy.cfg 是生产配置，我们一个
字节都不碰）：

1. `global` 段里要有采样入口：

   ```
   stats socket /run/haproxy/admin.sock mode 660 level user
   ```

2. `defaults` 段里要有 `option contstats`——不开的话 TCP 长连接的字节数
   只在会话结束时一次性入账，秒级带宽曲线全是脉冲。

缺了脚本会把该加的行原样打出来让你自己贴。

## 3. 装

```bash
sudo deploy/bare/rl-limiter.sh install
```

脚本按顺序做八件事，每一步都会说清楚做了什么：

1. **前置检查**（上一节那些），不过就停，不会装到一半
2. 建专用用户 `rl-limiter` 并加入 `haproxy` 组——读 stats socket 靠属组
   授权，所以**服务本身不需要 root**
3. venv 装到 `/opt/rl-limiter`
4. 配置文件 `/etc/rl-limiter/{config.yaml,rl-limiter.env}`。**已存在则
   原样不动**（里面是你调过的限额、填过的网卡名）；首次生成后脚本会提醒
   你先编辑再继续
5. **配置校验**：用与服务完全相同的加载链把 YAML + haproxy.cfg 真实解析
   一遍，列出解析到的 frontend 与限额；解析不到任何段会明确告警
6. 内核参数调优并持久化到 `/etc/sysctl.d/99-rl-limiter.conf`
7. 装 systemd unit
8. **起来之后逐项核对**：进程在不在、socket 通不通、**tc 队列树建了没**

第 8 步是重点。"服务在跑"不等于"限速在生效"——脚本最后会跑一遍
`tc_check.py verify`，把每个限速类、分类规则、`cburst` 逐条核对
（`cburst` 那一项是[docs/06 §9](06-tc限速方案.md) 那次线上事故的教训）。

## 4. 装完之后

```bash
deploy/bare/rl-limiter.sh status         # systemctl status
deploy/bare/rl-limiter.sh logs           # journalctl -f
deploy/bare/rl-limiter.sh check          # 体检
sudo deploy/bare/rl-limiter.sh restart   # 改完 env/接线字段要重启
```

控制台默认 `http://127.0.0.1:8090`（实时曲线 + 实例视图 + 日志 + 限额
编辑）。**读接口无鉴权**，默认只绑回环；要让内网访问必须改
`RL_CONSOLE_BIND` 并配合防火墙限制来源。**改限额要令牌**：在 env 里设
`RL_API_TOKEN`（`openssl rand -hex 24`）后重启，页面页头填同一个值；
不设则页面只读。

日常改配置：

- **改限额** → 编辑 `/etc/rl-limiter/config.yaml` 的 `quotas` 段，或在
  控制台 frontend 卡片上改，或调写 API（见 docs/03 §3.4）。5s 内热生效：
  `tc class change`，**连 reload 都不需要**，存量连接立刻跟上；
- **改实例总限速** → YAML 的 `instance_quota_mbps` / 控制台实例页 /
  `PUT /api/instance-quota`。设置后 tc 切层级模式（本机 HAProxy 全部
  frontend 出向合计不超过它；SSH/系统流量不受影响）；
- **改监听端口/后端** → 编辑 haproxy.cfg → `systemctl reload haproxy`。
  rl-limiter 轮询到 cfg 内容变化后自动更新监控清单与 tc 分类；
- **改日志级别/接线** → 编辑 config.yaml 对应字段 →
  `systemctl restart rl-limiter`（这些字段启动时定型，改了服务会在日志里
  提醒需要重启）。

## 5. systemd unit 的权限

unit 由 `deploy/bare/rl-limiter.service.in` 生成，只有一项特殊权限：

| 权限 | 干什么用 | 缺了会怎样 |
| --- | --- | --- |
| `AmbientCapabilities=CAP_NET_ADMIN` | 下发 tc 限速 | 服务启动即失败（刻意的——"静默地没在限速"比起不来危险得多） |

除此之外文件系统只放开两处（`ProtectSystem=strict` 全只读的前提下）：

- `LogsDirectory=rl-limiter`：systemd 自动创建 `/var/log/rl-limiter` 并
  授权写入——监控数据落盘（`RL_METRICS_LOG`，分钟粒度 JSONL）的目的地；
- `ReadWritePaths=/etc/rl-limiter`：控制台/写 API 改限额要把 quotas/
  `instance_quota_mbps` 回写到 config.yaml（临时文件 + 原子替换，需要目录写
  权限；装机脚本会把目录与文件的属组给服务用户并放开组写）。不用写 API
  的话删掉这一行，配置就回到完全只读。

**haproxy.cfg 在任何形态下都只读**：rl-limiter 不写 cfg、不 reload
haproxy。读 stats socket 靠把运行用户加进 `haproxy` 组（socket 是
mode 660）。

别直接改装好的 `/etc/systemd/system/rl-limiter.service`——重跑 install
会覆盖它。要改配置改 `/etc/rl-limiter/` 下的两个文件。

## 6. 卸载

```bash
sudo deploy/bare/rl-limiter.sh uninstall
```

停服务、删 unit。**以下东西刻意保留**，要清请手工来：

- `/etc/rl-limiter`、`/opt/rl-limiter`
- **网卡上的 tc 限速队列树**：`tc qdisc del dev <网卡> root`

最后这条要留意：**服务停了限速还在**。那是刻意的设计——rl-limiter 宕机不
该导致限速失效——但卸载时得手工清，否则队列树会一直留在网卡上。

## 7. 没做的部分

- **没有做多机批量安装**。脚本是单机的，多台机器请用你们已有的配置管理
  （Ansible/SaltStack）循环调用它；它幂等，重复跑是安全的。多机的限额
  配置分发同理——quotas 就是 YAML 里的几行，交给配置管理下发即可。
- **没有打包成 deb/rpm**。venv + systemd unit 这套对单机足够，做成包要处理
  升级、依赖、卸载残留，收益不成比例。
- **没有自动改 haproxy.cfg**。stats socket 与 contstats 那两行需要你自己
  加——那是生产配置，自动改的风险远大于省下的那点事。
- **没有历史数据查询界面**。监控数据落盘为分钟粒度 JSONL（默认保留
  90 天，`/var/log/rl-limiter/metrics.jsonl`），回查用 grep/jq；实时值
  可被 Prometheus 抓取（控制台端口的 `/metrics`），大盘在 Grafana 侧做。
- **装机脚本本身没有在真实生产机上跑过**。本仓库的开发沙箱内核没有
  `sch_htb`、也没有 systemd（PID 1 不是 systemd），所以 install 的完整
  路径无法在这里端到端验证。已经验过的是：脚本语法、前置检查各分支的
  判定、以及 rl-limiter 按这套配置加载并起来。
  **首次上线建议先在一台闲置机器上走一遍 install → check → uninstall。**
