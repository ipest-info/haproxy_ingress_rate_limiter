# 建议与讨论点

针对需求文档（[00-需求说明.md](00-需求说明.md)）本身提出的改进建议，以及需要产品/运营拍板的决策点。按重要性排序。

---

## 1. 【最重要】"只限新建连接"压不住带宽，必须补充存量连接整形

需求原文：*"如果总带宽大于环境约定的带宽，则限制haproxy的新建连接，如果掉下去了，则允许新建连接"*。

这个手段在代理业务里有结构性缺陷：

- 代理客户端普遍复用长连接。超限的元凶往往是**已建立连接上的大流量下载**，禁止新建连接对它们毫无作用——带宽可能长时间压不下去，而新用户却一直被拒。
- 反过来，靠"掐新连接"把带宽压下去的过程，等价于把限速压力全部转嫁给新请求（表现为连接被拒/超时），客户感知是"服务时好时坏"，比"整体变慢一点"体验差得多。

**建议（✅ 已采纳并进一步强化）**：主力用 HAProxy 2.8+ 原生的 `filter bwlim-out`（共享 stick-table 模式）做**聚合整形**——新老连接一视同仁共享环境配额、平滑降速、不断连。评审后进一步确定：**正常路径完全不拒绝新建连接**（maxconn 只作资源过载保护），上游摄入速率由 TCP 背压自然收敛，不需要显式限制上行。整形导致的数据积压不会堆在 haproxy 上（每流缓冲固定大小，压力背压回边缘节点），详见方案设计 §3.2 / §3.4。

**代价**：需要 HAProxy ≥ 2.8。建议借本项目统一升级到 2.8 LTS；个别无法升级的节点过渡期用 tc 单层硬限，并接受其体验打折。

## 2. 统计口径要写进合同/约定：应用层字节 vs 网络层字节、瞬时 vs 均值

- HAProxy `bytes_out` 是应用层字节；云厂商带宽包、网卡限速都按网络层算（含 TCP/IP 头，差 3~5%）。
- "不高于约定带宽"必须定义时间窗口：是 1 秒瞬时不超，还是 10 秒/1 分钟均值不超？瞬时口径会把限速做得非常暴躁。

**结论（✅ 已拍板）**：采用 **"10 秒滑动均值 ≤ 约定带宽，瞬时允许 ≤110%"** 的口径，不做瞬时限制；应用层/网络层换算系数做成配置项。

## 3. 超约策略应该分级，而不是一律硬限

现状痛点是"客户实际升级了很多回、后台没改"——说明业务上存在**先用后补手续**的真实场景。如果一上线就对所有环境硬限速，等于把这些客户瞬间打爆，会造成大量客诉。

**建议**：`ORDER_ENV` 上加 `overage_policy` 字段，三档：

| 档位 | 行为 | 适用 |
| ---- | ---- | ---- |
| `alert_only` | 只告警不限速（观测模式） | 上线初期全量默认；存量争议客户 |
| `soft` | 允许超约至 110%（与弹性上限一致，已拍板），超出部分限速 + 生成超约用量记录（可事后计费） | 大客户/有商务弹性的订单 |
| `hard` | 严格按配额限 | 标准订单 |

上线路径：全量 `alert_only` 跑 2~4 周 → 用对账报表清洗存量数据、逐单和商务确认 → 分批切 `soft`/`hard`。**切勿直接按现在后台里那份失真的配额数据开启硬限。**

## 4. 数据不同步的根因是"变更没有唯一入口"，要用流程 + 对账双保险

"升级过很多回但后台没改"不是技术故障，是流程漏洞：现场扩容/升级不经过后台。只靠"要求大家记得改数据"没有用。

**建议**：

1. **唯一入口**：配额生效值只能来自后台（rl-limiter 只认 Controller 下发），现场改了机器也改不了限速值——想给客户升级就必须先改后台，数据被动保持一致。
2. **自动对账**：Controller 每天比对"环境实测峰值/P95 用量"与"后台配额"，差异超阈值（如连续 3 天 P95 > 90% 配额，或用量远低于配额的疑似降配）自动生成差异工单。M1 观测模式先跑对账，即可在不做任何限速的情况下把存量烂账全部翻出来。
3. **变更留痕**：所有变更带操作人/原因/审批，进 `QUOTA_CHANGE_LOG`。

## 5. 把限速系统顺手变成"升级销售信号"（✅ 已采纳）

用量长期贴近配额的客户就是最优质的扩容线索。建议加一条运营规则：**环境用量 > 95% 配额持续 N 分钟 → 推送运营/销售跟进升级**。限速上线后客户侧感知到变慢，也天然形成升级动力。这条几乎零成本，但能把本项目从"成本/风控项目"变成"能带收入的项目"。

已拍板落地方式：用量与超约数据按环境/天聚合入库（峰值、P95、超约秒数/字节量、收紧事件），后台管理端做展示页面与报表，作为运营跟进与事后协商的依据（见方案设计 §3.8）。

## 6. 架构上的两个遗留风险，建议排期而非忽略

1. **HAProxy 入口是旁路限速覆盖不到的单点面**：若客户绕过域名直连 adapter（或历史遗留的直连入口存在），限速形同虚设。建议 M3 之后排查并收敛所有不经过 haproxy 的入口路径（adapter 只接受来自 LB 内网段的连接）。
2. **一个订单跨多个环境时的总带宽（✅ 已拍板）**：每个环境必须有自己的带宽配额、独立限速；**原则上允许订单内各环境配额之和大于订单名义总带宽**（超售弹性由商务把握）。系统不做订单级汇总限制，订单带宽仅作商务参考字段（见方案设计 §3.5）。

## 7. 实施建议汇总

- **先观测后限速**（M1 → M2），观测期同时完成存量数据清洗，风险最低。
- 限速执行必须**灰度 + dry-run**：先只打日志"本应限到多少"，人工核对一周再放开真执行。
- 阈值参数（90%/100%/滞回时间/AIMD 系数）全部做成 Controller 可下发的策略，不写死在 rl-limiter 里。
- rl-limiter 用 Python 实现，systemd 部署；发布走灰度分批。
