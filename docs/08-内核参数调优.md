# 08 内核参数调优

目标一句话：**让瓶颈落在业务服务自己的并发上限上，而不是内核默认值上。**
服务的 backlog/并发配得再大，内核的默认值会在下面悄悄削掉——
最典型的一条：cfg 写了 `backlog 65536`，而 listen(2) 的实际队列被
`net.core.somaxconn` 封顶（发行版默认 4096）：配置写着 65536、实际
生效 4096，没有任何告警；突发重连时溢出的 SYN 被内核直接丢掉，客户端
看到"偶发连接超时"，服务日志干干净净。

全部调优集中在一个脚本：`deploy/sysctl/tune-kernel.sh`（容器入口脚本
启动阶段自动跑，裸机装机脚本也会跑）。

## 1. 用法

```bash
tune-kernel.sh apply    # 尽力调优，逐项读回校验（默认动作）
tune-kernel.sh check    # 只体检不修改；有未达标项退出码 1
tune-kernel.sh dump     # 输出 sysctl.d 格式，宿主机固化用：
                        #   tune-kernel.sh dump > /etc/sysctl.d/99-rl-limiter.conf
                        #   sysctl --system
```

**实现上最重要的约束：写完必须读回。** 容器里一部分 sysctl 只读，而
`sysctl -w` 失败时**退出码仍是 0**——所以脚本一律直接写 `/proc/sys`
并读回比对，只认最终生效值；调不动的项逐条报出来而不是假装成功。

哪里跑决定哪些调得动：

- **bridge 容器**：net.* 按 netns 隔离，大多可写，但部分运行时把
  /proc/sys 挂只读——compose 里按 `sysctls:` 在创建期声明最可靠
  （demo compose 就是这么做的）；
- **host 网络容器**：与宿主机共享 netns，compose 的 `sysctls:` 不可用
  且容器内多半只读——在**宿主机**上 apply 或 dump 固化；
- **fs.nr_open、nf_conntrack_max**：从来不是 netns 的东西，容器里改
  不动，必须宿主机。

## 2. 参数表（脚本是唯一权威，这里是导读）

| 参数 | 目标值 | 为什么 |
| ---- | ---- | ---- |
| `net.core.somaxconn` | ≥65536 | accept 队列上限，封顶 listen backlog |
| `net.ipv4.tcp_max_syn_backlog` | ≥65536 | 半连接队列，默认 1024，突发建连即丢 SYN |
| `net.ipv4.tcp_tw_reuse` | 1 | 默认 2 只对回环生效，对"代理→后端"路径等于没开 |
| `net.ipv4.tcp_max_tw_buckets` | ≥2097152 | 默认 65536，高周转刷 "time wait bucket table overflow" |
| `net.ipv4.tcp_fin_timeout` | 15 | 默认 60s，压着临时端口不放 |
| `net.ipv4.ip_local_port_range` | `32768 65535` | **只抬上界不下探**：tc 按源端口分类，下界降到 1024 会让到后端的临时端口撞监听端口，把回程流量算进别人的限速类 |
| `net.ipv4.tcp_slow_start_after_idle` | 0 | 长连接"空闲一阵再猛传"的场景，留默认值等于每次重新慢启动 |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | 上限 16MiB | 缓冲自动调优上限；代理是发数据的一方，wmem 更吃紧（发行版默认常 4MiB） |
| `net.core.rmem_max` / `wmem_max` | ≥16MiB | 显式 SO_*BUF 的上限（本项目留内核自动调优，这两项是兜底） |
| `net.core.netdev_max_backlog` | ≥250000 | 软中断收包队列，万兆以上最先在这里丢（看 /proc/net/softnet_stat 第 2 列） |
| `net.core.netdev_budget` | ≥600 | 单次软中断收包预算 |
| `net.netfilter.nf_conntrack_max` | ≥4194304 | **容器部署最易踩**：Docker 的 iptables 把 conntrack 拉起来，每条连接都被跟踪；maxconn 100 万意味着前后各 100 万条+TIME_WAIT，默认 262144 直接撑爆、内核静默丢包 |
| `fs.nr_open` | ≥4194304 | 单进程 fd 硬天花板：百万连接量级的服务（每连接 1~4 个 fd）靠默认的 1048576 根本起不来；容器里改不动，要在宿主机设 |

改 maxconn 时需要连带复核的三件套：`fs.nr_open`、`nf_conntrack_max`、
`somaxconn`。

## 3. 验证真的生效了

1. `tune-kernel.sh check`——退出码 0 即全部达标；
2. 业务服务侧：按其自身文档核对并发/backlog 配置生效，启动无
   ALERT（fd 不够它会拒绝启动，入口脚本会提前按 cfg 实际值报数）；
3. 压测侧症状核对：accept 溢出看 `netstat -s | grep -i listen`（demo
   曾实测 5000 并发、backlog 默认值下 75s 溢出 3.1 万次，调完归零）；
   conntrack 看 `dmesg | grep nf_conntrack`。
