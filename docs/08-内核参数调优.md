# 内核参数调优（高并发 / 高带宽）

需求：**保证高并发、高带宽的 HAProxy 不受系统内核参数影响**——也就是让
瓶颈落在 HAProxy 自己的 `maxconn` 上，而不是内核的发行版默认值上。

调优在**镜像初始化阶段**（`node-entrypoint.sh`，启动 HAProxy 之前）完成，
表在 [deploy/sysctl/tune-kernel.sh](../deploy/sysctl/tune-kernel.sh)。

---

## 1. 为什么必须做：配置写了不等于生效

本项目 `haproxy-base.cfg` 的 `defaults` 里写着 `backlog 65536`。但
`listen(2)` 的实际队列长度被 `net.core.somaxconn` 封顶，而发行版默认是
4096。实测（`ss -lnt` 的 Send-Q 列就是监听套接字的实际 backlog）：

```
somaxconn=  4096  listen(backlog=65536) 实际生效=4096     <-- 默认
somaxconn= 65536  listen(backlog=65536) 实际生效=65536    <-- 调优后
```

配置文件里写着 65536，实际只有 4096，**内核不会给任何提示**。溢出的 SYN
被直接丢弃，客户端看到的是"偶发连接超时"，而 HAProxy 的日志里干干净净——
因为那些连接根本没到 HAProxy。

这类"配了但没生效"是本项目一贯最在意的故障形态（另一例见
[docs/06](06-tc限速方案.md) 里 bwlim 静默关闭 splice）。

---

## 2. 三类参数：容器里能设的、只能在宿主机设的、netns 里压根没有的

在独立 network namespace 里逐个看 `/proc/sys` 的权限位实测（Linux 6.18.5）：

| 类别 | 参数 | 容器内 |
| --- | --- | --- |
| 可写(644) | `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog`、`tcp_tw_reuse`、`tcp_max_tw_buckets`、`tcp_fin_timeout`、`tcp_slow_start_after_idle`、`tcp_rmem`、`tcp_wmem`、`ip_local_port_range` | ✅ 能设 |
| 只读(444) | `net.core.rmem_max` / `wmem_max`、`net.netfilter.nf_conntrack_max` | ❌ 宿主机设 |
| 不存在 | `net.core.netdev_max_backlog` / `netdev_budget`、`net.ipv4.tcp_mem`、`fs.*` | ❌ 宿主机设 |

### 一个必须知道的坑：`sysctl -w` 失败也返回 0

```console
$ sysctl -w net.core.rmem_max=16777216
sysctl: setting key "net.core.rmem_max": Operation not permitted
$ echo $?
0
```

报了错，退出码却是 0。也就是说 `sysctl -w ... || echo 失败` 这种写法
**永远不会报失败**——脚本会开开心心地告诉你调优完成了。

所以 `tune-kernel.sh` 一律直接写 `/proc/sys` 并**读回比对**，只认最终生效
值。设不上的会明确列出来并打印宿主机上该执行的命令，不会假装成功。

> 顺带解释一个选型：**没有用 compose 的 `sysctls:`**。那里只能写第一类，
> 写错一个（比如 `net.core.rmem_max`）runc 会拿到 EPERM，容器直接起不来；
> 而且三台 node 要各写一遍。放进初始化脚本则是同一份表，`docker run`、
> k8s、裸机 systemd 都通用，还能顺带报出宿主机侧该做什么。

## 3. 参数清单与依据

值按本项目基线定：**32 核、TCP L4 代理、`maxconn` / `maxpipes` 各 1000000**
（默认值不该成为限制，要限并发请显式配 frontend 级 maxconn）。
表里的值都是**下限**，`tune-kernel.sh` 只抬高不压低（本机已有更大的值会保留）。

### 3.1 建连路径（高并发）

| 参数 | 目标 | 常见默认 | 依据 |
| --- | --- | --- | --- |
| `net.core.somaxconn` | 65536 | 4096 | 见上，直接决定 `backlog 65536` 是否生效 |
| `net.ipv4.tcp_max_syn_backlog` | 65536 | 1024 | 半连接队列。突发建连时溢出即丢 SYN |

溢出了怎么看：`nstat -az TcpExtListenOverflows TcpExtListenDrops`，
非零就是 accept 队列扛不住。

### 3.2 连接周转（代理到后端）

| 参数 | 目标 | 常见默认 | 依据 |
| --- | --- | --- | --- |
| `net.ipv4.tcp_tw_reuse` | 1 | **2** | 2 = 只对回环生效。代理到后端走的是真实网卡，等于没开 |
| `net.ipv4.tcp_max_tw_buckets` | 2097152 | 65536 | 超了会刷 `TCP: time wait bucket table overflow`；计数看 `nstat -az TcpExtTCPTimeWaitOverflow` |
| `net.ipv4.tcp_fin_timeout` | 15 | 60 | FIN_WAIT_2 压着临时端口不放 |
| `net.ipv4.ip_local_port_range` | `32768 65535` | `32768 60999` | 临时端口 28232 → 32768 个（+16%） |

**`ip_local_port_range` 只抬上界、绝不下探**——这是本项目特有的约束。
网上通行的"高并发调优"会让你写 `1024 65535`，在这里是有害的：tc **按源
端口**给流量分类（`classid` 的 minor = 监听端口），下界降到 1024 之后，
HAProxy 连后端用的临时源端口就可能撞上某个监听端口，把回程流量算进别人
的限速类里。`tcshaper.ephemeral_conflicts()` 会在启动时检查并告警，但最
省事的做法是根本别把下界降下来。详见 [docs/06 §单网卡/两网卡](06-tc限速方案.md)。

### 3.3 吞吐（高带宽）

| 参数 | 目标 | 常见默认 | 依据 |
| --- | --- | --- | --- |
| `net.ipv4.tcp_slow_start_after_idle` | **0** | 1 | 默认值下，连接空闲一个 RTO 后 cwnd 被打回初始值。本项目大量长连接是"空闲一阵再猛传"（`/big` 那种下载场景尤其典型），留着它等于每次都重新慢启动 |
| `net.ipv4.tcp_wmem` | `4096 65536 16777216` | 上限常见 4 MiB | 自动调优的发送缓冲上限。**代理是往客户端发数据的一方，这项比 rmem 吃紧** |
| `net.ipv4.tcp_rmem` | `4096 131072 16777216` | 上限 6~32 MiB | 同上，接收侧 |

这两个是**自动调优的上限**，不是预分配——内核按需增长，不会 100 万条
连接乘以 16 MiB。真正的全局兜底是 `net.ipv4.tcp_mem`，而它在容器里不存在，
只能在宿主机上看（默认按内存大小推算，一般不用动，但值得在压测前看一眼）。

### 3.4 只能在宿主机设的

| 参数 | 目标 | 常见默认 | 依据 |
| --- | --- | --- | --- |
| `net.netfilter.nf_conntrack_max` | 4194304 | 262144 | **容器部署最容易踩的一条**。Docker 装 iptables 规则会把 conntrack 拉起来，于是每条连接都被跟踪。100 万连接意味着前后各 100 万条再加 TIME_WAIT，默认值直接撑爆，内核开始**静默丢包**并打 `nf_conntrack: table full`。别忘了 `nf_conntrack_buckets` 一般取 max/4 |
| `net.core.netdev_max_backlog` | 250000 | **1000** | 每 CPU 的软中断收包队列。万兆以上最先在这里丢包；丢没丢看 `/proc/net/softnet_stat` 第 2 列（非零即丢） |
| `net.core.netdev_budget` | 600 | 300 | 单次软中断轮询的收包预算 |
| `net.core.rmem_max` / `wmem_max` | 16777216 | 常见 208 KiB ~ 4 MiB | 只约束**显式** `SO_RCVBUF`/`SO_SNDBUF`。本项目刻意不写 `tune.rcvbuf`/`tune.sndbuf`（实测是负优化，见 [docs/06](06-tc限速方案.md)），所以这两项目前不在关键路径上——留着是为了有人手动写死缓冲时不被悄悄削掉 |
| `fs.nr_open` | 4194304 | 1048576 | 单进程 `RLIMIT_NOFILE` 的硬天花板。100 万连接基线需要 4000034，**默认值压不住，不抬它 HAProxy 根本起不来**；而它在容器里改不动——compose 演示因此用 `HAPROXY_MAXCONN` 把量级降到 10 万 |

## 4. FD 预检

内核参数之外，初始化阶段还多了一道 FD 预检。HAProxy 需要：

```
maxconn × 2 + maxpipes × 2 + 34 = 1000000×2 + 1000000×2 + 34 = 4000034
```

（管道那两项是 splice 用的；本项目全程开着 splice，见 docs/06。）

给不够 HAProxy 会**拒绝启动**，留下一行 `[ALERT] Cannot raise FD limit to
4000034, limit is 4096.` 然后容器进入重启循环刷屏，真正的原因埋在滚动的
日志里。入口脚本现在从 cfg 里读出 `maxconn`/`maxpipes`（不写 `maxpipes`
时按默认的 `maxconn/4` 算），跟**硬上限**（`ulimit -Hn`——HAProxy 自己会
把软上限抬到硬上限，所以软的低不要紧）比一遍，不够就直接说清楚该改哪里。

## 5. 怎么用

初始化阶段自动执行，无需干预。手工使用：

```bash
# 体检：只看不改，有未达标项时退出码 1（适合放进上线检查）
docker compose exec node1 tune-kernel.sh check

# 宿主机持久化：把表落成 sysctl.d 配置
deploy/sysctl/tune-kernel.sh dump | sudo tee /etc/sysctl.d/99-rl-limiter.conf
sudo sysctl --system
```

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_TUNE_KERNEL` | `1` | 设 `0` 跳过调优（运维用别的方式统一管内核参数时） |

调优失败**不阻断启动**：它影响的是性能上限，不像 tc 自检那样关系到"限速
到底有没有生效"。FD 预检则会阻断——那种情况 HAProxy 本来也起不来。

### 验证真的生效了

| 想确认 | 命令 | 期望 |
| --- | --- | --- |
| backlog 没被削 | `ss -lnt 'sport = :8080'` | Send-Q 列 = 65536 |
| accept 队列没溢出 | `nstat -az TcpExtListenOverflows TcpExtListenDrops` | 保持 0 |
| 网卡没丢包 | `awk '{print $2}' /proc/net/softnet_stat` | 全 0 |
| TIME_WAIT 没爆 | `nstat -az TcpExtTCPTimeWaitOverflow` | 保持 0 |
| conntrack 没满 | `dmesg \| grep nf_conntrack` | 无 `table full` |

## 6. 刻意没调的

- **`net.ipv4.tcp_congestion_control`**（BBR 等）。限速由 tc HTB 执行，
  而 BBR 靠主动探测估带宽——它与 HTB 的整形丢包怎么互相影响，本项目
  没有实测过。没测过的东西不写进默认值。
- **`net.core.default_qdisc`**。被限速的网卡上，根 qdisc 由 tcshaper 用
  `tc qdisc replace ... root htb` 直接接管，这个默认值管不着它。
- **`net.ipv4.tcp_syncookies`**、**`tcp_abort_on_overflow`**。保持发行版
  默认（1 / 0）。syn_backlog 抬上去之后 syncookies 很少触发；把
  `abort_on_overflow` 改成 1 会用 RST 代替静默丢弃，看着"更明确"，实际是
  把本可重传成功的连接直接打死。
- **HAProxy 侧的 `tune.bufsize` / `tune.rcvbuf.*` / `cpu-map`**。都实测过
  且都不划算，原委见 [docs/06](06-tc限速方案.md) 与 `haproxy-base.cfg`
  里那段"这里特意不写的东西"。
- **网卡多队列 / RSS / IRQ 亲和性 / 中断合并**。这些是宿主机与网卡驱动层面
  的事（`ethtool -L/-C`、`set_irq_affinity`），容器里完全够不着，也高度
  依赖具体网卡型号，因此不进本表。32 核万兆以上部署值得单独做一轮。

---

## 7. 尚未验证的部分

诚实起见——本文里**经过实测的**只有：各参数在 netns 内的读写权限、
`sysctl -w` 失败仍返回 0、`somaxconn` 对 `listen()` backlog 的封顶
（4096 vs 65536）、以及 FD 预检的算式与解析。

**没有实测**的是这些参数在真实高并发/高带宽压力下的收益幅度：

- 沙箱内核只有 `pfifo`，没有 `sch_htb`，tc 限速本身就跑不起来；
- `ulimit -n` 硬上限被限死在 4096，`maxconn 1000000` 这条基线在这里根本
  加载不了，并发压测最多只能做到约 600（见 docs/06 §9）。

所以表里每一项的**方向**都有明确依据（默认值是多少、瓶颈在哪、溢出计数器
叫什么），但"调完快了百分之多少"需要在真实的 32 核机器上补测。上线前建议
按 §5 的验证表逐项对一遍计数器——那比相信一个数字可靠。
