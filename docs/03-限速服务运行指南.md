# 限速服务（rl-limiter）运行指南

> 对应设计：[01-方案设计.md](01-方案设计.md)。本文覆盖安装、配置来源、
> 本地演示与 HAProxy 侧接线。docker compose 一键演示（含 Web 控制台
> 玩法）见 [04-DockerCompose演示.md](04-DockerCompose演示.md)。

**架构一句话**：限速由各台 HAProxy 自身的 **shared bwlim**（聚合限速，
配置常量 + reload 调整）执行；rl-limiter 是独立部署的集中监控服务，
通过内网 TCP 连接多台 HAProxy 的 stats socket，每秒采样各节点 frontend
的 `bytes_out`，按节点聚合出带宽视图（控制台实时展示 + 环境聚合），
对照配置库中登记的节点限额做**持续超限告警**。

单位约定：配置里的 `quota_bps` 一律为 **bit/s**（40000000 = 40 Mbps）；
HAProxy `limit` 为 **bytes/s**（同一限额 = quota_bps ÷ 8 = 5000000）；
服务内部统一使用 bytes/s（唯一换算点在 `rl_limiter/model.py` 的
`EnvQuota.quota_bytes_per_sec`）。

## 1. 安装

要求 Python ≥ 3.11。依赖：PyYAML、aiohttp、aiomysql、cryptography
（MySQL 8+ 默认认证需要）。

```bash
pip install -e ".[test]"    # 或 make install
make test                   # 全部单元测试
rl-limiter --version        # 验证入口可用
```

## 2. 配置来源（二选一）

### 2.1 MySQL 配置库（生产推荐）

设置 `RL_MYSQL_HOST` 即启用：启动时从库加载全量配置（等库就绪最长
120s），运行期每 `RL_MYSQL_POLL_S` 秒轮询热更新。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_MYSQL_HOST` | 无（必设才启用） | 配置库地址 |
| `RL_MYSQL_PORT` | `3306` | |
| `RL_MYSQL_USER` / `RL_MYSQL_PASSWORD` | `rl` / 空 | |
| `RL_MYSQL_DB` | `rl_limiter` | |
| `RL_MYSQL_POLL_S` | `5` | 配置轮询周期（秒） |
| `RL_CONSOLE_PORT` | 无（必设才启用） | 内置 Web 控制台端口（只绑内网/防火墙内） |

表结构与种子示例：[deploy/mysql/init.sql](../deploy/mysql/init.sql)；
热更新边界与常用 SQL 见 [04-DockerCompose演示.md](04-DockerCompose演示.md)。

### 2.2 本地 YAML（standalone / 开发）

不设 `RL_MYSQL_HOST` 时读取 `-c` 指定的 YAML（默认
`/etc/rl-limiter/config.yaml`），完整注释示例见
[deploy/config/limiter.example.yaml](../deploy/config/limiter.example.yaml)：

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `log_level` | `info` | debug / info / warning / error |
| `tick_interval_s` | `1.0` | 采样节拍（秒），设计基准为 1 秒 |
| `haproxy_nodes[].name` | 必填 | 节点名，`envs[].targets[].node` 引用它 |
| `haproxy_nodes[].host` / `port` | 必填 | 该节点内网 TCP stats socket 地址（`level user` 即够） |
| `haproxy_nodes[].quota_bps` | 被挂载节点必填 | **该节点的登记限额**（bit/s）——超限告警基准，应与该节点 haproxy.cfg 里 shared bwlim 的 `limit` 一致 |
| `haproxy_nodes[].timeout_ms` | `500` | 单次 runtime API 命令超时（毫秒） |
| `envs[].env_id` | 必填 | 环境 ID（**纯分组**：环境不携带限额） |
| `envs[].targets[]` | 必填（≥1） | 挂载点：`{node, frontend}`；节点是环境的独占资源 |

## 3. 限额调整 SOP（生产日常操作）

限额是 HAProxy 配置常量，调整走两步发布流程（**缺一不可**）：

```text
1) 改库（控制台节点卡或 SQL）：
     UPDATE haproxy_nodes SET quota_bps = <bit/s> WHERE name = '<节点>';
   → rl-limiter 监控基准一个轮询周期内跟随。

2) 改数据面（原地修改 + reload）：
   编辑该节点 haproxy.cfg 对应 listen 的
     filter bwlim-out node-agg limit <bytes/s = quota_bps ÷ 8> ...
   然后 systemctl reload haproxy。
   新连接立即按新限额；存量连接最迟在 hard-stop-after 宽限期
   （建议 30~60s）结束时断开重连、进入新限额。
```

只做第 1 步不做第 2 步 → rl-limiter 打**持续超限告警**（控制台节点卡
高亮"超限"徽标），提醒补做第 2 步。

## 4. 本地监控演示（无需真实 HAProxy / MySQL）

仓库自带联调工具 `tools/fake_haproxy.py`（假 stats socket，`show stat`
计数器按指定速率增长）。

**终端 1、2：两台假 HAProxy**

```bash
python3 tools/fake_haproxy.py --port 19991 --frontends fe_env_a:2000000
python3 tools/fake_haproxy.py --port 19992 --frontends fe_env_b:500000
```

**终端 3：监控服务（standalone YAML）**

```bash
cp deploy/config/limiter.example.yaml /tmp/limiter.yaml
# 编辑 /tmp/limiter.yaml：
#   hap-1: host 127.0.0.1, port 19991；hap-2: host 127.0.0.1, port 19992
rl-limiter -c /tmp/limiter.yaml
```

可观察到的行为：

- 启动即打 `服务配置加载完成，以下为完整配置摘要 ...`，随后
  `已用本地静态配置完成引导（监控单元=节点） ...`；每分钟一条
  `运行状态周期汇总 ... units_summary=hap-1:mean10_bytes_per_s=...`；
- 把 YAML 里某节点的 `quota_bps` 改到低于其 fake 速率（如 hap-1 改为
  `10000000`，低于 2 MB/s=16 Mbps 的模拟流量）后重启：10 秒后出现
  `节点带宽持续高于登记限额 ...` 告警；改回后解除；
- 停掉一台 fake_haproxy：该节点进入 degraded（周期汇总的
  `degraded_nodes` 列出），带宽视图冻结、超限判定暂停，另一台节点
  完全不受影响；拉起后自动恢复。

想连同 MySQL / Web 控制台 / 真实 HAProxy + 真实限速一起演示，直接用
`make demo-up`（docker compose，见 docs/04）。

## 5. HAProxy 侧接线（每台受控节点）

- **版本 ≥ 2.8**（`bwlim` 过滤器 2.8 起正式；无法升级的节点只能退化为
  tc 单层硬限）。
- **聚合限速接线**（shared bwlim：stick-table 速率桶 + filter + 动作，
  含逐行说明与限额调整 SOP）见
  [deploy/haproxy/bwlim-example.cfg](../deploy/haproxy/bwlim-example.cfg)。
- `global` 段：
  - **内网 TCP stats socket**（rl-limiter 只读采样用）：

    ```
    stats socket ipv4@<内网IP>:9999 level user
    ```

    只允许绑内网 IP，安全组/防火墙仅放行监控服务器的 IP；可同时保留
    一行本机 unix socket（admin 级）用于应急运维。
  - **`hard-stop-after 60s`**：reload 后旧 worker 的强停宽限期，是
    "限额调整对存量长连接生效"的手段（见 §3）。
- `defaults`（或各受控 `listen`）段开启 **`option contstats`**（连续
  统计）。HAProxy 默认在会话结束时才把字节计入 frontend 统计，TCP 长
  连接会让 `bytes_out` 长期不动、断连时一次性跳变——逐秒差分测速会
  变成脉冲锯齿，与 iptraf-ng 等网卡级工具完全对不上。不开启此项，
  监控数据不可用。
- 经限速入口的流量应使用 keep-alive / 客户端侧关连接（服务端先 FIN
  会与整形数据竞争导致响应截断）。
- 内核层兜底部署在**各 HAProxy 机器本机**：
  [deploy/tc/backstop.sh](../deploy/tc/backstop.sh)，速率取节点限额的
  115%，如 40 Mbps 限额 → `./backstop.sh eth0 46`。它与 rl-limiter 服务
  无关，rl-limiter 也因此不需要 CAP_NET_ADMIN。

## 6. 容错行为表（设计 §3.7）

| 故障 | 行为 |
| --- | --- |
| 某台 HAProxy 节点失联 | 该节点采样失败当秒沿用上一秒速率；连续失败进入 degraded（周期汇总与控制台节点面板可见），带宽视图冻结、超限判定暂停；**限速不受任何影响**（在该节点进程内执行）；恢复后自动解除 |
| MySQL 配置库断联 / 宕机 | 按最后一次加载的配置继续监控（fail-static）；启动阶段等库就绪最长 120s（凭据/依赖类永久错误立即失败）；单次拉取带整体超时，静默网络分区不会卡死轮询 |
| 配置写错（含引用运行期新增节点） | 整份快照被拒绝，保留当前配置继续监控并打日志；控制台/写库入口对常见错误（限额非法、挂载点冲突、节点被他环境占用）当场返回中文错误 |
| rl-limiter 自身宕机 | systemd `Restart=always` 2 秒拉起；离线期间**限速照常**（HAProxy 进程内执行），只是监控/告警暂停 |
| HAProxy reload（发版/改限额） | 新 worker 按新配置限速；采集侧识别计数器回绕（沿用上一秒速率并重建基线），监控曲线无毛刺 |

## 7. 尚未包含（后续里程碑）

- **管理后台**：配额审批/审计、对账报表、发布自动化（自动生成 cfg +
  reload）、告警通知（M4）。配置权威是 MySQL 配置库，后台建设时应
  直接读写配置库。
- **tc 自动化**：backstop.sh 需在各 HAProxy 机器上手工执行，rl-limiter
  不校验/不维护 tc 规则。
- **指标外呈**：无 Prometheus 端点/Grafana 大盘（观测走内置 Web 控制台
  与结构化日志）；用量按天聚合入库未做。
- 其他：监控服务自身高可用（当前单实例 + systemd 拉起；宕机不影响限速）。
