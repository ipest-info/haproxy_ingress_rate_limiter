# 限速服务（rl-limiter）运行指南

> 对应设计：[01-方案设计.md](01-方案设计.md)。本文覆盖安装、两个配置
> 文件怎么写、本地演示与 HAProxy 侧接线。docker compose 一键演示（含
> Web 控制台玩法）见 [04-DockerCompose演示.md](04-DockerCompose演示.md)。

**架构一句话**：一个 rl-limiter 实例管**一台**与它同机的 HAProxy。
**haproxy.cfg 是负载均衡配置的唯一权威**（监听端口、模式、后端服务器由
运维直接编辑 + reload）；rl-limiter 只**读** cfg 解析出 frontend/listen
清单，与本地 YAML 里 quotas 登记的限额合并后，把限额下发到本机网卡的
**内核 tc（HTB）**（见 [06-tc限速方案.md](06-tc限速方案.md)），并经本机
unix stats socket 每秒采样各 frontend 的 `bytes_out` 做带宽视图与持续
超限告警。

单位约定：**限额的配置单位一律是 Mbps**（quotas 里填 40 = 40 Mbps，
允许小数）。服务内部统一使用 bytes/s（唯一换算点在
`rl_limiter/model.py` 的 `FrontendConfig.quota_bytes_per_sec`）。

## 1. 安装

要求 Python ≥ 3.9（生产存量机器的 3.9 可直接用；推荐 3.11+，
Ubuntu 24.04 自带 3.12）。依赖：PyYAML、aiohttp。

```bash
pip install -e ".[test]"    # 或 make install
make test                   # 全部单元测试
rl-limiter --version        # 验证入口可用
```

生产上装在**每台 HAProxy 服务器**上——一键装机脚本见
[09-裸机部署.md](09-裸机部署.md)（`sudo deploy/bare/rl-limiter.sh
install`）；手工装的话（Ubuntu 24.04 起系统 Python 受 PEP 668 保护，用
独立 venv 而不是 `pip install` 到系统解释器）：

```bash
# 每台 HAProxy 机器上：
python3 -m venv /opt/rl-limiter
/opt/rl-limiter/bin/pip install /path/to/rl-limiter    # 或 wheel/仓库地址
ln -sf /opt/rl-limiter/bin/rl-limiter /usr/local/bin/rl-limiter

# 专用非特权用户；读 HAProxy 的 unix stats socket 靠 haproxy 属组
useradd --system --no-create-home --shell /usr/sbin/nologin rl-limiter
usermod -aG haproxy rl-limiter

cp deploy/config/limiter.example.yaml /etc/rl-limiter/config.yaml
# 编辑它：cfg_path/socket_path 指向本机实际路径，quotas 按段名登记限额
cp deploy/systemd/rl-limiter.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now rl-limiter
```

## 2. 配置：两个本机文件

| 文件 | 谁写 | 内容 |
| --- | --- | --- |
| haproxy.cfg | 运维手工编辑 | 负载均衡配置的**唯一权威**：监听端口、模式、后端服务器 |
| YAML（`-c` 指定，默认 `/etc/rl-limiter/config.yaml`） | 运维手工编辑 | stats socket 接线、cfg 路径、quotas 限额登记、运行参数 |

rl-limiter 对 haproxy.cfg **绝对只读**；YAML 也以手工编辑为主，但控制
台页面/写 API 改限额（§3.4）时会把 quotas/`nic_quota_mbps` **回写**到
这份 YAML（整份校验 + 原子替换，**手写注释会丢**）。运行期轮询两份文件
的内容（5s），变化即热生效；文件短暂读不到时按最后一次配置继续跑
（fail-static）。**没有数据库**。

### 2.1 YAML 字段

完整注释示例见
[deploy/config/limiter.example.yaml](../deploy/config/limiter.example.yaml)：

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `log_level` | `info` | `debug` / `info` / `warn` / `error`（注意是 `warn`，不是 `warning`）。启动时定型，改了要重启 |
| `tick_interval_s` | `1.0` | 采样节拍（秒）。**设计基准为 1 秒，不要改动**——速率差分与告警窗口都以 1 拍 = 1 秒为前提 |
| `haproxy.name` | `haproxy` | 实例名（日志/控制台展示用） |
| `haproxy.socket_path` | 与 host/port 二选一 | **同机形态（推荐）**：本机 unix stats socket 绝对路径（如 `/run/haproxy/admin.sock`） |
| `haproxy.host` / `port` | 与 socket_path 二选一 | **远程观测形态**：内网 TCP stats socket。此形态下 rl-limiter 不在 HAProxy 本机，**无法做 tc 限速**，一般只用于纯监控 |
| `haproxy.cfg_path` | **必填** | 本机 haproxy.cfg 的绝对路径——受管 frontend 清单从它解析 |
| `haproxy.timeout_ms` | `500` | 单次 runtime API 命令超时（毫秒） |
| `quotas` | `{}` | **限额登记**：frontend 名（= cfg 里 frontend/listen 段的名字）→ 限额（Mbps，≥ 0）。**0 = 显式不限速**（撤掉该端口的 tc 类，不再提醒"未登记"）。热生效 |
| `nic_quota_mbps` | `0` | **网卡总限速**（Mbps；0/不写 = 不限）。整张限速网卡出方向的总闸：所有流量（受管端口 + SSH/监控等未受管流量）合计不超过它，各 frontend 限额仍各自生效（单端口上限 = min(自身限额, 总限速)）。设置后 tc 切换为层级模式（见 06 文档）。热生效 |

`socket_path` 与 `host`/`port` **同时给会被拒绝**（最常见的配错：加了
`socket_path` 却忘了清掉旧的 `host`/`port`）；一个都不给同样拒绝。
旧版 YAML 里的 `frontends` 段（带监听端口/后端服务器）**会被显式拒绝**
并提示迁移方向——负载均衡配置已改为从 haproxy.cfg 直接读取。

### 2.2 cfg 与 quotas 的合并规则

| 情况 | 行为 |
| --- | --- |
| cfg 里有、quotas 登记了 | 限速（tc）+ 监控 + 超限告警 |
| cfg 里有、quotas 没登记 | **只监控不限速**（不建 tc 类、不判超限），启动时 warn 一次 |
| cfg 里有、quotas **显式写 0** | 同样只监控不限速，但这是运维的明确决定，**不 warn**；全部为 0/清空时整棵 tc 队列树被拆掉、网卡恢复默认 qdisc |
| quotas 登记了、cfg 里没有 | 该条目被忽略并 warn（段被删了或名字拼错） |

解析口径（刻意保守，完整语法校验是 `haproxy -c` 的职责）：只认
`frontend`/`listen` 段（backend 无监听端口）；每段取**第一条** `bind`
的端口（多 bind 段其余端口不在限速范围内，会 warn——需要限速的端口应
各自成段）；`mode` 缺省继承 `defaults`；名为 `stats` 的段与没有 bind
的段跳过。

### 2.3 环境变量（本机硬件/运行相关）

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_TC_IFACE` | 自动探测 | **限速在哪张网卡上执行**。不设则取默认路由的出口网卡；两网卡部署时指向**客户端侧**那张；探测不出来直接启动失败。设 `-` 明确关闭限速（只监控）。**单网卡时监听端口须避开本机临时端口范围**（典型 32768–60999），否则限速会偶发失准——原因与两网卡的取舍见 06 文档第 6 节 |
| `RL_NIC` | 同 `RL_TC_IFACE` | 实例监控视图里**入向**数据包统计要采样的网卡（取自 `/proc/net/dev`）。出向的包/丢包已由 tc 按 frontend 精确统计，不需要它。设 `-` 禁用。详见 [05-监控视图.md](05-监控视图.md) |
| `RL_CONSOLE_PORT` | 无（必设才启用） | 内置 Web 控制台端口；同端口的 `GET /metrics` 提供 Prometheus 抓取、`/api/quotas/*`、`/api/nic-quota` 提供限额写 API（§3.4） |
| `RL_CONSOLE_BIND` | `127.0.0.1` | 控制台监听地址。**读接口无鉴权**（暴露全量监控数据与日志），放到内网必须配合防火墙/安全组限制来源 |
| `RL_API_TOKEN` | 无 | **写 API 的鉴权令牌**（`openssl rand -hex 24` 生成一个即可）。不设则写接口整体 403、控制台页面退化为只读；读接口/监控不受影响 |
| `RL_METRICS_LOG` | 无（必设才启用） | **监控数据落盘**：本地 JSONL 文件路径（分钟粒度，avg/max/mean10_max/超限秒数，限额随行），按天轮转。systemd 部署推荐 `/var/log/rl-limiter/metrics.jsonl`（unit 的 LogsDirectory 自动建目录并授权） |
| `RL_METRICS_LOG_DAYS` | `90` | 落盘文件保留天数（按天轮转后删除更旧的） |
| `RL_TUNE_KERNEL` | `1` | （容器入口脚本）初始化阶段是否自动调优内核参数。裸机 systemd 部署由装机脚本处理，见 [08-内核参数调优.md](08-内核参数调优.md) |

## 3. 配置调整 SOP（生产日常操作）

限额类（quotas / 网卡总限速）有三条等价入口：编辑文件、控制台页面、
写 API（后两条见 §3.4）；监听端口/后端只有编辑 haproxy.cfg 一条路。

### 3.1 改限额（最常见，热生效、不 reload）

```text
编辑 YAML 的 quotas 段：
  quotas:
    fe_main: 20        # 40 → 20 Mbps
     ↓ 一个轮询周期内（≤5s）
rl-limiter 执行 tc class change（就地改令牌速率，不动队列结构）
     ↓
存量连接（含长连接）**立刻**按新限额跑；连接不断、不 reload。
```

不想限速有两种写法：**删掉那一行**（cfg 里的段回到"未登记"状态，启动
时会 warn 提醒），或**显式写 0**（运维确认过的不限速，不再提醒）。两者
都会撤掉该端口的 tc 类；全部不限速时整棵限速队列树被拆掉、网卡恢复默认
qdisc。负数会被校验拒绝。

### 3.2 改监听端口 / 后端服务器

```text
编辑 haproxy.cfg（加/删/改 frontend、listen、server 行）
     ↓
systemctl reload haproxy        # 数据面生效（HAProxy 的固有流程）
     ↓ 一个轮询周期内（≤5s）
rl-limiter 解析到 cfg 内容变化，自动更新监控清单与 tc 分类
（新段开始被监控；新段要限速记得在 quotas 里加一行）。
```

注意顺序无所谓——先改 cfg 还是先改 quotas 都行，两边各自热生效，最终
收敛到一致。

### 3.3 改限额为什么不需要 reload

限速在内核 tc 上，改限额是 `tc class change`——队列的令牌速率就地改掉，
**存量连接立刻跟上，连接不断**。需要 reload 的只剩监听端口与后端服务器
的变更（那是 HAProxy 的固有约束）。

对比之前的 bwlim 方案：那时 limit 是配置常量、运行期改不了，改限额必须
reload，而且存量连接要等 `hard-stop-after` 宽限期结束被断开重连才会用上
新限额。详见 [06-tc限速方案.md](06-tc限速方案.md) §4.1。

检查限速有没有真的生效：`python3 tools/tc_check.py verify`。

### 3.4 控制台页面 / 写 API 改限额（带鉴权，回写 YAML）

前提：`RL_CONSOLE_PORT` 已启用控制台，且服务环境变量里设了
`RL_API_TOKEN`（裸机部署写在 `/etc/rl-limiter/rl-limiter.env`；不设则
写接口整体 403，页面退化为只读）。systemd 部署还需要 unit 放开配置目录
的写权限（`ReadWritePaths=/etc/rl-limiter`，装机脚本生成的 unit 已带；
目录与 config.yaml 的属组须是服务用户且可写，装机脚本会校正）。

**页面**：打开控制台，在页头输入框填入令牌（存浏览器 localStorage）。
frontend 卡片右上角改单端口限额（0 = 显式不限速，"删除登记" = 回到只
监控）；"实例" tab 的"网卡总限速"卡改整卡总闸。

**API**（`Authorization: Bearer <token>` 或 `X-API-Token: <token>`）：

```bash
TOKEN=<RL_API_TOKEN 的值>
# 改单个 frontend 限额（Mbps；0 = 显式不限速）
curl -X PUT -H "X-API-Token: $TOKEN" -H "Content-Type: application/json" \
     -d '{"quota_mbps": 20}' http://127.0.0.1:8090/api/quotas/fe_main
# 删除登记（回到"只监控不限速"，启动时会 warn 提醒）
curl -X DELETE -H "X-API-Token: $TOKEN" http://127.0.0.1:8090/api/quotas/fe_main
# 设置/取消网卡总限速（Mbps；0 或 DELETE = 不限）
curl -X PUT -H "X-API-Token: $TOKEN" -H "Content-Type: application/json" \
     -d '{"quota_mbps": 800}' http://127.0.0.1:8090/api/nic-quota
curl -X DELETE -H "X-API-Token: $TOKEN" http://127.0.0.1:8090/api/nic-quota
```

行为要点：

- 完整的接口参考（全部读/写端点、响应字段口径、错误码、集成示例）见
  [07-API文档.md](07-API文档.md)——给第三方程序对接用的就是那份；
- 修改先过与启动完全相同的校验链，**不合法直接 400、文件不动**——绝不
  会写出一份服务重启后加载不了的 YAML；给 cfg 里不存在的段名登记限额
  同样 400（并列出现有段名，多半是拼错了）；
- 回写是"临时文件 + 原子替换"，读者绝不会见到半份文件；**YAML 里的
  手写注释会丢**（数据往返的限制，文件头部会注明）；
- 写完立即触发配置重读（不等 5s 轮询），tc 数秒内跟上；
- 监控数据本身没有写接口——`/metrics`、`/api/overview` 等读接口与写
  接口共用端口但互不相干，令牌只管写。

## 4. 本地监控演示（无需真实 HAProxy）

仓库自带联调工具 `tools/fake_haproxy.py`（假 stats socket，`show stat`
计数器按指定速率增长；`--unix-path` 模拟同机形态、`--port` 模拟跨机
TCP 形态）。

**终端 1：本机假 HAProxy（unix socket，同机形态）**

```bash
mkdir -p /tmp/rl
python3 tools/fake_haproxy.py --unix-path /tmp/rl/hap1.sock \
    --frontends fe_main:2000000
```

> unix socket 路径受内核 `sun_path` 限制（Linux 107 字节），别放在很深
> 的目录里——超长路径会在启动校验时被直接拒绝。

**终端 2：监控服务（YAML + 一份最小 haproxy.cfg）**

```bash
# 受管清单来自 haproxy.cfg：给一份只含 fe_main 的最小 cfg
cat > /tmp/rl/haproxy.cfg <<'EOF'
listen fe_main
    bind :8080
EOF
cp deploy/config/limiter.example.yaml /tmp/limiter.yaml
# 编辑 /tmp/limiter.yaml：
#   haproxy.socket_path: /tmp/rl/hap1.sock
#   haproxy.cfg_path:    /tmp/rl/haproxy.cfg
#   quotas: {fe_main: 40}
RL_TC_IFACE=- RL_CONSOLE_PORT=8090 rl-limiter -c /tmp/limiter.yaml
```

（`RL_TC_IFACE=-` 关闭 tc——本地演示只看监控链路，不需要 root。）

可观察到的行为：

- 启动即打 `已用 haproxy.cfg + YAML 限额完成引导 ... frontends=1
  detail=fe_main@:8080,quota=40Mbps`；
- 每分钟一条 `运行状态周期汇总 ... summary=fe_main:mean10_bytes_per_s=...`；
- 打开 http://127.0.0.1:8090 ：每个 frontend 一张卡片（曲线 + 配置视图，
  只读）；
- 把 YAML 里 `fe_main` 的限额改到低于 fake 速率（如 `10`，低于
  2 MB/s = 16 Mbps 的模拟流量）：5s 内热生效，10 秒后出现
  `frontend 带宽持续高于限额 ...` 告警；改回后解除；
- 往 /tmp/rl/haproxy.cfg 里加一个 `listen fe_new` 段：5s 内控制台多出
  一张卡片（未登记限额，显示"仅监控"口径）；
- 停掉 fake_haproxy：出现 `采样失败 ...（fail-static）`，连续 10 秒后
  进入 degraded、超限判定暂停；拉起后自动恢复。

想连同真实 HAProxy（Ubuntu 24.04）+ 真实 tc 限速一起演示，直接用
`make demo-up`（docker compose，见 docs/04）。

## 5. HAProxy 侧接线（每台机器）

haproxy.cfg 整份都是你的（rl-limiter 只读不写），完整示例见
[deploy/haproxy/haproxy-example.cfg](../deploy/haproxy/haproxy-example.cfg)
（compose 演示用的是 `deploy/docker/haproxy-base.cfg`）。要点：

- **版本 ≥ 2.8**（`option splice-*` 与监控用的 stats 列都以 2.8 为准；Ubuntu 24.04 自带 2.8.16）。
- `global` 段：
  - **本机 unix stats socket**（同机的 rl-limiter 只读采样用）：

    ```
    stats socket /run/haproxy/admin.sock mode 660 level user
    ```

    路径要与 YAML 的 `haproxy.socket_path` 一致。`mode 660` 让访问权
    由文件属主/属组控制——把 rl-limiter 的运行用户加进 `haproxy` 组即可，
    **不需要 root，也不占任何网络端口**。

    远程只读观测形态改用内网 TCP（YAML 填 `host`/`port`）：

    ```
    stats socket ipv4@<内网IP>:9999 level user
    ```

    此时 socket 暴露在网络上，只允许绑内网 IP（绝不可绑 `0.0.0.0`），
    安全组/防火墙仅放行监控服务器的 IP。同机形态没有这层暴露面，优先选它。
  - **`hard-stop-after 60s`**：reload 后旧 worker 的强停宽限期。限额调整
    **不依赖它**（tc 改限额不 reload）；它只影响改监听端口/后端时存量
    连接被断开重连的最长等待。
- `defaults`（或各 `listen`）段开启 **`option contstats`**（连续统计）。
  HAProxy 默认在会话结束时才把字节计入 frontend 统计，TCP 长连接会让
  `bytes_out` 长期不动、断连时一次性跳变——逐秒差分测速会变成脉冲锯齿，
  与 iptraf-ng 等网卡级工具完全对不上。不开启此项，监控数据不可用。
- 业务 `listen`/`frontend` 段：一个段 = 一个监控单位 = 一个 tc 速率类。
  段名就是 stats 的 pxname，也是 quotas 的键——**三处一致**。一个段只放
  一个 bind 端口。段里开 `option splice-auto/request/response`（限速在
  tc 上，与 splice 不冲突——这正是换 tc 的收益）。
- 经限速入口的流量应使用 keep-alive / 客户端侧关连接（服务端先 FIN
  会与整形数据竞争导致响应截断）。

### 5.1 高并发 / 高带宽调优（32 核 TCP 代理基线）

可直接抄的完整配置见
[deploy/docker/haproxy-base.cfg](../deploy/docker/haproxy-base.cfg)。每项的
**实测依据**统一放在 [06-tc限速方案.md](06-tc限速方案.md)，这里只列取值：

| 项 | 取值 | 一句话理由 |
| --- | --- | --- |
| `maxconn` | `1000000` | **默认值不该成为限制**：默认给到 100 万连接，真要限并发用 frontend 级 maxconn。**改它必须同步改 FD 上限**，见下 |
| `maxpipes` | `1000000`（= maxconn） | splice 的内核管道池，默认只给 maxconn/4；不够时吞吐直接掉。同时在传的连接远少于 maxconn 时可以调小，省一半 FD |
| `nbthread` | **不写** | 2.8 起自动等于可用 CPU 数；写死会在换机器/限核后失配 |
| `tune.listener.default-shards` | `by-thread` | 每线程一个 SO_REUSEPORT 监听套接字，改善 accept 扩展性 |
| `tune.bufsize` | **不写** | splice 全程可用时无收益，却让每连接内存涨 3 倍 |
| `tune.rcvbuf.*` / `tune.sndbuf.*` | **不写** | 写死会关掉内核自动调优，实测是负优化 |
| `cpu-map` | 默认注释掉 | 裸金属独占可开；容器里会把线程钉到 cpuset 之外的核 |

**唯一会让服务起不来的一项是 FD 上限**：

```
FD 需求 = maxconn × 2 + maxpipes × 2 + 34 = 4000034
[ALERT] Cannot raise FD limit to 4000034, limit is 4096.   ← 给不够就是它
```

要放开的是 **haproxy 自己的** unit（不是 rl-limiter 的）：
`systemctl edit haproxy` 里写 `LimitNOFILE=4194304`；容器里用 compose 的
`ulimits.nofile`。

**还有一道容器里改不动的天花板**：`fs.nr_open` 默认 1048576，压不住 400 万。
不先在宿主机把它抬上去，`LimitNOFILE` 根本设不上去（容器则是压根起不来）。
`deploy/sysctl/tune-kernel.sh` 里已经带上这一项，见 [08-内核参数调优.md](08-内核参数调优.md)。

> 别用 `no strict-limits` 绕开：实测它**不会把 maxconn 降下来**，只是把
> 启动期的明确失败换成运行期莫名其妙的 accept 失败。

资源预算：实测约 20 KB/连接，`maxconn 1000000` 满载约 20 GB（按需分配，
满载才用得到）。机器扛不住就把 `maxconn` 往下调——**有意识地设限，好过
被一个默认值悄悄卡住**。

**HAProxy 这边配好了还不够，内核默认值会在下面把它削掉。** 最典型的一条：
上面配置里写的 `backlog 65536` 被 `net.core.somaxconn`（发行版默认 4096）
静默封顶，实测 `ss -lnt` 的 Send-Q 只有 4096——配置写着 65536，溢出的 SYN
被内核直接丢弃，客户端看到偶发连接超时而 HAProxy 日志里干干净净。容器部署
还有 `nf_conntrack_max` 默认 262144 撑不住 10 万连接的问题。

容器节点在初始化阶段（启动 HAProxy 之前）自动跑
[deploy/sysctl/tune-kernel.sh](../deploy/sysctl/tune-kernel.sh) 把这些抬到位，
并对 FD 上限做预检。**裸机 systemd 部署**由装机脚本处理（或手工落一份）：

```bash
deploy/sysctl/tune-kernel.sh dump | sudo tee /etc/sysctl.d/99-rl-limiter.conf
sudo sysctl --system
deploy/sysctl/tune-kernel.sh check     # 体检，有未达标项时退出码 1
```

取值、依据与"怎么验证真的生效了"见 [08-内核参数调优.md](08-内核参数调优.md)。

> **压测时的一个坑**：若读到"正好 2 倍限额"，先查有没有上一个 haproxy
> 进程没退干净——SO_REUSEPORT 会让两个进程共享同一个端口、各自按限额整形，
> 看起来就像限速失效了一倍。本项目已经被这个假象骗过两次。验证时按 PID
> 确认旧进程真的退了，别只看端口。

## 6. 容错行为表（设计 §3.7）

| 故障 | 行为 |
| --- | --- |
| 本机 HAProxy 停止 / stats socket 消失 | 采样失败当秒沿用上一秒速率；连续 10 秒失败进入 degraded（周期汇总与控制台可见），带宽视图冻结、超限判定暂停；socket 回来后自动解除。**已下发的 tc 限速不受影响** |
| 整台节点宕机 | 该节点的限速与监控一起消失（本就没有流量经过它）；**其它节点完全不受影响**——同机形态下不存在"监控服务器挂了所有节点都瞎"的单点 |
| haproxy.cfg / YAML 短暂读不到（原子替换瞬间、编辑到一半） | 保留当前配置继续运行（fail-static），warn 后下一轮再试 |
| 配置写错（quotas 写 0、名字非法、接线两个都给…） | 启动时：直接失败并点名字段；运行期：整份新配置被拒绝，保留当前配置继续跑并打日志（fail-static） |
| quotas 登记的段在 cfg 里不存在 | 该条目被忽略并 warn（多半是段被删了或拼错）——不会拿错段限速 |
| rl-limiter 自身崩溃 | systemd `Restart=always` 2 秒拉起；离线期间**限速照常**（tc 规则在内核里），只是本机监控/告警与限额调整暂停 |
| HAProxy reload（发版/改端口） | 新 worker 按 cfg 转发；采集侧识别计数器回绕（沿用上一秒速率并重建基线），监控曲线无毛刺；tc 规则不受 reload 影响 |

## 7. 尚未包含（后续里程碑）

- **历史数据查询界面**：监控数据可落盘（`RL_METRICS_LOG`，分钟粒度
  JSONL 保留 90 天）+ `/metrics` 可被 Prometheus 抓取，但本服务不提供
  历史查询页面——回查用 grep/jq 直接读 JSONL，或在 Grafana 里查
  Prometheus。
- **跨机汇总视图**：每个控制台只看本机，多台合计走 Prometheus 聚合。
- **多机配置分发**：quotas 是本机 YAML 里的几行，多机统一管理交给
  Ansible/SaltStack 等配置管理下发。
- 其他：监控服务自身高可用（当前单实例 + systemd 拉起；宕机不影响限速）。
