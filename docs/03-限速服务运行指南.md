# 限速服务（rl-limiter）运行指南

> 对应设计：[01-方案设计.md](01-方案设计.md)。本文覆盖安装、配置来源、
> 本地演示与 HAProxy 侧接线。docker compose 一键演示（含 Web 控制台
> 玩法）见 [04-DockerCompose演示.md](04-DockerCompose演示.md)。

**架构一句话**：一个 rl-limiter 实例管**一台**与它同机的 HAProxy——把
配置库里的监听端口、限额、后端服务器渲染进本机 haproxy.cfg 的受管区块
并 reload（改完立刻生效），同时经本机 unix stats socket 每秒采样各
frontend 的 `bytes_out` 做带宽视图与持续超限告警。限速本身由**内核 tc
（HTB）**执行，见 [06-tc限速方案.md](06-tc限速方案.md)。

单位约定：**限额的配置单位一律是 Mbps**（`quota_mbps`，40 = 40 Mbps，
允许小数）。数据库、本地 YAML、Web 控制台三个配置入口用的都是这一个
字段、这一个单位；服务内部统一使用 bytes/s（唯一换算点在
`rl_limiter/model.py` 的
`FrontendConfig.quota_bytes_per_sec`）。

## 1. 安装

要求 Python ≥ 3.11（Ubuntu 24.04 自带 3.12，直接可用）。依赖：PyYAML、
aiohttp、aiomysql、cryptography（MySQL 8+ 默认认证需要）。

```bash
pip install -e ".[test]"    # 或 make install
make test                   # 全部单元测试
rl-limiter --version        # 验证入口可用
```

生产上装在**每台 HAProxy 服务器**上（Ubuntu 24.04 起系统 Python 受
PEP 668 保护，用独立 venv 而不是 `pip install` 到系统解释器）：

```bash
# 每台 HAProxy 机器上：
python3 -m venv /opt/rl-limiter
/opt/rl-limiter/bin/pip install /path/to/rl-limiter    # 或 wheel/仓库地址
ln -sf /opt/rl-limiter/bin/rl-limiter /usr/local/bin/rl-limiter

# 专用非特权用户；读 HAProxy 的 unix stats socket 靠 haproxy 属组
useradd --system --no-create-home --shell /usr/sbin/nologin rl-limiter
usermod -aG haproxy rl-limiter

cp deploy/systemd/rl-limiter.service /etc/systemd/system/
# 编辑 unit：把 RL_NODE_NAME 改成本机在配置库里的节点名
systemctl daemon-reload && systemctl enable --now rl-limiter
```

## 2. 部署形态与配置来源

### 2.0 一个实例 = 一台 HAProxy

`RL_NODE_NAME` 指定本实例对应配置库 `haproxy_instances` 里的哪一行
（默认 `haproxy`）。多台机器可以共用一个配置库：各自只读写属于自己的
那些行，集中管理与集中审计因此得以保留。

`RL_NODE_NAME` 与库里对不上会在启动时直接失败并说明原因——容忍它会让
服务"看起来在跑"却什么都采不到。

采样通道二选一：**本机 unix socket**（`socket_path`，推荐；不占网络
端口、按文件属组授权）或**内网 TCP**（`host`/`port`，远程只读观测；
此形态**无法下发配置**，因为改 cfg + reload 必须在本机做）。

### 2.1 配置来源（二选一）

#### 2.1.1 MySQL 配置库（生产推荐）

设置 `RL_MYSQL_HOST` 即启用：启动时从库加载全量配置（等库就绪最长
120s），运行期每 `RL_MYSQL_POLL_S` 秒轮询热更新。

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_MYSQL_HOST` | 无（必设才启用） | 配置库地址 |
| `RL_MYSQL_PORT` | `3306` | |
| `RL_MYSQL_USER` / `RL_MYSQL_PASSWORD` | `rl` / 空 | |
| `RL_MYSQL_DB` | `rl_limiter` | |
| `RL_MYSQL_POLL_S` | `5` | 配置轮询周期（秒） |
| `RL_NODE_NAME` | `haproxy` | 本实例对应配置库里的哪个 HAProxy 实例 |
| `RL_APPLY_HAPROXY_CFG` | 无 | 设为本机 haproxy.cfg 路径即启用**配置自动下发**（改完立刻生效，见 §3.1） |
| `RL_APPLY_RELOAD_CMD` | `systemctl reload haproxy` | reload 命令（只从本机环境变量读） |
| `RL_APPLY_PERIOD_S` | `30` | 兜底 reconcile 周期（秒） |
| `RL_CONSOLE_PORT` | 无（必设才启用） | 内置 Web 控制台端口 |
| `RL_CONSOLE_BIND` | `127.0.0.1` | 控制台监听地址。**控制台无鉴权且带写接口**，放到内网必须配合防火墙/安全组限制来源 |
| `RL_TC_IFACE` | 自动探测 | **限速在哪张网卡上执行**（限速由内核 tc 承担，见 [06-tc限速方案.md](06-tc限速方案.md)）。不设则取默认路由的出口网卡；两网卡部署时指向**客户端侧**那张；探测不出来直接启动失败。设 `-` 明确关闭限速。**单网卡时监听端口须避开本机临时端口范围**（典型 32768–60999），否则限速会偶发失准——原因与两网卡的取舍见 06 文档第 6 节 |
| `RL_TUNE_KERNEL` | `1` | 初始化阶段是否自动调优内核参数（somaxconn、syn_backlog、临时端口、缓冲上限等）。设 `0` 跳过——运维用别的方式统一管内核参数时才需要。不调的话内核默认值会在 HAProxy 的 `maxconn` 下面先成为瓶颈，且**不会有任何告警**；详见 [08-内核参数调优.md](08-内核参数调优.md) |
| `RL_METRICS_RETENTION` | 开启 | 监控数据落库（1 分钟粒度存 7 天、5 分钟粒度存 90 天，支持 **90 天回查**与 95 计费）。设 `0`/`false` 关闭。仅数据库模式下生效。详见 [07-监控数据回查.md](07-监控数据回查.md) |
| `RL_NIC` | 同 `RL_TC_IFACE` | 实例监控视图里**入向**数据包统计要采样的网卡（取自 `/proc/net/dev`）。出向的包/丢包已由 tc 按 frontend 精确统计，不需要它。不设则跟随 `RL_TC_IFACE`；设 `-` 禁用入向包统计。详见 [05-监控视图.md](05-监控视图.md) |

表结构与种子示例：[deploy/mysql/init.sql](../deploy/mysql/init.sql)；
热更新边界与常用 SQL 见 [04-DockerCompose演示.md](04-DockerCompose演示.md)。

> **从 v0.3 升级**：配置模型不兼容——`haproxy_nodes` / `envs` /
> `env_targets` 三张表被 `haproxy_instances` / `haproxy_frontends` /
> `haproxy_servers` 取代（建表语句见 init.sql）。旧模型见 tag
> `v0.3.0-colocated`。

#### 2.1.2 本地 YAML（standalone / 开发）

不设 `RL_MYSQL_HOST` 时读取 `-c` 指定的 YAML（默认
`/etc/rl-limiter/config.yaml`），完整注释示例见
[deploy/config/limiter.example.yaml](../deploy/config/limiter.example.yaml)：

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `log_level` | `info` | `debug` / `info` / `warn` / `error`（注意是 `warn`，不是 `warning`） |
| `tick_interval_s` | `1.0` | 采样节拍（秒）。**设计基准为 1 秒，不要改动**——速率差分与告警窗口都以 1 拍 = 1 秒为前提 |
| `haproxy.name` | `haproxy` | 实例名；数据库模式下须与 `RL_NODE_NAME` 一致 |
| `haproxy.socket_path` | 与 host/port 二选一 | **同机形态**：本机 unix stats socket 绝对路径（如 `/run/haproxy/admin.sock`） |
| `haproxy.host` / `port` | 与 socket_path 二选一 | **远程观测形态**：内网 TCP stats socket（此形态**无法下发配置**） |
| `haproxy.timeout_ms` | `500` | 单次 runtime API 命令超时（毫秒） |
| `haproxy.limit_scope` | `host` | **限速范围**：`host` = 整机限速（一个总闸门罩住本机网卡全部出向，不按端口分类）；`frontend` = 按监听端口分别限速。限额按机器算就用前者，按入口算才用后者。两种范围的取舍见 [06 文档 §2](06-tc限速方案.md) |
| `haproxy.host_quota_mbps` | 留空 | 整机限额（**Mbps**，允许小数）。**留空 = 不限速**（默认值不该成为限制），填正数才开闸门。**留空与填 0 不是一回事**：填 0 直接拒绝——0 Mbps 谁也跑不动，那是配错了而不是"不想限"，用 0 兼表"没设"会让打错字静默变成不限速。`limit_scope: frontend` 时这一项不用 |
| `frontends[].name` | 必填 | frontend 名 = stats 的 pxname，也是 cfg 里的段名；实例内唯一 |
| `frontends[].bind_port` | 必填 | 监听端口 |
| `frontends[].bind_address` | `""` | 监听地址；留空 = 所有地址 |
| `frontends[].quota_mbps` | 必填 | 限额（**Mbps**，允许小数）。`limit_scope: frontend` 时是下发给 tc 的类速率（真实限速），`limit_scope: host` 时只作为超限告警基准（真正的闸门是 `host_quota_mbps`）。两种情况下都是同一个字段，因此告警基准与真实限速不会漂移 |
| `frontends[].mode` | `tcp` | `tcp` / `http` |
| `frontends[].maxconn` | `0` | 资源保护水位（0 = 不写该指令）；不是限速手段 |
| `frontends[].balance` | `roundrobin` | `roundrobin`/`static-rr`/`leastconn`/`first`/`source`/`random` |
| `frontends[].timeout_*_ms` | `5000`/`50000`/`50000` | connect / client / server |
| `frontends[].servers[]` | 必填（≥1） | 后端服务器：`{name, address, port, weight, check, check_inter_ms}` |

名字与后端地址受字符集白名单限制（字母/数字/点/下划线/连字符，地址另
允许冒号）——它们会被原样渲染进 haproxy.cfg，放宽等于允许通过配置库往
配置文件注入指令。

`socket_path` 与 `host`/`port` **同时给会被拒绝**（最常见的配错：加了
`socket_path` 却忘了清掉旧的 `host`/`port`）；一个都不给同样拒绝。

## 3. 配置调整 SOP（生产日常操作）

### 3.1 启用配置自动下发后（推荐，改完立刻生效）

**只有一步**：在 Web 控制台上改（或直接改配置库）。监听端口、限额、
后端服务器都是这一步。**限速范围与整机限额在「实例」页上改**（它是实例级
配置，不属于任何监听端口）：

```text
-- 开启整机限速（默认是整机范围但不设限额 = 不限速）
UPDATE haproxy_instances SET host_quota_mbps = 1000 WHERE name = '<实例>';
-- 关掉限速：置回 NULL（不是 0——填 0 会被拒）
UPDATE haproxy_instances SET host_quota_mbps = NULL WHERE name = '<实例>';
-- 改用按监听端口限速
UPDATE haproxy_instances SET limit_scope = 'frontend' WHERE name = '<实例>';
```

只改整机限额走 `tc class change`，不打断任何连接；切换范围、以及在
"限速/不限速"之间来回都会动队列树（有一个极短的不整形窗口）。把限额从
有值改成 NULL 会**拆掉整棵队列树**——本机限速就此关闭，日志里会有一条
明确的 warning，不会悄悄发生。

```text
改配置（Web 控制台上改端口/限额/后端服务器，或 SQL）：
  UPDATE haproxy_frontends SET quota_mbps = <Mbps>
    WHERE instance = '<实例>' AND name = '<frontend>';
     ↓ 一个轮询周期内
该机器的 rl-limiter 自动：渲染受管区块 → haproxy -c 校验
  → 原子替换 → reload
     ↓
新建连接立即按新配置；存量连接最迟在 hard-stop-after 宽限期结束时
断开重连、进入新配置。
```

实测（HAProxy 2.8.16，同机）：rl-limiter 完成一次应用 **~74 ms**，
新 worker 接管 ~23 ms，reload 后新建连接**立刻**按新限额。

控制台顶部会显示应用状态：绿色横幅 = 已生效；红色横幅 = 应用失败并附
具体原因，**此时数据面仍在按调整前的限额运行**（下一轮自动重试）。

启用方式：

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_APPLY_HAPROXY_CFG` | 无（**设了才启用**） | 本机 haproxy.cfg 路径 |
| `RL_APPLY_RELOAD_CMD` | `systemctl reload haproxy` | reload 命令。**只从本机环境变量读，绝不从配置库读**——否则拿到库写权限就等于在每台 HAProxy 上远程执行任意命令 |
| `RL_APPLY_PERIOD_S` | `30` | 兜底 reconcile 周期（秒）。变更是事件驱动的即时生效，这个只用来纠正手改 cfg 与重试失败的应用 |

所需授权与 systemd 加固项的配合（cfg 目录可写、polkit/sudoers 授权
reload、`ReadWritePaths`、`NoNewPrivileges` 与 sudo 的冲突）见
[deploy/systemd/rl-limiter.service](../deploy/systemd/rl-limiter.service)
文件头，那里有可直接抄的配置片段。

**配置漂移自动修复**：下发逻辑幂等且持续 reconcile，所以有人手改了受管
区块也会在一个兜底周期内被拉回——配置库是唯一真相源这件事由此真正成立。
标记之外的手写内容不受影响。

### 3.2 未启用时（纯人工，两步缺一不可）

```text
1) 改库：UPDATE haproxy_frontends SET quota_mbps = <Mbps>
     WHERE instance = '<实例>' AND name = '<frontend>';
   → rl-limiter 监控基准一个轮询周期内跟随。
2) 改数据面：在本机执行
     tc class change dev <网卡> parent 1: classid 1:<监听端口的十六进制> htb \
       rate <Mbps×1e6>bit ceil <同左>bit burst <约10ms额度> cburst <同左>
   （不需要 reload HAProxy；命令可用 tools/tc_check.py plan 生成）。
```

**手敲这条命令有两个坑，建议直接用 `tc_check.py plan` 生成而不是自己拼**：
classid 的次要号被 iproute2 按**十六进制**解析（端口 8080 要写 `1:1f90`，
写 `1:8080` 是另一个类；10000 以上的端口写十进制会直接报 `invalid class
ID`）；`cburst` 漏了的话 tc 会兜底成 MTU 量级，**速率显示完全正常而实际
吞吐远低于限额**。两个坑的来历见 [06 文档 §2.1 与 §9](06-tc限速方案.md)。

整机限速（`limit_scope: host`）下第 2 步改的是固定的那一个类，与端口无关：

```text
   tc class change dev <网卡> parent 1: classid 1:2 htb \
     rate <Mbps×1e6>bit ceil <同左>bit burst <约10ms额度> cburst <同左>
```

只做第 1 步不做第 2 步 → rl-limiter 打**持续超限告警**（控制台卡片上
高亮"超限"徽标），提醒补做第 2 步。

### 3.3 改限额为什么不需要 reload

限速在内核 tc 上，改限额是 `tc class change`——队列的令牌速率就地改掉，
**存量连接立刻跟上，连接不断**。需要 reload 的只剩监听端口与后端服务器
的变更（那是 HAProxy 的固有约束）。

对比之前的 bwlim 方案：那时 limit 是配置常量、运行期改不了，改限额必须
reload，而且存量连接要等 `hard-stop-after` 宽限期结束被断开重连才会用上
新限额。详见 [06-tc限速方案.md](06-tc限速方案.md) §4.1。

## 4. 本地监控演示（无需真实 HAProxy / MySQL）

仓库自带联调工具 `tools/fake_haproxy.py`（假 stats socket，`show stat`
计数器按指定速率增长；`--unix-path` 模拟同机形态、`--port` 模拟跨机
TCP 形态）。

**终端 1：本机假 HAProxy（unix socket，同机形态）**

```bash
mkdir -p /tmp/rl
python3 tools/fake_haproxy.py --unix-path /tmp/rl/hap1.sock \
    --frontends fe_main:2000000
```

> unix socket 路径受内核 `sun_path` 限制（Linux 107 字节），别放在很深
> 的目录里——超长路径会在启动校验时被直接拒绝。

**终端 2：监控服务（同机模式 + standalone YAML）**

```bash
cp deploy/config/limiter.example.yaml /tmp/limiter.yaml
# 编辑 /tmp/limiter.yaml：把 haproxy.socket_path 改成 /tmp/rl/hap1.sock，
# 并把 frontends 精简成只留 fe_main（与假 HAProxy 提供的 frontend 对应）
RL_CONSOLE_PORT=8090 rl-limiter -c /tmp/limiter.yaml
```

可观察到的行为：

- 启动即打 `服务配置加载完成 ... instance=haproxy endpoint=/tmp/rl/hap1.sock
  ... frontends=1 detail=fe_main@:8080,...`；
- 随后 `rl-limiter 服务已启动 ... apply=off`（本地演示未启用下发）；每分钟
  一条 `运行状态周期汇总 ... summary=fe_main:mean10_bytes_per_s=...`；
- 打开 http://127.0.0.1:8090 ：每个 frontend 一张卡片（曲线 + 配置表单），
  顶部横幅提示"配置自动下发未启用"（本地演示没有真 HAProxy 可下发）；
- 把 YAML 里 `fe_main` 的 `quota_mbps` 改到低于 fake 速率（如
  `10`，低于 2 MB/s = 16 Mbps 的模拟流量）后重启：10 秒后出现
  `frontend 带宽持续高于限额 ...` 告警；改回后解除；
- 停掉 fake_haproxy：出现 `采样失败 ...（fail-static）`，连续 10 秒后
  进入 degraded、超限判定暂停；拉起后自动恢复。

想连同 MySQL / Web 控制台 / 真实 HAProxy（Ubuntu 24.04）+ 真实限速一起
演示，直接用 `make demo-up`（docker compose，见 docs/04）。

## 5. HAProxy 侧接线（每台机器）

启用配置下发后，**监听端口、限速、后端服务器都不需要手写**——它们由
rl-limiter 渲染进 cfg 末尾的受管区块。手写的只剩 `global` / `defaults`
这个骨架（示例见
[deploy/haproxy/haproxy-example.cfg](../deploy/haproxy/haproxy-example.cfg)，
compose 演示用的是 `deploy/docker/haproxy-base.cfg`）。

- **版本 ≥ 2.8**（`option splice-*` 与监控用的 stats 列都以 2.8 为准；Ubuntu 24.04 自带 2.8.16）。
- `global` 段：
  - **本机 unix stats socket**（同机的 rl-limiter 只读采样用）：

    ```
    stats socket /run/haproxy/admin.sock mode 660 level user
    ```

    路径要与配置库 `haproxy_instances.socket_path` 一致。`mode 660` 让访问权
    由文件属主/属组控制——把 rl-limiter 的运行用户加进 `haproxy` 组即可，
    **不需要 root，也不占任何网络端口**。

    跨机集中监控形态改用内网 TCP（配置库填 `host`/`port`）：

    ```
    stats socket ipv4@<内网IP>:9999 level user
    ```

    此时 socket 暴露在网络上，只允许绑内网 IP（绝不可绑 `0.0.0.0`），
    安全组/防火墙仅放行监控服务器的 IP。同机形态没有这层暴露面，优先选它。
  - **`hard-stop-after 60s`**：reload 后旧 worker 的强停宽限期，是
    "限额调整对存量长连接生效"的手段（见 §3）。
- `defaults`（或各受控 `listen`）段开启 **`option contstats`**（连续
  统计）。HAProxy 默认在会话结束时才把字节计入 frontend 统计，TCP 长
  连接会让 `bytes_out` 长期不动、断连时一次性跳变——逐秒差分测速会
  变成脉冲锯齿，与 iptraf-ng 等网卡级工具完全对不上。不开启此项，
  监控数据不可用。
- 经限速入口的流量应使用 keep-alive / 客户端侧关连接（服务端先 FIN
  会与整形数据竞争导致响应截断）。

### 5.1 高并发 / 高带宽调优（32 核 TCP 代理基线）

可直接抄的骨架见
[deploy/docker/haproxy-base.cfg](../deploy/docker/haproxy-base.cfg)。每项的
**实测依据**统一放在 [06-tc限速方案.md](06-tc限速方案.md)，这里只列取值：

| 项 | 取值 | 一句话理由 |
| --- | --- | --- |
| `maxconn` | `1000000` | **默认值不该成为限制**：默认给到 100 万连接，真要限并发用 frontend 级 maxconn。**改它必须同步改 FD 上限**，见下 |
| `maxpipes` | `1000000`（= maxconn） | splice 的内核管道池，默认只给 maxconn/4；不够时吞吐直接掉。同时在传的连接远少于 maxconn 时可以调小，省一半 FD |
| `nbthread` | **不写** | 2.8 起自动等于可用 CPU 数；写死会在换机器/限核后失配 |
| `tune.listener.default-shards` | `by-thread` | 每线程一个 SO_REUSEPORT 监听套接字，改善 accept 扩展性 |
| `tune.bufsize` | **不写** | splice 全程可用时无收益，却让每连接内存涨 3 倍 |
| `tune.rcvbuf.*` / `tune.sndbuf.*` | **不写** | 写死会关掉内核自动调优，实测是负优化 |
| `cpu-map` | 默认注释掉 | 裸金属独占可开；容器里会把线程钉到 cpuset 之外的核 |

**唯一会让服务起不来的一项是 FD 上限**：

```
FD 需求 = maxconn × 2 + maxpipes × 2 + 34 = 4000034
[ALERT] Cannot raise FD limit to 4000034, limit is 4096.   ← 给不够就是它
```

要放开的是 **haproxy 自己的** unit（不是 rl-limiter 的）：
`systemctl edit haproxy` 里写 `LimitNOFILE=4194304`；容器里用 compose 的
`ulimits.nofile`。

**还有一道容器里改不动的天花板**：`fs.nr_open` 默认 1048576，压不住 400 万。
不先在宿主机把它抬上去，`LimitNOFILE` 根本设不上去（容器则是压根起不来）。
`deploy/sysctl/tune-kernel.sh` 里已经带上这一项，见 [08-内核参数调优.md](08-内核参数调优.md)。

> 别用 `no strict-limits` 绕开：实测它**不会把 maxconn 降下来**，只是把
> 启动期的明确失败换成运行期莫名其妙的 accept 失败。

资源预算：实测约 20 KB/连接，`maxconn 1000000` 满载约 20 GB（按需分配，
满载才用得到）。机器扛不住就把 `maxconn` 往下调——**有意识地设限，好过
被一个默认值悄悄卡住**。

**HAProxy 这边配好了还不够，内核默认值会在下面把它削掉。** 最典型的一条：
上面骨架里写的 `backlog 65536` 被 `net.core.somaxconn`（发行版默认 4096）
静默封顶，实测 `ss -lnt` 的 Send-Q 只有 4096——配置写着 65536，溢出的 SYN
被内核直接丢弃，客户端看到偶发连接超时而 HAProxy 日志里干干净净。容器部署
还有 `nf_conntrack_max` 默认 262144 撑不住 10 万连接的问题。

节点初始化阶段（启动 HAProxy 之前）会自动跑
[deploy/sysctl/tune-kernel.sh](../deploy/sysctl/tune-kernel.sh) 把这些抬到位，
并对 FD 上限做预检。**裸机 systemd 部署没有这个初始化阶段**，需要手工落一份：

```bash
deploy/sysctl/tune-kernel.sh dump | sudo tee /etc/sysctl.d/99-rl-limiter.conf
sudo sysctl --system
deploy/sysctl/tune-kernel.sh check     # 体检，有未达标项时退出码 1
```

取值、依据与"怎么验证真的生效了"见 [08-内核参数调优.md](08-内核参数调优.md)。

> **压测时的一个坑**：若读到"正好 2 倍限额"，先查有没有上一个 haproxy
> 进程没退干净——SO_REUSEPORT 会让两个进程共享同一个端口、各自按限额整形，
> 看起来就像限速失效了一倍。本项目已经被这个假象骗过两次。验证时按 PID
> 确认旧进程真的退了，别只看端口。

## 6. 容错行为表（设计 §3.7）

| 故障 | 行为 |
| --- | --- |
| 本机 HAProxy 停止 / stats socket 消失 | 采样失败当秒沿用上一秒速率；连续 10 秒失败进入 degraded（周期汇总与控制台节点面板可见），带宽视图冻结、超限判定暂停；socket 回来后自动解除 |
| 整台节点宕机 | 该节点的限速与监控一起消失（本就没有流量经过它）；**其它节点完全不受影响**——同机形态下不存在"监控服务器挂了所有节点都瞎"的单点 |
| MySQL 配置库断联 / 宕机 | 各节点独立按最后一次加载的配置继续监控（fail-static）；启动阶段等库就绪最长 120s（凭据/依赖类永久错误立即失败）；单次拉取带整体超时，静默网络分区不会卡死轮询 |
| 配置写错（端口冲突、frontend 没有后端、名字非法…） | 整份快照被拒绝，保留当前配置继续运行并打日志（fail-static）；控制台写接口当场返回中文错误，坏配置进不了数据面 |
| `RL_NODE_NAME` 拼错 | 启动即失败并列出已登记的节点名（容忍它会让服务"看起来在跑"却什么都采不到） |
| rl-limiter 自身崩溃 | systemd `Restart=always` 2 秒拉起；离线期间**限速照常**（同机 HAProxy 进程内执行），只是本机监控/告警暂停 |
| HAProxy reload（发版/改限额） | 新 worker 按新配置限速；采集侧识别计数器回绕（沿用上一秒速率并重建基线），监控曲线无毛刺 |

## 7. 尚未包含（后续里程碑）

- **管理后台**：配额审批/审计、对账报表、发布自动化（自动生成 cfg +
  reload）、告警通知（M4）。配置权威是 MySQL 配置库，后台建设时应
  直接读写配置库。
- **跨机汇总视图**：每个控制台只看本机，多台合计需要逐台查看，或等 M4
  的集中后台汇总。
- **TLS / 证书管理**：受管区块目前不表达 `bind ... ssl crt`，需要 TLS 的
  frontend 请手写在标记之外。
- **指标外呈**：无 Prometheus 端点/Grafana 大盘（观测走内置 Web 控制台
  与结构化日志）；用量按天聚合入库未做。
- 其他：监控服务自身高可用（当前单实例 + systemd 拉起；宕机不影响限速）。
