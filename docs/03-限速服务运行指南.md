# 限速服务（rl-limiter）运行指南

> 对应设计：[01-方案设计.md](01-方案设计.md)。本文覆盖 v3.0：配置源由本地 YAML 改为 **MySQL 数据库**，并用 **docker compose** 一键部署；同时保留 v2.0 的本地 YAML 模式作为可选路径。

**架构一句话**：一个独立部署的 rl-limiter 服务通过内网 TCP 连接多台 HAProxy 的 stats socket，每秒采样各节点 frontend 的 `bytes_out`，把同一环境横跨多台节点的流量全局聚合后做 AIMD 决策，再按各挂载点近期用量加权把整形值写回各节点的 bwlim map。v3.0 起，受控节点、环境配额、运行模式全部从 MySQL 读取（改库即秒级热重载），用量与心跳写回 MySQL。

单位约定：凡是给人读写的带宽——配置字段 `quota_mbps`、日志里的 `*_mbps` 字段、fake_haproxy 的 `--frontends` 速率——一律用 **Mbps**（如 200 表示 200 Mbps，允许小数）；服务内部计算统一用 **bytes/s**，换算集中在 `rl_limiter/model.py` 的 `to_mbps` / `mbps_to_bytes_per_sec`。

## 1. docker compose 快速启动（推荐）

一条命令拉起 **MySQL + 两台假 HAProxy + 限速服务**，无需任何本地配置文件：

```bash
docker compose up --build
```

首次启动时 MySQL 会自动执行 [`deploy/mysql/schema.sql`](../deploy/mysql/schema.sql) 建表并写入种子（两台节点 hap-1/hap-2、env-a 200Mbps 横跨两节点、env-b 50Mbps、`mode=dry-run`）。

**预期日志**（`rl-limiter` 服务）：

- 启动即打 `配置源为 MySQL（v3.0）：受控节点/环境配额/运行模式均来自数据库 ...`；
- 等库就绪后 `MySQL 连接就绪 host=mysql port=3306 db=rl_limiter attempt=...`；
- 随后 `rl-limiter 服务已启动（MySQL 配置源），快环与数据库后台开始运行 node_id=rl-limiter-01 mode=dry-run nodes=2 envs=2 ...`；
- 每分钟一条 `运行状态周期汇总（每 60 拍输出一次） ... mode=dry-run envs=2 ...`（DRY-RUN 只观测不下发）。

**改配置（秒级热生效）**——直接改库，rl-limiter 每 5s 轮询配置版本（= envs/env_targets/settings 三表 `updated_at` 最大值）自动重载：

```bash
# 改环境配额（约 5 秒内 rl-limiter 打出“检测到数据库配置版本变化，已拉取新配置下发核心循环 ...”）
docker compose exec mysql mysql -url -prlpass rl_limiter \
  -e "UPDATE envs SET quota_mbps=100 WHERE env_id='env-a'"
```

**切到 enforce（真实下发限速）**：

```bash
docker compose exec mysql mysql -url -prlpass rl_limiter \
  -e "UPDATE settings SET v='enforce' WHERE k='mode'"
# 之后 hap-1/hap-2 容器日志会打 “收到 map 更新，本节点限速值已改写（enforce 下发的观察窗口） ...”
```

**查看用量**（每秒样本落 `usage_samples` 表）：

```bash
docker compose exec mysql mysql -url -prlpass rl_limiter \
  -e "SELECT * FROM usage_samples ORDER BY id DESC LIMIT 10"
# 查看各实例心跳：
docker compose exec mysql mysql -url -prlpass rl_limiter -e "SELECT * FROM heartbeats"
```

**停止 / 清库重来**：

```bash
docker compose down       # 停服务，保留数据卷（配置/用量仍在）
docker compose down -v     # 连数据卷一起删，下次 up 重新执行 schema.sql 回到初始种子
```

## 2. 环境变量参考（MySQL 模式）

rl-limiter 检测到 `RL_MYSQL_HOST` 即进入 MySQL 配置源模式（compose 默认路径），忽略 `-c` YAML 参数。引导信息全部来自环境变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RL_MYSQL_HOST` | 无（设置即启用 MySQL 模式） | MySQL 主机名/IP；compose 里为服务名 `mysql` |
| `RL_MYSQL_PORT` | `3306` | MySQL 端口 |
| `RL_MYSQL_USER` | `rl` | 数据库用户 |
| `RL_MYSQL_PASSWORD` | 空 | 数据库密码 |
| `RL_MYSQL_DB` | `rl_limiter` | 数据库名 |
| `RL_MYSQL_CONNECT_TIMEOUT_S` | `5` | 单次连接超时（秒） |
| `RL_MYSQL_POLL_INTERVAL_S` | `5` | 配置版本轮询间隔（秒），决定改库热重载的时延 |
| `RL_NODE_ID` | `rl-limiter-01` | 本实例标识（心跳/用量样本携带） |
| `RL_TICK_INTERVAL_S` | `1.0` | 快环节拍（秒） |
| `RL_LOG_LEVEL` | `info` | debug / info / warning / error |

## 3. 数据库表参考

初始化脚本见 [`deploy/mysql/schema.sql`](../deploy/mysql/schema.sql)（全部 InnoDB / utf8mb4）。

| 表 | 用途 | 是否参与配置版本 |
| --- | --- | --- |
| `settings` | 全局运行开关，rl-limiter 只读 `k='mode'` 行（dry-run / enforce） | 是 |
| `haproxy_nodes` | 受控 HAProxy 节点接线（name/host/port/bwlim_map_path/timeout_ms） | 否（改后需重启服务） |
| `envs` | 环境配额（`quota_mbps` Mbps，可选 `params_json` 参数覆盖） | 是 |
| `env_targets` | 环境 ↔ (节点,frontend) 挂载点映射，外键级联删除 | 是 |
| `usage_samples` | 每秒用量样本（Mbps 口径），每 5s 批量写入，供后台展示/对账 | — |
| `heartbeats` | 各实例心跳（模式/配置版本），按 `node_id` upsert | — |

**配置版本 = `envs`/`env_targets`/`settings` 三张配置表 `updated_at` 的最大值（秒）**。任一行新增或修改即推高该值，rl-limiter 轮询到变化便全量重载——这就是“改库热生效”的机制。

## 4. 本地非 docker（YAML 模式，可选）

> 本章为可选路径：不使用 docker、以本地 YAML 作配置源的传统方式（v2.0）。docker compose 用户可跳过。

### 4.1 安装

要求 Python ≥ 3.11。依赖仅 PyYAML 与 aiohttp（其余全部为标准库）。

```bash
pip install -e ".[test]"    # 或 make install
make test                   # 全部单元测试
rl-limiter --version        # 验证入口可用
```

### 4.2 本地 dry-run 演示（三步，无需真实 HAProxy）

仓库自带两个联调工具：

- `tools/fake_haproxy.py`：假 HAProxy stats socket（TCP）。`show stat` 的计数器按指定速率真实增长（带抖动），`set map` 只记录并打日志——它就是一台"受控节点"。
- `tools/mock_backend.py`：管理后台桩。JSON 文件作配置源，版本号 = 文件 mtime（秒），改文件/`touch` 即触发长轮询下发；metrics / heartbeat 只打摘要日志。

**第一步：起两台假 HAProxy（终端 1、2）**

```bash
python3 tools/fake_haproxy.py --port 19991 --frontends fe_env_a:16,fe_env_b:4
python3 tools/fake_haproxy.py --port 19992 --frontends fe_env_a:12
```

即模拟：env-a 横跨两台节点（合计约 3.5 MB/s），env-b 只在第一台上（约 0.5 MB/s）。

**第二步：起管理后台桩（终端 3）**

```bash
python3 tools/mock_backend.py --addr 127.0.0.1:9090 --config deploy/config/mock-backend-config.json
```

**第三步：起限速服务（终端 4）**

```bash
cp deploy/config/limiter.example.yaml /tmp/limiter.yaml
# 编辑 /tmp/limiter.yaml，改四处以指向本地演示环境：
#   haproxy_nodes[0]: host: 127.0.0.1, port: 19991   （名字保持 hap-1）
#   haproxy_nodes[1]: host: 127.0.0.1, port: 19992   （名字保持 hap-2）
#   backend.base_url: http://127.0.0.1:9090
#   backend.cache_path: /tmp/rl-limiter-cache.json
rl-limiter -c /tmp/limiter.yaml
```

可观察到的行为：

- rl-limiter 侧：启动即打 `服务配置加载完成，以下为完整配置摘要（排障第一条要看的日志） ...`，随后 `已用本地静态环境配额完成引导 ...`（有缓存时为 `已用本地缓存的后台配置完成引导（fail-static，重启前后限速行为连续） ...`），拿到后台配置后打 `配置已应用到快环（映射/配额/模式已更新） version=<mtime> mode=dry-run envs=2 ...`；每分钟一条 `运行状态周期汇总（每 60 拍输出一次） tick=60 config_version=... mode=dry-run envs=2 degraded_nodes=- envs_summary=env-a:mean10=...Mbps,conn=...;env-b:...`。
- mock_backend 侧：`已向限速服务下发配置（长轮询返回 200） ... waited_ms=...`、每 10s `收到限速服务心跳（可据此核对配置是否推送到位）`、每 5s `收到用量样本批次（桩仅记录条数后丢弃） ... samples=5`。
- 修改（或 `touch`）`mock-backend-config.json`，1 秒内新版本下发，rl-limiter 打出新的 `配置已应用到快环`。
- dry-run 模式下执行器只记录本应写入的整形值；把 JSON 里 `mode` 改为 `enforce` 后，fake_haproxy 侧会开始打 `收到 map 更新，本节点限速值已改写（enforce 下发的观察窗口） map=/etc/haproxy/maps/bwlim.map key=fe_env_a old=... new=...`——这就是限速值真实下发的窗口。
- 停掉其中一台 fake_haproxy：该节点采样连续失败后进入 degraded，`运行状态周期汇总` 的 `degraded_nodes` 字段列出节点名；限速值冻结不动（fail-static），拉起后自动恢复。

## 5. 配置参考（YAML 模式，/etc/rl-limiter/config.yaml）

完整注释示例见 [deploy/config/limiter.example.yaml](../deploy/config/limiter.example.yaml)。

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `node_id` | 必填 | 本服务实例标识（心跳/上报携带） |
| `mode` | `dry-run` | `dry-run` 只打日志；`enforce` 真实写各节点 bwlim map；非法值归一为 dry-run |
| `log_level` | `info` | debug / info / warning / error |
| `tick_interval_s` | `1.0` | 快环节拍（秒），设计基准为 1 秒 |
| `haproxy_nodes[].name` | 必填 | 节点名，`envs[].targets[].node` 引用它 |
| `haproxy_nodes[].host` / `port` | 必填 | 该节点内网 TCP stats socket 地址（`level admin`） |
| `haproxy_nodes[].bwlim_map_path` | `/etc/haproxy/maps/bwlim.map` | 与该节点 haproxy 配置中 `map_str_int(...)` 路径一致 |
| `haproxy_nodes[].timeout_s` | `0.5` | 单次 runtime API 命令超时（秒） |
| `envs[].env_id` | 必填 | 环境 ID |
| `envs[].quota_mbps` | 必填 | 约定带宽，**Mbps**（允许小数） |
| `envs[].targets[]` | 必填 | 挂载点清单：`{node, frontend}` 二元组，可横跨多台节点 |
| `envs[].params` | 缺省用默认 | 快环参数覆盖（§3.3：1.10 / 0.90 / 3s / 5s / ×0.9 / 0.95 / +5%） |
| `backend.base_url` | 空 | 空 = standalone 只用本地 `envs`；非空 = 长轮询 + 上报 + 心跳 |
| `backend.cache_path` | `/var/lib/rl-limiter/config-cache.json` | fail-static 缓存（systemd `StateDirectory=rl-limiter` 自动建目录） |

配置优先级（引导时）：后台缓存（fail-static） > 本地 `envs` > 不限速等待后台首发。

## 6. HAProxy 侧前置条件（每台受控节点）

- **版本 ≥ 2.8**（`bwlim` 过滤器 2.8 起正式；无法升级的节点只能退化为 tc 单层硬限）。
- `global` 段开启**内网 TCP** stats socket（v2.0 与 v1 的关键差异——不再是本机 unix socket）：

  ```
  stats socket ipv4@<内网IP>:9999 level admin
  ```

  **安全须知**：admin 级端口等同于 HAProxy 的完全控制权。只允许绑内网 IP，绝不可绑 0.0.0.0；安全组/防火墙仅放行限速服务器的 IP。可同时保留一行本机 unix socket 用于应急运维（见示例 cfg 注释）。
- map 文件 `/etc/haproxy/maps/bwlim.map` 必须在 HAProxy 启动前存在（解析期加载），每行 `<frontend名> <bytes/s>`（HAProxy map 存整数 bytes/s，rl-limiter 写入时由 Mbps 换算）；运行期条目归 rl-limiter 所有，经 runtime API `set map` 更新，改限速不需要 reload。
- frontend 侧 bwlim 接线（含逐行说明、按流动态限速与共享 stick-table 两种方案的取舍）见 [deploy/haproxy/bwlim-example.cfg](../deploy/haproxy/bwlim-example.cfg)。
- 内核层兜底部署在**各 HAProxy 机器本机**：[deploy/tc/backstop.sh](../deploy/tc/backstop.sh)，速率取节点配额的 115%（§3.2 L3），如 200 Mbps 配额 → `./backstop.sh eth0 230`。它与 rl-limiter 服务无关，rl-limiter 也因此不需要 CAP_NET_ADMIN。

## 7. 容错行为表（设计 §3.7）

| 故障 | 行为 |
| --- | --- |
| 某台 HAProxy 节点失联 | 该节点采样失败当秒沿用上一秒速率；连续失败进入 degraded（`运行状态周期汇总` 的 `degraded_nodes` 可见），相关环境限速冻结不动；节点上残留的 map 值保持最后一次写入（安全方向），且该机的 tc 兜底仍在内核生效；恢复采样后自动解除 |
| 管理后台断联 / 宕机 | 长轮询退避重试；按最后一次下发配置继续限速（fail-static），重启时从 `backend.cache_path` 复原，绝不放开为不限速 |
| rl-limiter 自身宕机 | systemd `Restart=always` 2 秒拉起；离线期间各台 HAProxy 保持最后写入的 map 限速值不变 + 各机 tc 兜底仍然生效，限速不会放开 |
| 上报失败 | 样本本地缓冲，恢复后补发，超限丢最旧 |
| dry-run → enforce 切换 | 配置先于 tick 生效（下一拍即按新模式执行），切换后把当前限速值真实写入各节点 map |

## 8. 骨架刻意未包含（后续里程碑）

- **真实管理后台**：配额管理、审批审计、对账、告警都不在；mock_backend 只回放一个静态 JSON。
- **tc 自动化**：backstop.sh 需在各 HAProxy 机器上手工执行，rl-limiter 不校验/不维护 tc 规则。
- **用量数据落库**：metrics 上报后即弃，无时序库、无 Prometheus 指标端点、无大盘。
- 其他：HAProxy reload 检测与限速值重放（§3.7）、mTLS 证书签发流程（配置项已留好）、限速服务自身的高可用（当前单实例 + systemd 拉起）。
