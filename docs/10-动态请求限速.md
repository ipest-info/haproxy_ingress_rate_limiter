# 动态请求限速：带宽驱动的 AIMD 控制环

本分支在 tc 带宽限速之上加一个**请求侧的动态闸**：持续对比各 frontend
的 10 秒均值带宽与登记限额（quotas），带宽顶上限额时经 HAProxy runtime
API 收缩该 frontend 的**并发接纳上限**（`set maxconn frontend`），回落
后再逐步放开——新请求在 HAProxy 门口被排队/拒绝，而不是放进来再被 tc
慢慢掐。

## 1. 控制策略（AIMD）

| 条件 | 动作 |
| --- | --- |
| mean10 > 限额 × `high_ratio`（默认 1.0） | **乘性收缩**：接纳上限 × `decrease`（默认 0.7），下限 `min_conns` |
| mean10 < 限额 × `low_ratio`（默认 0.85） | **加性恢复**：每轮 +基准/20，直到回到基准 |
| 两者之间（滞回带） | 不动作——没有滞回会在限额线附近来回抖 |

恢复基准 = frontend 自己配置的 maxconn（`show stat` 的 slim 列）；cfg
没给 frontend 级 maxconn 时用 `max_conns`（默认 100000）兜底。调节节拍
`adjust_interval_s` 默认 3 秒。

## 2. 配置与前提

```yaml
quotas:
  fe_main: 40                  # 带宽限额照旧（tc 执行）
dynamic_request_limit:
  enabled: true                # 默认关闭，显式打开
  min_conns: 50                # 收缩下限（绝不把入口饿死）
  # max_conns: 100000          # frontend 无自带 maxconn 时的恢复基准
  # high_ratio: 1.0
  # low_ratio: 0.85
  # decrease: 0.7
  # adjust_interval_s: 3
```

**stats socket 需要 level admin**——已对真实 HAProxy 2.8 实测：
`set maxconn frontend` 在 level user 与 level operator 下都被
Permission denied，只有 admin 级能执行（成功回包为空，`show stat` 的
slim 列实时反映新值）：

```
stats socket /run/haproxy/admin.sock mode 660 level admin
```

admin 级 socket 的暴露面大：**务必用本机 unix socket + mode 660 属组
授权**，绝不要把 admin 级开在 TCP 上（那等于把 HAProxy 管理权交给能
连上端口的任何人）。权限不足时服务会告警一次并只观测不动作。这些控制
参数启动时定型，改了要重启（watch 检测到变化会提示）。

## 3. 口径与边界（诚实说明）

- **调的是并发接纳上限，不是每秒请求数**。HAProxy runtime API 没有
  per-frontend 的 req/s 旋钮，reload-free 可调的请求侧闸只有 maxconn
  ——压并发即压请求接纳速率，长连接场景下两者不完全等价。要精确的
  req/s 限速用 haproxy.cfg 里的 stick-table/`http_req_rate`（静态配置，
  与本模块互补、可叠加）；
- **这是主分支"只读 HAProxy"承诺的刻意例外**：本模块写且只写这一个
  旋钮（不碰权重、不上下线服务器）。maxconn 是运行期值，HAProxy
  reload 即回到 cfg 配置值；本服务启动时也会先把受管 frontend 恢复到
  基准再开始调（不继承上个进程留下的压缩值）；
- **失效安全**：采样失联（degraded）不动作；限额取消一次性恢复基准；
  命令失败不推进内部状态（恢复后从基准重新收敛）。

## 4. 与 tc 带宽限速的关系

两层互补，不替代：tc 是硬闸（字节速率的最终保证，服务宕机也仍生效）；
本模块是软闸（把压力挡在接纳阶段，减少已接入连接在 tc 队列里的排队与
丢包）。只开 tc 不开本模块 = 主分支行为；只开本模块不开 tc（设
`RL_TC_IFACE=-`）= 纯靠接纳控制，带宽没有硬保证——不建议生产这么用。
