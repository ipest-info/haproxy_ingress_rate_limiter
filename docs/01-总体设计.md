# 01 总体设计

rl-limiter 是带宽按量计费场景下的**服务器出口限速与监控服务**（通用
形态）：一台服务器一个实例，**不依赖机器上跑的任何服务**——nginx、
HAProxy、自研 TCP 服务，或者什么都不跑，一概适用。它把本机出向带宽
压在登记的目标内，同时提供实时监控、历史落盘与一个内置 Web 控制台。

核心形态是**双网卡 + 闭环动态限速**：

1. `instance_quota_mbps` 是**出向带宽目标**（网卡口径，与按量计费同
   口径），但不直接整形出向；
2. 出向超过目标时，**动态收紧客户端侧网卡（默认 eth0）的入向带宽**把
   出向间接压回目标：请求进得慢 → 响应自然出得少；
3. 调整过程刻意**平缓**——宁可收敛慢，也不要振荡。

原理与算法见 [02 闭环限速原理](02-闭环限速原理.md)。

## 1. 设计原则

- **一切观测来自内核，与服务无关。** 带宽/包/丢包读网卡计数器
  （/proc/net/dev，双网卡设备视图）；连接统计读内核 TCP 计数器
  （/proc/net/snmp：CurrEstab、PassiveOpens 差分）。机器上跑什么、
  跑几个服务、服务死活，监控与限速一概不感知、不受影响；
- **限速与计费同口径（网卡字节）。** 闭环的观测值就是客户端侧网卡的
  流出字节——压的就是账单上的那个数；
- **限额住在 rl-limiter 自己的 YAML 里，没有数据库。** 配置来源只有
  一个本地文件（`-c` 指定），运行期轮询（5s）热生效；写 API 的修改回
  写 YAML（整份校验 + 原子替换），"页面改的"与"手工编辑的"殊途同归；
- **fail-static。** 配置文件短暂读不到/非法时按最后一次合法配置继续
  跑；采样失联时冻结基于观测的动作，陈旧数据不配驱动决策；
- **宁可起不来，也不要"以为在限速"。** 一切会让限速静默失效的条件都
  在启动时大声失败：procfs 读不到 → 启动失败；ifb 模式下建不出 IFB
  设备 → 启动失败并写明处置；闭环被显式关闭但登记了限速值 → 启动
  告警"不会被执行"；
- **限速在内核 tc，不在应用层。** 改限额走 `tc class change`，存量
  连接立刻跟上；rl-limiter 进程挂掉也不影响已下发的限速；
- **单位约定。** 配置与页面一律 Mbps；API 的速率字段一律 bytes/s；
  tc 命令行内部是 bit/s。换算只在边界处做一次。

## 2. 组件与数据流

```
                 ┌────────────────────── 本机（任意服务的服务器） ─────────────────────┐
 客户端 ──eth0──▶ 业务进程（nginx / 自研服务 / …，rl-limiter 不感知）──eth1──▶ 后端/内网
                 │
                 │  /proc/net/dev（双网卡设备计数器）   /proc/net/snmp（TCP 计数器）
                 │        │                                   │
                 │        ▼                                   ▼
                 │   netdev 采样 ◀──────── collector ───────▶ netsrc 采样
                 │                             │ 每秒一拍
                 │                             ▼
                 │                      loop（监控主循环）
                 │                │               │
                 │                ├─▶ StatusHub ─▶ Web 控制台 / SSE / /metrics
                 │                ├─▶ metricslog（分钟粒度 JSONL 落盘）
                 │                └─▶ IngressGovernor（闭环控制器）
                 │                               │ 动态入向总闸
                 │   cfgparse.watch（5s 轮询 YAML）──▶ tc 执行面（tcifb：IFB+HTB 入向）
                 └──────────────────────────────────────────────────────────────────────┘
```

模块职责（`rl_limiter/`）：

| 模块 | 职责 |
| ---- | ---- |
| `model.py` | 共享领域类型与单位约定 |
| `netsrc.py` | 内核 TCP 计数器采样（/proc/net/snmp，连接统计） |
| `netdev.py` | 网卡解析与 /proc/net/dev 设备计数器（带宽/包/丢包） |
| `collector.py` | 每秒采样与差分：设备视图 + 整机连接视图；降级语义 |
| `window.py` | 滑动窗口（10s 均值）与 EWMA |
| `loop.py` | 监控主循环：采集 → 发布 |
| `cfgparse.py` | 端口登记派生受管清单 + YAML 轮询热更 |
| `config.py` | YAML 解析与校验（启动与回写共用同一条校验链） |
| `configstore.py` | 写 API 的 YAML 回写（唯一写配置的地方） |
| `ingressgov.py` | **闭环控制器**：按网卡口径出向带宽平缓调节入向总闸 |
| `tcifb.py` | 入向执行面：IFB+HTB 平稳整形（默认） |
| `tcingress.py` | 入向执行面：police 直接丢包（老内核备选）+ SYN 速率闸 |
| `tcshaper.py` | 出向执行面：HTB（可选，默认关闭） |
| `webconsole.py` | 控制台：StatusHub、HTTP API、SSE、Prometheus、写 API |
| `metricslog.py` | 分钟粒度 JSONL 落盘（按天轮转，默认保留 90 天） |
| `fleet*.py` | rl-fleet 总控：多机汇总与总带宽按需分配（[10](10-总控制台.md)） |

`tools/`：`loadgen.py`（多进程可调并发压测）、`random_web.py`（随机
大小响应的模拟服务，demo 的"任意业务进程"示例）、`tc_check.py`
（限速体检：doctor/plan/verify）。

## 3. 配置（一份 YAML + 环境变量）

| 来源 | 内容 | 生效方式 |
| ---- | ---- | ---- |
| `/etc/rl-limiter/config.yaml` | instance_quota_mbps、ports、request_limits、dynamic_ingress、name、运行参数 | 限额/端口/闭环参数热生效（5s 轮询）；name/log_level/tick_interval_s 重启生效。见 [03 配置参考](03-配置参考.md) |
| `rl-limiter.env`（环境变量） | 网卡接线（RL_TC_IN_IFACE/RL_TC_IFACE/RL_NIC）、控制台（RL_CONSOLE_*）、令牌、落盘 | 启动时定型 |

## 4. 多机形态：总控制台（rl-fleet）

多台服务器要做**总量控制**时，部署一个 rl-fleet 总控（同包里的第二个
进程）：轮询各节点控制台 API 汇总流量（网卡口径），把
total_egress_mbps 按需动态分配为各节点的 instance_quota_mbps——节点
闭环再转成入向限速。节点侧零改动；总控是慢速外环、节点闭环是快速
内环。详见 [10 总控制台](10-总控制台.md)。

## 5. 与 HAProxy 形态分支的关系

本仓库另有以 HAProxy 为采样源的形态分支（按 frontend 监控、端口级
出向目标闭环）。本分支把观测面全部换成内核（设备 + TCP 计数器），
换来的是**对服务零依赖**；放弃的是按端口拆分的应用层监控与端口级
出向目标（网卡物理上无法按端口拆分出向字节）。要按服务精细监控请用
HAProxy 形态分支；要"什么服务都能限"用本分支。
