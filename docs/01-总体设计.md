# 01 总体设计

rl-limiter 是带宽按量计费场景下的**入口限速与监控服务**：一个 rl-limiter
实例管一台与它**同机**的 HAProxy，把每个监听端口（frontend/listen 段）的
带宽压在登记的限额内，同时提供实时监控、持续超限告警、历史落盘与一个
内置 Web 控制台。

本分支（双网卡请求方向限速）的核心形态是**闭环动态限速**：

1. 填写的限速值是对**出向带宽的判断基准**，但**不直接整形出向**；
2. 出向带宽超过基准时，通过**动态收紧入向（请求方向）带宽**来间接把
   出向压回目标；
3. 调整过程刻意**平缓**——宁可收敛慢，也不要振荡。

原理与算法见 [02 闭环限速原理](02-闭环限速原理.md)。

## 1. 设计原则

这些原则贯穿全部代码，排障与二次开发时先对齐它们：

- **haproxy.cfg 是负载均衡配置的唯一权威。** 监听端口、模式、后端服务器
  由运维直接写 cfg 并自行 reload；rl-limiter 只**读** cfg 解析出受管
  清单，绝不写它、绝不 reload HAProxy。控制台与写 API 同样不提供任何
  cfg 写入口。
- **限额住在 rl-limiter 自己的 YAML 里，没有数据库。** 配置来源只有两个
  本地文件：haproxy.cfg + YAML（`-c` 指定）。两者被运行期轮询（5s），
  内容变化即热生效；写 API 的修改回写 YAML（整份校验 + 原子替换），
  所以"页面改的"与"手工编辑的"殊途同归，重启后都还在。
- **fail-static。** 配置文件短暂读不到/非法时，按最后一次合法配置继续
  跑；采样失联（degraded）时冻结一切基于观测的动作（超限判定、闭环
  调节），陈旧数据不配驱动决策。
- **宁可起不来，也不要"以为在限速"。** 一切会让限速静默失效的条件都在
  启动时大声失败：配置了 request_limits 却没给入向网卡 → 启动失败；
  ifb 模式下建不出 IFB 设备（典型：Docker Desktop 精简内核）→ 启动
  失败并写明处置；实例总限速在本机没有执行者 → 页面置灰 + 写接口 409。
- **限速在内核 tc，不在 HAProxy。** 早期方案用过 HAProxy 的 shared
  bwlim，实测发现只要挂着 bwlim 滤镜，HAProxy 就会完全关闭内核 splice
  （零拷贝转发），同吞吐 CPU 多花一倍（0.59 → 0.33 CPU 秒/GB）。换成
  tc 后限速逻辑整体下沉内核：改限额走 `tc class change`，不 reload、
  存量连接立刻跟上；rl-limiter 进程挂掉也不影响已下发的限速。
- **单位约定。** 配置与页面一律 Mbps；API 的速率字段一律 bytes/s
  （应用层口径）；tc 命令行内部是 bit/s。换算只在边界处做一次。

## 2. 同机部署的理由

tc 只能在流量进出的那台机器上做，限速与被限的流量必须同机。附带收益：

- 采样走本机 unix stats socket，不占网络端口、无需对内网开放；
- 一台机器的故障不外溢，没有中心化的限速服务可炸；
- rl-limiter 短暂宕机不影响已生效的限速（tc 规则留在内核里）。

## 3. 组件与数据流

```
                    ┌────────────────────────── 本机 ──────────────────────────┐
 客户端 ──eth-front──▶ HAProxy（haproxy.cfg，运维直管）──eth-back──▶ 后端服务器
                    │      │ unix stats socket（只读采样，1s）
                    │      ▼
                    │  collector ──▶ loop（监控主循环：超限判定/告警）
                    │      │              │
                    │      │              ├─▶ StatusHub ─▶ Web 控制台 / SSE / /metrics
                    │      │              ├─▶ metricslog（分钟粒度 JSONL 落盘）
                    │      │              └─▶ IngressGovernor（闭环控制器）
                    │      ▼                        │ 动态入向上限
                    │  cfgparse.watch（5s 轮询      ▼
                    │  haproxy.cfg + YAML）──▶ tc 执行面（tcifb：IFB+HTB 入向；
                    │                            tcshaper：出向 HTB，可选）
                    └──────────────────────────────────────────────────────────┘
```

模块职责（`rl_limiter/`）：

| 模块 | 职责 |
| ---- | ---- |
| `model.py` | 共享领域类型与单位约定（FrontendConfig、RequestLimit、接线） |
| `haproxy.py` | HAProxy runtime API 客户端（unix/TCP stats socket，只读） |
| `collector.py` | 每秒采样：按 frontend 的用量 + 整机实例视图；降级语义 |
| `window.py` | 滑动窗口（10s 均值）与 EWMA |
| `loop.py` | 监控主循环：采集 → 持续超限判定（滞回告警）→ 发布 |
| `cfgparse.py` | 解析 haproxy.cfg 受管清单 + 双文件轮询热更 |
| `config.py` | YAML 解析与校验（启动与回写共用同一条校验链） |
| `configstore.py` | 写 API 的 YAML 回写（唯一写配置的地方） |
| `ingressgov.py` | **闭环控制器**：按出向带宽平缓调节入向上限（两级环） |
| `tcifb.py` | 入向执行面：IFB+HTB 平稳整形（本分支默认） |
| `tcingress.py` | 入向执行面：police 直接丢包（老内核备选）+ SYN 速率闸 |
| `tcshaper.py` | 出向执行面：HTB（单网卡形态可选，本分支默认关闭） |
| `netdev.py` | 网卡解析与 /proc/net/dev 包统计 |
| `webconsole.py` | 控制台：StatusHub、HTTP API、SSE、Prometheus、写 API |
| `metricslog.py` | 分钟粒度 JSONL 落盘（按天轮转，默认保留 90 天） |

`tools/`：`loadgen.py`（多进程可调并发压测）、`random_web.py`（随机大小
响应的模拟后端，多进程 SO_REUSEPORT）、`fake_haproxy.py`（联调假节点）、
`tc_check.py`（限速体检：doctor/plan/verify）。

`deploy/`：`bare/`（裸机一键装机 + systemd）、`docker/`（容器入口脚本与
模板配置）、`sysctl/tune-kernel.sh`（内核参数调优表）、`config/`（带全量
注释的 YAML 示例）。

## 4. 两份配置文件的分工

| 文件 | 内容 | 谁写 | 生效方式 |
| ---- | ---- | ---- | ---- |
| `/etc/haproxy/haproxy.cfg` | 监听端口、模式、后端、stats socket | 运维手工 | 运维自行 reload；rl-limiter 轮询到变化后更新受管清单 |
| `/etc/rl-limiter/config.yaml` | 接线（haproxy 段）、quotas、request_limits、instance_quota_mbps、dynamic_ingress | 运维手工 或 写 API 回写 | 限额类字段热生效；接线/闭环参数启动时定型（见 [03 配置参考](03-配置参考.md)） |

## 5. 分支形态一览

本仓库有三条形态分支，共享同一个基线（监控/控制台/出向 HTB）：

- **本分支**：双网卡 + 入向闭环（IFB+HTB 平稳整形 + 动态调节），
  出向默认不整形；
- `claude/yaml-cfg-source`（基线）：单网卡出向 HTB 直接限速；
- `claude/dynamic-request-limit`：按带宽利用率动态调节 HAProxy maxconn
  （AIMD，runtime API 执行，不动 tc）。
