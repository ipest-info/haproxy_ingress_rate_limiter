# 把 HAProxy 换成 LVS/IPVS：可行性研究

**本文只做研究，没有动任何代码。** 结论涉及一次不小的改造，先把该算的账
算清楚。

> **2026-07 更新：限速支持整机范围之后，本文最大的那个未知数没了。**
> 原文把"IPVS 反向 NAT 之后 tc 还能不能按源端口分类"列为整个方案的地基，
> 且标注为未实测。现在限速多了一个 `limit_scope: host` 的范围
> （[docs/06 §2.2](06-tc限速方案.md)），它**根本不做分类**——所有出向包
> 落进同一个 HTB 类。这个前提弱到只剩"转发出去的包会经过本机网卡的根
> qdisc"，而那对任何转发路径都成立。
>
> 也就是说：**整机限速 + IPVS-NAT，限速这一侧不再有可行性风险。**
> 受影响的段落已就地标注。DR/TUN 依然致命（那是"字节根本不经过这台机器"，
> 换什么限速范围都救不回来），计费口径那条也依然是本次改造里唯一直接
> 影响到钱的地方。

---

## 0. 结论先行

**只有 NAT 模式可行。DR 与 TUN 模式会让这个项目失去存在基础。**

而 NAT 模式恰恰是 LVS 优势最小的那个模式——LVS 之所以快，正是因为 DR 模式
下回程流量不经过它；而"回程流量不经过它"对本项目等于**功能完全不存在**。

具体建议按目标分三种情况，见 [§7](#7-建议)。一句话预告：**如果换 IPVS 是
为了解决上次那个"出向低于入向"，方向是错的**——那是 tc 的问题，和谁做转发
无关。

---

## 1. 先明确本项目到底依赖什么

这套系统做的两件事，都建立在同一个前提上：**下行流量必须经过这台机器**。

| 能力 | 怎么实现的 | 依赖 |
| --- | --- | --- |
| 限下行带宽（`limit_scope: frontend`）| tc HTB 挂在**本机网卡出向**，按源端口分类 | 下行包从本机网卡出去，**且源端口是监听端口** |
| 限下行带宽（`limit_scope: host`）| tc HTB 挂在**本机网卡出向**，不分类 | 下行包从本机网卡出去 |
| 每秒采各 frontend 下行字节 | HAProxy `show stat` 的 `bytes_out` | 下行字节流过本进程 |
| 计费（95 分位） | 上面那个采样落库 | 同上 |

任何让下行流量绕过本机的方案，这几项**同时**失效——注意两种限速范围的
依赖强弱不同：整机范围只要求"包从本机网卡出去"，按 frontend 范围还额外
要求"出去时源端口仍是监听端口"，而后者恰恰是换成 IPVS 之后唯一可能变的
东西。**换数据面时，限速范围选 `host` 能少担一份风险。**

---

## 2. 三种转发模式的判定

| 模式 | 回程流量走哪 | 能限速吗 | 能计费吗 | 判定 |
| --- | --- | --- | --- | --- |
| **NAT** | 经过 director（反向 NAT） | ✅ | ✅ | **唯一可行** |
| **DR**（直接路由） | RS 直接回客户端，**不经过 director** | ❌ | ❌ | 致命 |
| **TUN**（IP 隧道） | 同 DR | ❌ | ❌ | 致命 |

DR/TUN 下 director 只看得到请求方向的小包（几百字节的 HTTP GET），而本项目
要管的是响应方向的几百 MB。**不是"精度差一点"，是那台机器上根本没有这些
字节可以数、也没有这些包可以整形。**

这一条把选择空间直接压到只剩 NAT 模式。后面全部只讨论 NAT。

## 3. NAT 模式逐项对照

### 3.1 保得住的

| 能力 | 现在 | IPVS-NAT | 说明 |
| --- | --- | --- | --- |
| TCP L4 转发 | `mode tcp` | 纯内核转发 | 理论上更省 CPU，**未实测** |
| 下行限速 | tc HTB（整机 / 按源端口） | **tc 规则一个字都不用改** | 整机范围下这一条**无需论证**；按端口范围下要验，见下 |
| 下行字节采样 | `show stat` 的 `bytes_out` | `/proc/net/ip_vs` 的 `OutBytes` | 同样是"读计数器做差分" |
| 并发/活跃连接 | `scur` / 活跃空闲 | `ActiveConn` / `InActConn` | 语义接近 |
| 改配置立刻生效 | 渲染 cfg → `haproxy -c` → reload（实测 ~74 ms） | `ipvsadm` 即时，**且不断存量连接** | ✅ 比现在更好 |
| 改限额 | `tc class change` | 完全不变 | ✅ |

**为什么 tc 规则不用改**，分两种限速范围看，风险差得很远：

**`limit_scope: host`（整机范围）：不需要任何论证。** 它一条 filter 都不用
（受限流量就是 HTB 的 `default` 类），所以"源端口在反向 NAT 之后是什么"
根本不进入判断。剩下的唯一前提是"转发出去的包会经过本机网卡的根 qdisc"
——那是 Linux 发包路径的定义，对本机产生的包和转发的包一视同仁。
**换 IPVS 时选这个范围，限速这一侧就没有可行性风险了。**

**`limit_scope: frontend`（按端口范围）：才需要下面这段推论。**
IPVS-NAT 在回程方向把源地址端口改写回 VIP:服务端口。而 tc 的出向 qdisc
在数据路径上位于 **netfilter POSTROUTING 之后**（`POSTROUTING →
dev_queue_xmit → qdisc → 网卡`）。所以 tc 看到的包，源端口已经是服务端口
了——和现在 HAProxy 发出去的包一模一样，现有的 `match ip sport <监听端口>`
规则原样有效。

> ⚠️ 这一条是**按内核数据路径推出来的，本仓库没有实测**（开发沙箱没有
> `ip_vs`，连 classful qdisc 都没有）。**只在按 frontend 限速时它才是地基**
> ——那种情况下必须在真机上第一个验，见 [§6](#6-验证计划)。整机限速下这一步
> 可以跳过。
>
> 整机范围下唯一还用到源端口匹配的，是那两条把 SSH（22）挑进免限类的
> filter。它们万一没匹配上，后果是 **SSH 也被算进整机限额**——链路打满时
> 登录会变慢，而不是"限速静默失效"。量级完全不同，不构成方案风险，但真机
> 上顺手验一下（`tc -s filter show` 看那条规则的命中数）没有坏处。

顺带澄清一个**不是问题的问题**：有人会担心 director→RS 方向用临时端口会和
tc 的源端口分类冲突。不会——tc 匹配的是 director→**客户端**方向，那个源
端口是 VIP 端口。这和现在 HAProxy 连后端的情况完全一样，[docs/06 §6](06-tc限速方案.md)
已经处理过（`ip_local_port_range` 下界不下探）。

### 3.2 会失去的

| 能力 | 现在 | IPVS-NAT | 代价 |
| --- | --- | --- | --- |
| **后端健康检查** | HAProxy 内置（`check inter 2000`） | **完全没有** | 要么装 keepalived，要么自己实现 |
| `mode http` | 支持 | 不支持（纯 L4） | 配置模型要删掉这个字段 |
| 每 frontend `maxconn` | 支持 | 没有等价物 | 只剩全局手段 |
| 每 frontend 超时 | connect/client/server 各一个 | 只有**全局** `tcp`/`tcpfin`/`udp` | 降级为全局 |
| 优雅停机 | `hard-stop-after` | 无 | 删服务即断连 |
| 被拒绝的连接数 | `dreq`/`dcon` 等 | 没有这个计数 | 监控视图少一条曲线 |

健康检查是最大的那块。两条路：

- **装 keepalived**：多一个要运维的组件，而且它自己也有一套配置文件要渲染
  ——等于把刚从 HAProxy 那里省下的"渲染 + reload"原样搬到 keepalived 上，
  还多一次进程间的状态不一致风险。
- **在 rl-limiter 里实现**：asyncio 每 N 秒对每个 RS 建一次 TCP 连接，失败
  N 次就 `ipvsadm -d` 摘掉、恢复后加回。技术上不难（比现在的 tc reconcile
  简单），而且**少一个组件**。但要自己处理慢启动、抖动抑制这些 HAProxy
  已经做好的细节。

倾向后者，但这是一块实打实的新工作量。

### 3.3 硬约束（部署层面）

1. **真实服务器的默认网关必须指向 director。** 否则 RS 直接把响应发给
   客户端（源地址是 RS 而不是 VIP），客户端一个 RST 就断了。HAProxy 完全
   没有这个约束——它自己发起到后端的连接，路由是平凡的。
   
   变通是在 director 上再做一次 MASQUERADE（`iptables -m ipvs --vaddr ...`），
   效果等同 FULLNAT。可行，但等于承认"要额外一层 NAT 才能用"。

2. **`conn_tab_bits` 是模块加载参数，运行期改不了。** 默认 12（4096 个哈希
   桶），百万连接要给到 20。改它得 `modprobe ip_vs conn_tab_bits=20`，也就是
   **要卸载重载模块**（等于断掉所有连接）或者重启机器。对比现在的 `maxconn`
   ——改完 reload 一下就行。这是运维体验的实质性倒退。

3. **与 conntrack 的关系要想清楚。** IPVS 自己维护连接表；一旦同时有
   iptables NAT 规则（比如上面那个 MASQUERADE），就要打开
   `net.ipv4.vs.conntrack`，于是每条连接又回到 `nf_conntrack` 表里——
   [docs/08 §3.4](08-内核参数调优.md) 那个容量问题重新登场，而且这次躲不掉。

### 3.4 一个必须提前说清楚的口径变化

**IPVS 的 `InBytes`/`OutBytes` 是 IP 层字节（含 IP/TCP 头与重传），
HAProxy 的 `bytes_out` 是应用层字节。**

换过去之后，**同一份流量的监控数字会变大 3%~8%**。影响两处：

- 监控曲线：和 tc 的口径反而统一了（tc 数的也是链路层），是好事；
- **计费**：[docs/07](07-监控数据回查.md) 的 95 分位用的是 `out_avg`。切换
  当天账单会莫名其妙涨几个点。**必须提前和商务对齐，或者在切换点做一次
  口径标注**，否则这是个会被当成事故的"数据异常"。

这一条容易被忽略，但它是本次改造里**唯一会直接影响到钱**的地方。

## 4. 性能：真的会更快吗

理论上会：IPVS-NAT 是纯内核转发，连 splice 都不需要（splice 好歹还有两次
系统调用和一个管道）。

但有三点要泼冷水：

1. **本项目实测 HAProxy + splice 是 0.33 CPU 秒/GB**（[docs/06 §1](06-tc限速方案.md)）。
   这已经不高了。IPVS 能省下的绝对值有多少，**没有实测过**，不能假设"内核态
   一定明显更快"。
2. **带宽瓶颈完全不变。** NAT 模式下所有流量照样过这台机器，网卡、softirq、
   PCIe 的账一分不少。
3. **tc 的 qdisc 锁问题一点都不会改善。** HTB 作为 root qdisc 会取代多队列
   网卡的 `mq`、把 TX 串行到一个锁上（[docs/06 §9.1](06-tc限速方案.md) 里
   一直挂着的未验证项）。那是 **tc 的问题，与谁做转发无关**——换成 IPVS
   之后 tc 还在那儿。

第 3 点值得单独强调：**上次那台机器"出向 899 Mbps / 入向 1115 Mbps"，根因
已经查明是 `cburst` 漏给（已修）。但 qdisc 锁那一条还没排除。如果修完
cburst 出向仍然偏低，那说明是锁——而换 IPVS 解决不了它。**

## 5. 工作量估计

| 模块 | 改动 | 量级 |
| --- | --- | --- |
| `tcshaper.py` | **不用改**（源端口分类不变） | — |
| `haproxy.py` → `ipvs.py` | 采样源换成 `/proc/net/ip_vs` 或 netlink | 中 |
| `collector.py` | 字段映射调整（少了 denied，多了 ActiveConn/InActConn） | 小 |
| `enforcer.py` | 从"渲染 cfg + reload"改成"调 ipvsadm 做幂等 reconcile" | 中偏大 |
| **健康检查** | **全新**：探活 + 摘除 + 恢复 + 抖动抑制 | 大 |
| `config.py` / 数据模型 | 删 `mode`、`maxconn`、三个 `timeout_*` 或改语义（**破坏性 schema 变更**） | 中 |
| 控制台 | 跟着改字段 | 小 |
| 部署脚本 | 换成装 `ipvsadm` + 模块参数 + VIP 配置 | 中 |
| 文档与测试 | 全套 | 中 |

整体**比 tc 那次改造大**：那次只换了"限速"一条链路，这次要同时换"转发"与
"配置下发"两条，还要新增健康检查，并且带一次破坏性的配置模型变更。

## 6. 验证计划

真机上按顺序做，**任何一步不成立就停下来**——后面的工作量全部建立在前面
的结论上。仓库里带了 `tools/ipvs_probe.sh` 把前两步做成了可跑的脚本。

### 第 1 步（地基）：tc 还能不能按源端口分类

> **只在 `limit_scope: frontend` 下需要做这一步。** 整机限速不分类，这条
> 推论用不上（见 [§3.1](#31-保得住的)）——那种情况下直接从第 2 步开始，
> 顺手用 `tc -s class show` 确认整机那个类的 `Sent` 在涨即可。

这是 [§3.1](#31-保得住的) 那条推论的实测。按 frontend 限速时它不成立的话，
要么改用整机限速，要么整个方案作废。

```bash
sudo tools/ipvs_probe.sh classify   # 建一个最小 IPVS-NAT 服务，打一点流量，
                                    # 看 tc 类的计数器有没有涨
```

判据：`tc -s class show` 里对应端口那个类的 `Sent` 在涨。不涨就说明反向 NAT
之后 tc 没匹配上，方案作废。

### 第 2 步：监控数据够不够用

```bash
sudo tools/ipvs_probe.sh stats
```

要确认三件事：
- `/proc/net/ip_vs` 里**按服务**分开的 `OutBytes` 存在且在涨；
- 计数器是 **64 位**（32 位在万兆上几分钟就绕回，差分会算出负数或天文数字）；
- 采一次的开销可接受（现在的预算是每秒一次，`show stat` 约 1 ms）。

### 第 3 步：性能到底赢多少

**这一步没捷径，必须 A/B 实测。**同一台机器、同一份流量、同样开着 tc：

```
方案 A：HAProxy（splice 开）+ tc
方案 B：IPVS-NAT + tc
```

比 **整机 CPU**（不只是进程 CPU——IPVS 的开销在 softirq 上，`mpstat -P ALL`
看 `%soft`），以及同 CPU 预算下的吞吐上限。

判据（建议）：如果整机 CPU 秒/GB 改善**不到 30%**，这次改造不值得——失去的
（健康检查、per-frontend 超时、运行期改连接表容量）比省下的多。

### 第 4 步：确认那两个硬约束能接受

- RS 的默认网关能不能指向 director？不能的话要加 MASQUERADE，那就顺带回答
  conntrack 容量怎么办。
- `conn_tab_bits` 要重载模块才能改，运维接受吗？

## 7. 建议

**按你换 IPVS 的目标分三种情况：**

| 目标 | 建议 |
| --- | --- |
| **省 CPU** | 值得先做第 3 步的 A/B 实测。省不到 30% 就别换 |
| **提高吞吐上限** | **方向错了。** 先排除 tc 的 qdisc 锁（docs/06 §9.1），换 IPVS 不解决它 |
| **简化架构** | **反向。** IPVS 少了健康检查、HTTP 模式、per-frontend 超时，补回来更复杂 |

我的倾向：**先做第 1、2 步（成本很低，一天以内），把地基验掉；第 3 步的
A/B 实测再决定要不要动。** 在拿到实测数字之前就开工，风险是花掉一次比 tc
改造更大的工作量，换来一个可能只有个位数百分比的收益，同时丢掉健康检查。

**如果真要做，限速范围用默认的 `host` 就行**（它现在就是默认值）。 这不是顺手改改：按 frontend
限速是这次改造里唯一一处依赖"IPVS 改写完源端口之后 tc 还能认出来"的地方，
切成整机范围就把那份不确定性整个去掉了。而 IPVS 的场景本来也更贴整机
口径——它没有 frontend 这个概念，一个 director 通常就对应一份带宽。
代价是失去"这个入口 100M、那个入口 200M"的能力；真需要分入口限额，
那这条依赖就得靠第 1 步实测顶住。

如果最后决定要做，建议**分两步走**而不是一次切换：

1. 先把采样层抽象出来（`haproxy.py` 变成一个接口，IPVS 是另一个实现），
   让两种数据面能共存、能并行对比；
2. 再换转发层。

这样任何一步出问题都能退回去，而不是一次性推倒重来。

## 8. 本文的证据等级（重要）

**本仓库的开发沙箱里，关于 IPVS 的一切都无法实测**：内核没有 `ip_vs`
（`/proc/net/ip_vs` 不存在），没有 `/lib/modules`，`modprobe` 也没有；
`ipvsadm` 装上了但一执行就是 `Can't initialize ipvs: Protocol not
available`。连 classful qdisc 都只有 `pfifo`，htb/prio/clsact 全没有。

所以本文里：

- **有实测支撑的**：只有"这个沙箱跑不了 IPVS"这一条，以及本项目现状的那些
  数字（HAProxy+splice 0.33 CPU 秒/GB、一次下发 74 ms 等，来自
  [docs/06](06-tc限速方案.md)）。
- **属于推理的**：DR/TUN 回程不经过 director（这是 LVS 的定义，可靠）、
  tc 出向 qdisc 在 POSTROUTING 之后（内核数据路径，可靠但**没量过**）、
  IPVS 的计数器语义与字段（来自 `ipvsadm` 文档，**没跑过**）。
  
  这三条里第二条的分量已经变了：整机限速只需要它弱化后的版本（"转发的包
  也走根 qdisc"），那是发包路径的定义；只有按 frontend 限速才需要它的完整
  版本（"到 qdisc 时源端口已被改写回服务端口"）。**前者按可靠算，后者仍然
  按"没量过"算。**
- **纯属估计的**：§5 的工作量、§4 关于性能的判断、§6 那个"30%"的判据阈值。

§6 的验证计划就是为了把第二类和第三类变成第一类。**在第 1、2 步跑出结果
之前，本文任何结论都不该被当成决策依据。**
