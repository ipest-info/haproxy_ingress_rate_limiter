# 监控数据的存储与回查（90 天窗口）

需求：监控视图的数据要能存下来，支持 **90 天回查**。

本文说明存什么、怎么存、怎么查，以及为什么是这么定的。所有容量与耗时
数字都是**在真实 MariaDB 10.11 上实测**的，不是估算。

---

## 1. 先算账：粒度决定一切

监控循环每秒产出一拍。90 天 = 7,776,000 秒。按每行约 200 字节、10 个
frontend 估算：

| 粒度 | 10 个 frontend 的行数 | 占用 |
| --- | --- | --- |
| 1 秒 | 77,760,000 | **14.5 GB** |
| 10 秒 | 7,776,000 | 1.4 GB |
| 1 分钟 | 1,296,000 | 247 MB |
| 5 分钟 | 259,200 | **49 MB** |

结论很直白：**90 天回查这件事本身几乎不花钱，贵的是粒度**。1 秒粒度存
90 天是单表近亿行，写不动也查不动——一次范围扫描就是事故。

因此采用**分级保留**（RRD、Prometheus、各家 TSDB 都是这个路子）：

| 层 | 粒度 | 保留 | 用途 |
| --- | --- | --- | --- |
| 内存 | 1 秒 | 10 分钟 | 控制台实时曲线（不落库） |
| 落库 | 1 分钟 | 7 天 | "昨天下午三点前后到底怎么了" |
| 落库 | 5 分钟 | **90 天** | 回查 + **计费** |

### 为什么最长的那层是 5 分钟

不是凑数：**带宽计费的行业惯例（95 计费）就是按 5 分钟采样点统计的**。
本项目服务的正是带宽计费场景，把最长那层直接对齐计费口径，回查与对账
用同一份数据——不会出现"运维看的数和账单上的数对不上"。

实测：30 天的 95 分位算一次只要 34 ms（8,640 个采样点）。

## 2. 每个桶存什么：三类量三种聚合

这是整个设计里最容易做错的地方。**把所有指标一律存平均值，回查时会发现
该问的问题一个都答不了。**

| 类别 | 指标 | 聚合方式 | 为什么 |
| --- | --- | --- | --- |
| 速率类 | 出/入带宽 | **avg + max** | avg 是计费口径；max 用来找峰值。只存 avg 会把尖峰彻底抹平，"那天下午到底冲到多少"就永远查不出来 |
| 计数类 | 新建连接、被拒绝、丢包、触发限速 | **sum** | 问题形如"那天一共丢了多少包"。存平均速率再乘回去会因桶不满而失真 |
| 瞬时类 | 并发/活跃/空闲连接 | **avg + max** | 同上 |

另外每个桶还记两样东西，缺了它们数据就没法解读：

- **当时的限额**（`quota`）。限额会被人改，事后从配置里查到的是**现在**
  的值而不是当时的值。没有它，一条带宽曲线读不出"到底有没有打满"。
- **`samples` / `degraded`**：该桶实际采到几拍、其中几拍是采样失联时沿用
  的陈旧值。没有这两个数，一个"半空的桶"和一个"真的很闲的桶"在图上长得
  一模一样。

平均值按**实际采到的拍数**算，不是按桶的理论长度——桶不满时（启动、
重启、失联）除以理论长度会把均值系统性拉低。

## 3. 表结构

建表语句见 [deploy/mysql/init.sql](../deploy/mysql/init.sql) 的
`metric_rollup`。两个设计点：

```sql
PRIMARY KEY (instance, scope, bucket_s, ts),
KEY idx_prune (bucket_s, ts)
```

- **主键顺序 = 最常见的查询形状**："某台机器的某个 frontend、某个粒度、
  某段时间"，四个条件正好构成一次连续的范围扫描。实测 `EXPLAIN` 确认
  `type=range key=PRIMARY`。
- **`idx_prune` 专供剪枝**：按 (粒度, 时间) 删过期行，不必扫主键。实测
  `EXPLAIN DELETE` 确认 `type=range key=idx_prune`。

`scope` 列存 frontend 名，空串表示实例级——两级数据同表，查询时按 scope
区分。多台机器写进同一张表（`instance` 列区分），因此**这份数据天然支持
跨机回查**，补上了"每个控制台只看本机"的短板。

## 4. 实测：90 天数据下到底跑多快

在真实 MariaDB 10.11 上灌满 90 天 × 5 分钟 + 7 天 × 1 分钟（10 个
frontend + 实例级，共 **396,000 行 / 58.2 MB**，与前面的估算吻合）：

| 查询 | 返回行数 | 耗时 |
| --- | --- | --- |
| 某 frontend 最近 1 小时（60s 粒度） | 58 | **1.4 ms** |
| 某 frontend 最近 24 小时（300s） | 288 | 2.2 ms |
| 某 frontend 最近 30 天（300s） | 8,640 | 53 ms |
| 某 frontend 整 90 天（300s） | 25,920 | **137 ms** |
| 实例级整 90 天（300s） | 25,920 | 137 ms |
| 30 天 95 分位（计费口径） | 8,640 | 34 ms |

剪枝：

| 场景 | 行数 | 耗时 |
| --- | --- | --- |
| 稳态（每天删最老一天的 5 分钟数据） | 3,168 | **27 ms** |
| 最坏（保留期从没跑过，一次删 60 天积压） | 186,912 | 1,795 ms（38 批） |

剪枝**分批删**（每批 5000 行）而不是一条 DELETE 扫全表：这张表和配置表
在同一个库里，长事务持锁会把配置读写一起拖慢。

## 5. 写入路径：与限速、与实时监控完全隔离

与本项目其它副链路一脉相承——**落库失败绝不影响限速，也不影响实时控制台**。

```
监控循环（每秒一拍）
   ├─→ StatusHub.record()      内存环形缓冲 → SSE 实时曲线
   └─→ MetricStore.record()    纯内存累加，**不做任何 IO**
                                    ↓ 桶关闭时入队（有界队列）
                               写入任务 ──→ MySQL
```

`record()` 只做内存累加。即便数据库卡住几十秒，监控循环的节拍也一拍不差。
队列满时**丢最旧的批次**并告警：宁可丢历史，也不能让内存无界增长或把
监控循环拖住。

**停机时会 flush 未关闭的桶**。桶要等下一拍跨过边界才关闭，所以最新那个
桶一直悬在内存里；不 flush 的话每次重启都会丢掉最多一个桶——5 分钟那层
就是 5 分钟数据。生产上重启（发版、配置变更）并不罕见，日积月累会在 90 天
的曲线上留下一串规律的缺口。flush 出来的是"半截桶"（`samples` 小于桶长），
查询侧据此知道这个点不完整，不会把它当成一次真实的低谷。

## 6. 怎么查

### HTTP 接口

```bash
# 不给 bucket_s 时按区间自动选层
curl 'http://localhost:8090/api/metrics?scope=fe_main&from=<unix>&to=<unix>'

# 实例级用空 scope
curl 'http://localhost:8090/api/metrics?scope=&from=<unix>&to=<unix>'

# 也可以指定粒度
curl 'http://localhost:8090/api/metrics?scope=fe_main&from=..&to=..&bucket_s=300'
```

自动选层的规则：**能用细的就用细的**，前提是该层的保留期覆盖得到起点，
且点数不超过 2000。查 90 天却拿 1 分钟粒度会一次拉回 13 万个点；查最近
半小时用 5 分钟粒度又太糊。

> `/api/history` 与 `/api/metrics` 的分工：前者读**内存**里最近 10 分钟的
> 1 秒粒度（实时曲线），后者读**库**里的分级聚合（历史回查）。路径与语义
> 都分开，免得有人拿 history 去查昨天。

### 直接查库（对账、跑报表）

```sql
-- 某 frontend 最近 30 天的 5 分钟曲线
SELECT ts, out_avg, out_max, conn_max, drop_out_sum, quota
  FROM metric_rollup
 WHERE instance='hap-1' AND scope='fe_main' AND bucket_s=300
   AND ts >= UNIX_TIMESTAMP() - 30*86400
 ORDER BY ts;

-- 95 计费：30 天出向带宽的 95 分位（单位 bytes/s，×8 得 bps）
SELECT out_avg FROM metric_rollup
 WHERE instance='hap-1' AND scope='fe_main' AND bucket_s=300
   AND ts >= UNIX_TIMESTAMP() - 30*86400
 ORDER BY out_avg
 LIMIT 1 OFFSET (SELECT FLOOR(COUNT(*)*0.95) FROM metric_rollup
                  WHERE instance='hap-1' AND scope='fe_main' AND bucket_s=300
                    AND ts >= UNIX_TIMESTAMP() - 30*86400);

-- 跨机汇总：某天全部机器的出向峰值
SELECT instance, MAX(out_max) AS peak
  FROM metric_rollup
 WHERE scope='' AND bucket_s=300 AND ts BETWEEN %s AND %s
 GROUP BY instance;
```

## 7. 开关与容量规划

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_METRICS_RETENTION` | 开启 | 设 `0`/`false` 关闭落库（此时只有内存里最近 10 分钟的实时曲线） |

**只在数据库配置模式下生效**：落库表与配置表在同一个库里，纯 YAML 部署
没有可写的地方。

容量按 frontend 数线性增长。上面 58 MB 是 10 个 frontend 的实测值，
每多 10 个 frontend 约再加 55 MB。要调保留期改
`metricstore.RETENTION_DAYS`。

## 8. 没做的部分

- **没有做表分区**。90 天 40 万行的量级，分批 DELETE 实测 27 ms 就够了；
  引入 RANGE 分区会让建表与运维复杂度上一个台阶，收益不成比例。如果
  frontend 数量涨到几百个、单表过千万行，那时再按 `ts` 做 RANGE 分区、
  用 `DROP PARTITION` 代替 DELETE 是自然的下一步。
- **没有引入专门的时序库**（Prometheus/VictoriaMetrics/InfluxDB）。它们
  在这个数据量上是杀鸡用牛刀，而且会多一个必须运维的组件；MySQL 已经是
  本项目的既有依赖，运维也已经在备份它。数据量真正上量时再迁不迟——
  聚合语义（avg/max/sum + 桶）和主流 TSDB 是一致的，迁移不会推倒重来。
- **没有做告警的持久化**。超限告警目前只进日志与控制台，没有落库成
  "告警事件表"。回查"这三个月一共超限过几次"目前只能从 `out_avg` 与
  `quota` 两列自己比较得出。
