# 04 部署指南

形态永远是**同机**：rl-limiter 与被限的流量在同一台机器上（tc 只能在
流量进出的那台机器上做；原因见
[01 总体设计](01-总体设计.md) §2）。三种部署方式按推荐顺序：

| 方式 | 适用 | 入口 |
| ---- | ---- | ---- |
| 二进制一键安装 | 批量生产机（目标机不需要 Python） | [11 发布与安装](11-发布与安装.md) |
| 裸机 + systemd（venv） | 开发机/想读改源码 | `deploy/bare/rl-limiter.sh` |
| 容器（host 网络） | 想要镜像交付、性能≈裸机 | `docker-compose-host.yml` |
| compose 演示 | 本地体验/验证，非生产 | `docker-compose-demo.yml`，见 [05](05-DockerCompose演示.md) |

## 1. 内核与权限前提（所有方式通用）

| 需要 | 用途 | 验证 |
| ---- | ---- | ---- |
| `sch_htb` | HTB 整形（出向与 IFB 上的入向） | `modprobe sch_htb` |
| `ifb` + `act_mirred` | 入向平稳整形（`RL_TC_IN_MODE=ifb`，默认） | `modprobe ifb`；建不出来服务会**启动失败**并写明处置 |
| `cls_flower` + `act_police` | `conn_rate` SYN 速率闸 / police 模式 | `tc filter add ... flower` 干跑 |
| `CAP_NET_ADMIN` | 一切 tc 操作 | 容器需 `cap_add: [NET_ADMIN]`；裸机 root 或 systemd `AmbientCapabilities` |

Docker Desktop（Mac/Win）的精简虚拟机内核通常**没有 ifb**：只能
`RL_TC_IN_MODE=police` 降级（实例总闸不可用），或换 Linux 主机。这不是
配置问题，是内核缺模块；服务的启动失败信息会把三条出路写清楚。

内核参数（somaxconn、conntrack、端口区间等）统一由
`deploy/sysctl/tune-kernel.sh` 处理，见 [08 内核参数调优](08-内核参数调优.md)。

## 2. 双网卡接线

生产双网卡 = 机器的两张物理网卡：

```
客户端 ──► eth-front（客户端侧）  [入向整形在这张卡]
             │ 业务进程（任意服务，rl-limiter 不感知）
             ▼
           eth-back（后端侧）──► 后端服务器   [不碰，后端流量绝不被误伤]
```

**节点必须双网卡**：两种装机脚本（二进制 `install.sh`、venv
`deploy/bare/rl-limiter.sh`）都先检查本机物理网卡，少于两张**不允许
安装**。客户侧与后端侧网卡**相斥**——不能是同一张卡（入向限速会卡住
后端回程流量）；装机时校验一次，rl-limiter 每次启动再校验一次
（`RL_TC_IN_IFACE` 与 `RL_BACKEND_IFACE` 相同即启动失败）。

**出厂默认即此形态**：流出方向不限速（`RL_TC_IFACE=-`）、流入方向在
eth0（客户端侧）限速（`RL_TC_IN_IFACE=eth0`）、eth1 为后端侧
（`RL_BACKEND_IFACE=eth1`）。这几行在
`deploy/bare/rl-limiter.env.example` 里**显式写死**（装机后在
`/etc/rl-limiter/rl-limiter.env`）——接线以 env 文件为准，排障时看
文件即知，不用记代码默认值；代码默认值与之相同，env 文件缺行为也
一致。

- 机器网卡不是 eth0/eth1 命名（ens33/enp1s0…）：二进制安装时用
  `--client-nic <客户侧> --backend-nic <后端侧>` 指定（写进 env），或
  手工设 `RL_TC_IN_IFACE` / `RL_BACKEND_IFACE`——不做自动探测，入向
  规则放错网卡会误伤后端流量。容器里网卡名不稳定时，用
  `RL_FRONT_SUBNET=<客户端网段前缀>` 让入口脚本按网段定位；
- 基线的出向 HTB 形态（`RL_TC_IFACE=<网卡>`、`RL_TC_IN_IFACE=-`，
  闭环与入向整形整体不参与）只留给开发验证：单网卡机器过不了装机
  脚本的双网卡检查，生产节点一律双网卡。

## 3. 裸机 + systemd

不依赖机器上跑的任何服务：装机脚本只装 rl-limiter 自己。

```bash
cd deploy/bare
sudo ./rl-limiter.sh install     # 幂等，可反复跑；或 make bare-install
sudo ./rl-limiter.sh check       # 体检：只看不改，有问题退出码 1
sudo ./rl-limiter.sh start|stop|restart|status|logs
```

install 做的事（每步有输出）：

1. 前置检查：python3 ≥ 3.9、tc 可用、内核有 HTB、systemd、双网卡；
2. 建专用用户 `rl-limiter`（tc 权限由 unit 的 CAP_NET_ADMIN 提供）；
3. venv 装到 `/opt/rl-limiter`；
4. 配置落到 `/etc/rl-limiter/{config.yaml,rl-limiter.env}`（已存在**不
   覆盖**）；systemd unit 用 `deploy/bare/rl-limiter.service.in` 模板。

环境变量（`RL_TC_IN_IFACE`、`RL_BACKEND_IFACE`、`RL_CONSOLE_PORT`、
`RL_API_TOKEN` 等）写在
`/etc/rl-limiter/rl-limiter.env`，模板见 `deploy/bare/rl-limiter.env.example`。
改配置后：YAML 限额类字段自动热生效；接线/闭环参数 `systemctl restart
rl-limiter`。

## 4. 容器 + host 网络（生产推荐的容器形态）

样例：仓库根目录 `docker-compose-host.yml`（单节点、逐项注释）：

```bash
docker compose -f docker-compose-host.yml up -d --build
```

为什么是 host 网络：bridge 的数据面（veth→网桥→conntrack/NAT）在高带宽/
高新建连接下有 10%~30% 开销；host 网络没有这些层，性能与裸机一致，又保留
镜像交付便利。要点（样例注释里都有）：

- `network_mode: host` + `cap_add: [NET_ADMIN]`，不需要 privileged；
- **没有 `ports:` 映射**：控制台端口直接占宿主机。
  控制台保持默认只绑 `127.0.0.1`，远程看走 SSH 隧道；
- 默认接线已是闭环形态（`RL_TC_IFACE=-` + `RL_TC_IN_IFACE=eth0`），
  客户端侧网卡不叫 eth0 时在 compose 里改；
- host 网络下 compose 的 `sysctls:` **不可用**（与宿主机共享 netns）：
  内核参数在宿主机上 `tune-kernel.sh apply`，或 `dump` 固化到
  `/etc/sysctl.d/`；
- 配置模板复制副本后再挂载，别直接改仓库里的模板（升级会冲突）；
- 监控落盘挂宿主机卷（样例已挂 `/var/log/rl-limiter`）。

容器异常被杀时 IFB/tc 规则可能残留在宿主机内核里：重启本服务即幂等
重建/接管，无需手工清。

## 5. 升级与回滚

- 代码升级：换镜像/换 venv 后重启进程即可。tc 规则由 reconcile 幂等
  对齐，限额配置都在 YAML 里，无迁移步骤；
- 闭环动态值不落盘：重启后从"全开"重新收敛（几个调节周期）；
- 回滚同理——两份配置文件向后兼容是设计约束（废弃字段会在启动时给出
  明确的迁移指引而不是静默忽略）。

## 6. 部署后的验收清单

1. `systemctl status rl-limiter` / `docker ps`：进程在跑（起不来先看
   日志里的启动失败原因，都是人话）；
2. 启动日志第一条"服务配置加载完成"的摘要：受管清单、限额、两个配置
   文件路径逐项核对；
3. `python3 tools/tc_check.py verify`：核对网卡上的 tc 实况与配置一致
   （`doctor` 体检环境、`plan` 干跑看命令）；
4. 控制台"配置"页：运行参数只读表 = 你以为的接线；"tc 实况"面板：
   期望配置与内核原始输出对得上；
5. 压一把流量，看"调节视图"收敛（见 [06](06-控制台与监控.md)）。
