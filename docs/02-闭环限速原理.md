# 02 闭环限速原理

本分支的限速语义（与基线"出向 HTB 直接整形"不同）：

1. **登记的限速值是出向带宽的判断基准**——`quotas.<frontend>` 是该端口
   出向带宽的目标值，`instance_quota_mbps` 是实例出向总带宽的目标值；
2. **出向本身不做 tc**（`RL_TC_IFACE=-`）。出向超过目标时，通过**动态
   收紧入向（请求方向）带宽**来间接把出向压回去：请求进得少 → 响应
   自然出得少；
3. **调整过程平缓**：小步、带死区、带滞回，宁可收敛慢也不要振荡。

## 1. 为什么限入向而不是直接整形出向

出向 HTB 把超速流量**排队**，响应延迟全体抬高，所有客户端一起变慢。
入向限速只掐请求流（体量远小于响应流），响应路径零排队：没被掐的请求
全速完成，客户端体验是"进得慢"而不是"下得慢"。代价是控制是间接的、
有滞后——所以算法必须平缓。

**ACK 杠杆**是理解一切数值的关键：下载型业务的入向几乎全是 TCP ACK，
实测杠杆约 70~150:1（入向 1Mbps 的 ACK 可维持约 70Mbps 以上的出向）。
推论：

- 入向的均衡点比出向目标低一两个数量级（出向目标 40Mbps 时入向总闸
  往往收敛在 0.5Mbps 附近）；
- 一切"锚出向刻度"的参数（下限、步长）在入向刻度上都是巨值，必须锚
  入向的实际值（落位值/当前值）——这正是算法里"落位""锚当前值"等
  设计的由来。

## 2. 执行面：IFB + HTB（默认）与 police（备选）

入向整形由 `RL_TC_IN_MODE` 选择，作用在客户端侧网卡（`RL_TC_IN_IFACE`）：

| | `ifb`（默认，`tcifb.py`） | `police`（备选，`tcingress.py`） |
| ---- | ---- | ---- |
| 机制 | ingress 把包镜像重定向到 IFB 虚拟设备（默认 `ifbrl0`），在 IFB 上建 HTB **排队整形** | ingress 上直接 police，超额**丢包** |
| 平稳性 | 平稳（borrow/burst，曲线圆滑） | 锯齿（靠 TCP 对丢包的反应收敛） |
| 实例总闸 | 支持（HTB 层级聚合类） | 不支持（police 没有层级） |
| 内核要求 | ifb 模块 + act_mirred | act_police |

ifb 模式的 tc 结构（`tc` 的一条 prio 只能挂一种 protocol，ip 与 ipv6
必须用不同 prio——这是全项目 tc 过滤器的统一规则）：

```
真实网卡 ingress (ffff:):
  prio 3/4  flower ip_proto tcp tcp_flags syn  police <conn_rate>/s   ← SYN 速率闸
  prio 5/6  matchall  action mirred egress redirect dev ifbrl0        ← 其余包全部转 IFB

ifbrl0 root: htb
  1:ffff  实例入向总闸（动态值；没设实例目标时不建）
  1:<port> 每个端口的类（登记了 request_limits.mbps 的端口；
           有总闸时全部端口都挂进 1:ffff）
  过滤器按目的端口分类，ip=prio 1 / ipv6=prio 2
```

`conn_rate`（每秒新建连接数）始终是**静态**登记值、在真实网卡 ingress
上用 flower+police 执行——SYN 只有几十字节，超了直接丢即可，不参与
带宽闭环。

## 3. 闭环控制器（ingressgov.py）

两级环共用同一套算法，由 `dynamic_ingress` 段配置，每 `interval_s`
（默认 15s，demo 用 5s）跑一轮：

| 环 | 观测（10s 均值） | 目标 | 执行 |
| ---- | ---- | ---- | ---- |
| 单端口环 | 该 frontend 出向 mean10（HAProxy 口径——网卡无法按端口拆，这是唯一的端口级数据源） | `quotas.<name>` | 该端口入向类的速率，活动区间 [floor, `request_limits.<name>.mbps`] |
| 实例环 | **客户端侧网卡的流出速率**（/proc/net/dev 差分的 10s 滑窗；链路层、整机，与按量计费同口径）。设备数据缺席（`RL_NIC=-`）才回退 HAProxy 口径求和并 warn 一次 | `instance_quota_mbps` | IFB 总闸类 `1:ffff` 的速率（仅 ifb 模式） |

实例环盯网卡而不是 HAProxy 的理由：①按量计费计的就是网卡字节；
②网卡读数是本地文件差分（μs 级），没有 stats socket 应答时延带来的
伪波动；③HAProxy 采样失联（degraded）时实例环**照常工作**——只有
端口级环（观测必须来自 HAProxy）才冻结。网卡口径含链路层头部与
HAProxy 之外的流量，比应用层字节偏大 3%~8%，死区宽度把这层差异吃掉。

单轮决策（ratio = 观测/目标）：

- **死区**：ratio ∈ [`low_ratio`, `high_ratio`]（默认 [0.85, 1.0]）→
  不动。目标附近的波动不折腾 tc；
- **超了**（ratio > high_ratio）：下调。降幅 = (ratio − high_ratio)×0.5，
  **封顶 `step_down_max`**（默认单次最多 −10%），乘性作用在当前值上；
- **低了**（ratio < low_ratio）：上调 `step_up`×**当前值**（默认 +5%/次，
  乘性；绝对步长下限 0.1Mbps，免得贴地时爬不动），封顶回到登记上限。
  到顶后退出动态语义（= 静态全开）；
- **epsilon**：变化小于 `apply_epsilon`（默认 2%）不下发——入向规则整组
  重建有成本且清零 tc 统计。唯一例外：封顶回上限的最后一步放行（那一步
  的语义是退出动态，乘性末步永远小于 epsilon，不放行会永远卡在上限脚下）；
- **degraded 冻结**：HAProxy 采样失联的轮次，端口级环不动作（观测是
  陈旧值）；实例环的观测来自网卡，照常运行——有网卡观测时总闸不会
  因 stats socket 权限/失联问题跟着失明。

**为什么上下都乘性锚当前值**（本分支踩过的坑，别改回去）：早期上调是
`step_up`×上限的加性步。由于 ACK 杠杆，动态值收敛在上限的几十分之一
刻度，那一步等于一步翻倍——上冲过头 → 出向猛涨 → 猛降回来，形成稳定
的**极限环**（页面上带宽一会高一会低）。两个方向都乘性锚当前值后步长
对称，流量稳定时动态值收敛进死区不再动。

### 实例环的落位（起调点 = 实测流入带宽）

实例环首次需要收紧时，总闸**不从上限爬降**，而是直接**落位**到
`实测流入带宽 × 1.1`（留一口气；绝对下限 0.1Mbps；落位值必须低于当前值
才算落位）。原因还是 ACK 杠杆：从上限/出向目标起步，前几十步全是空转。
落位本身不掐流量（闸 ≈ 当前流量 + 余量），真正收紧由后续小步完成。

- 实测读的是**真实网卡的 RX 字节差分**（`ip -s link`），不是 IFB 计数
  ——只设实例目标、没登记 request_limits 时，首次收紧那一刻重定向管路
  还没建，IFB 上读不到数；
- 实测暂缺（差分基准刚建立）等一轮再落位；连续两轮没有才回退从上限
  爬降——坏掉的测量源不能把实例环卡死；
- **落位后下限锚落位值**：floor = max(0.1, `floor_ratio`×落位值)。没
  登记 request_limits 时总闸上限退化为出向目标值，`floor_ratio`×它是
  出向刻度的下限，比入向均衡点高一个量级，总闸会贴着它卡死、出向永远
  压不到目标（e2e 实测抓到过）。

### 总闸上限与两环并存

总闸上限 = 登记的 `request_limits.*.mbps` 之和；一个都没登记时退化为
实例目标值本身（入向远小于出向，等于"全开但有界"）。两环可同时在跑、
互不覆盖——HTB 层级天然执行 min(端口 ceil, 总闸)。

### 接线

- 控制器挂在监控循环的 sampler 链上吃每拍的 mean10；
- `run_governor` 周期跑 `adjust_once`，有变化就 set 下发事件，叫醒
  `run_ingress` 立刻 reconcile；
- 下发侧经 `effective_limits()` / `effective_instance_bits()` 取**动态
  后的**值——静态登记值只是上限，不再直接下发；
- 带宽变更尽量走 `tc class change` 原位改速率，不重建规则、不清统计。

## 4. 收敛特性（demo 实测）

目标 40Mbps、900 并发、无 request_limits 登记：

- 落位：首轮按实测流入 ~1.6Mbps×1.1 起调；
- 收敛：约 70s 内出向从 247Mbps 压到目标附近；
- 稳态：出向 34~42Mbps（均值 38.4、标准差 1.8），总闸在 0.53~0.63Mbps
  之间小步微调，死区内长时间零动作。

判断收敛质量看控制台"调节视图"：出向总带宽应贴着目标参考线、总闸曲线
应是小台阶而不是大锯齿。见 [06 控制台与监控](06-控制台与监控.md)。

## 5. 为什么不是 bwlim / 不是出向 HTB（历史依据）

- **HAProxy shared bwlim**：挂上滤镜即关闭内核 splice，同吞吐 CPU 多花
  一倍（实测 0.59 → 0.33 CPU 秒/GB），限速精度也不如内核 tc；
- **出向 HTB**（基线形态，本分支仍可用）：精确、简单，但超速时响应
  排队、全体延迟抬高。按量计费场景的诉求是"把量压住 + 对客户端温和"，
  闭环入向更合适。单网卡机器要用出向 HTB：设 `RL_TC_IFACE=<网卡>`、
  `RL_TC_IN_IFACE=-` 即回到基线行为。

## 6. 已知边界

- `conn_rate` 的 SYN 闸依赖 `cls_flower` + `act_police`：本仓库的沙箱
  内核缺这两个模块，该路径**未经真机验证**（命令结构有单元测试钉住）；
- IFB 依赖内核 ifb 模块：Docker Desktop（Mac/Win）的精简虚拟机内核
  通常没有——启动会**直接失败**并写明处置（见 [09 排障指南](09-排障指南.md)）；
- 实例环的观测与执行同为链路层口径（网卡）；端口级环的观测是 HAProxy
  应用层字节、执行是链路层字节，两者本就不相等（头部开销），死区的
  宽度已把这层差异吃掉；
- 动态值不落盘：进程重启后从"全开"重新收敛（几个调节周期内完成）。
