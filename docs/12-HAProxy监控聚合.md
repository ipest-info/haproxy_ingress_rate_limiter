# 多台 HAProxy 的监控聚合（hapagg）

从一批 HAProxy 的 stats socket 批量拉 `show stat` / `show info`，把 N 台
**合并成一个视图**。与本仓库其它部分（rl_limiter / netlimit）不共享代码
与配置，可以单独拿走。

**纯只读**：只发 `show stat` 和 `show info` 两条命令，不改任何运行期状态。

```bash
hapagg view    -f targets.txt          # 聚合视图（默认子命令）
hapagg view    -f targets.txt --all    # 全部监控维度（默认只显示核心列）
hapagg view    -f targets.txt --watch  # 每 5 秒刷新
hapagg node    -f targets.txt          # 每台机器一行的健康小结
hapagg drill   -f targets.txt --proxy fe_main   # 某个 proxy 在各台上的原值
hapagg json    -f targets.txt          # 机器可读输出
hapagg targets -f targets.txt          # 只解析清单，不连接任何机器
```

---

## 1. 接线

各台的 `haproxy.cfg` 里要有：

```
stats socket ipv4@*:9999 level admin expose-fd listeners
```

**关于 `level`**：hapagg 只用两条只读命令，`level user` 就够。上面写
`admin` 是因为很多现场本来就这么配（`expose-fd listeners` 是为无缝
reload 准备的，与监控无关）。

> ⚠️ **TCP stats socket 没有任何鉴权。** `level admin` 意味着任何能连上
> 9999 的人都可以停服务、改权重、下线后端。`ipv4@*` 还表示监听所有地址。
> 至少要用防火墙/安全组把 9999 限制在监控网段内；能收就把 level 降到
> `user`。这一条与 hapagg 无关——它只读——但既然要求把这个口子开出来，
> 就得把风险说清楚。

## 2. 批量导入

目标清单一行一台，`-f` 指文件（可多次），`-t` 直接在命令行给（可逗号
分隔）。两边同一套解析规则。

```
10.0.0.11:9999            地址:端口
10.0.0.12                 省略端口 → 用 -p 的默认值（9999）
bj-1 = 10.0.0.13:9999     起名字，视图里按名字显示
[2001:db8::5]:9999        IPv6 必须加方括号
10.0.0.20-24:9999         末段区间 → 展开成 5 台
# 注释，行内 # 之后也忽略
```

几条刻意的行为：

- **写错的行报到具体行号并中止**，不跳过。清单里一行写错说明运维的意图
  没被完整表达，静默忽略等于让聚合少一台——而视图看起来完全正常。
- **重复的行去重**（按 `host:port`）。同一台写两遍会让它的流量被**算两
  次**，同样是"视图正常、数字错误"。重复登记是无害的手误，所以去重而不
  是报错。
- **区间带名字时会自动编号**（`sh` → `sh-1`…`sh-5`）。否则几台同名，
  视图里分不出谁是谁。
- 上线前先跑一次 `hapagg targets -f ...`：它只解析、不连接，能在碰任何
  机器之前把清单问题挑出来。

IPv6 带端口为什么强制方括号：`2001:db8::5:9999` 的最后一段到底是端口还
是地址的一部分，没有任何办法判断。

## 3. 跨机怎么合并 —— 这是最容易出错的地方

合并的身份是 **(pxname, svname)**：几台上同名的 proxy 对象被当成同一个
东西。3 台各有一个 `fe_main`，运维关心的是"这个入口一共扛了多少"。

**每个维度用哪种合并方式，直接决定数字对不对。** 选错不会报错，只会给
出一个看起来合理、实际错误的数：

| 方式 | 用在哪 | 选错的后果 |
| --- | --- | --- |
| **求和** | 字节、连接数、会话数、速率、各类错误计数 | — |
| **取最大** | 峰值类（`smax`/`rate_max`/`*_max`） | 相加会得到一个**从未真实发生过**的"总峰值"（各台峰值不同时发生） |
| **取最小** | 空闲率 `Idle_pct`、运行时长 `Uptime_sec` | 求和得到 285% 这种荒唐数字；取平均会把一台已经跑满的机器藏在平均值后面 |
| **加权平均** | 各类延迟 `qtime`/`ctime`/`rtime`/`ttime` | 简单平均会让空闲机器把繁忙机器的高延迟稀释掉 |

加权平均的权重是该对象的累计会话数 `stot`。举个真实会遇到的例子：

```
一台繁忙机器 100ms（10000 个请求）+ 两台空闲机器各 1ms（各 1 个请求）
  简单平均 = 34ms   ← 看起来一切正常
  加权平均 = 100ms  ← 问题立刻可见
```

### 峰值为什么标成「(单机)」

当前会话是**求和**（3 台各 60 = 180），会话峰值是**取最大**（单台最高
99）。表上就会出现 "当前 180 / 峰值 99" 这种自相矛盾的组合。

两个数各自都对，错的是让人以为它们同一口径。**真正的"集群同时刻峰值"
无法从各台的历史峰值推出来**——那需要时间对齐的采样，stats socket 给不
了。所以不假装能算，只在标签上把口径写死：`会话峰值(单机)`。

### 状态取最坏

3 台里 1 台 `DOWN`，整体就显示 `DOWN`，不会被 2 台 `UP` 平均掉。同时
保留 per-node 状态——聚合告诉你"有问题"，下钻告诉你"在哪台"。

## 4. 部分失败必须看得见

这是这类工具**最危险的失效方式**：

> 5 台里 2 台连不上，视图照样给出一个漂亮的总量，没有任何迹象表明少了
> 2 台。那个数字偏低，但看起来完全正常，可能好几天没人发现。

所以：

- 每个总量旁边都带覆盖度：`**3/4 台**（1 台失败，下面的总量只含成功的
  那些）`；
- 每台的失败原因单独列出（超时 / 连不上 / 权限被拒 / 回包解析不了）；
- 一台都没采到时**退出码非零**——这个命令常被塞进脚本或告警里，"全挂了"
  和"一切正常"必须在退出码上就能分开；
- 一台卡住只让**这一台**失败，不中断整轮（并发采集，单台超时默认 3 秒）。

顺带还有一个只有聚合视图才看得出来的信号：

```
[warn] fe_api/FRONTEND 只在 2/3 台上存在（hap-1、hap-2）
       —— 各机器的 haproxy.cfg 可能不一致
```

某台漏了一次发布，单看那台一切正常，只有横向比对才发现。

## 5. 版本差异怎么处理

**一律按列名取值，绝不按列序。** HAProxy 2.4→2.8 的 CSV 多了十几列；
按位置取的话换个版本所有数字都会串位，而且串完之后图照样画得出来。

取不到的列返回 `None`，视图显示 `-`，**不是 0**。"这个版本没有这个指标"
和"这个值确实是 0"是两回事。集群里混着不同版本时视图会明说：

```
[warn] 各机器 HAProxy 版本不一致（hap-1=2.8.16, hap-3=2.4.22）——
       部分维度可能只有一部分机器提供
```

表格会自动丢掉**所有机器都取不到**的列：一整列 `-` 只占宽度、不带信息。

## 6. 监控维度

按运维实际关心的问题分组，而不是按 CSV 的列序：

| 分组 | 内容 |
| --- | --- |
| 流量 | 入向/出向字节 |
| 连接 | 当前/峰值/上限/累计会话、会话速率、连接速率 |
| 排队 | 当前排队、排队峰值（backend/server 才有意义） |
| 错误 | 请求错误、连接后端错误、响应错误、拒绝请求/响应/连接、重试、重新分发、客户端/后端中断、健康检查失败、被摘除次数 |
| HTTP | 1xx–5xx、请求速率、累计请求 |
| 延迟 | 排队/连接/响应/总耗时及各自峰值 |
| 后端 | 活跃/备份服务器数、被选中次数、权重 |
| 进程 | 当前/累计连接、连接与会话速率、连接上限、SSL 连接、任务数、运行队列、最低空闲率、最短运行时长 |

默认只显示**核心列**（每天真要看的那些）；`--all` 显示全部。全部铺开是
30+ 列，任何终端都放不下，而横向滚动的表格等于没有表格。

## 7. 联调

仓库里带了一个能造出"不完美现实"的假集群：

```bash
python3 tools/fake_haproxy_cluster.py --ports 19001,19002,19003
python3 tools/fake_haproxy_cluster.py --ports 19004 --down be_api/srv2
python3 tools/fake_haproxy_cluster.py --ports 19005 --drop-proxy fe_api
python3 tools/fake_haproxy_cluster.py --ports 19006 --old-version --slow 2
```

它回的是**照抄真实 HAProxy 2.8 的完整列头**（含 frontend/backend/server
三类行）。用自洽的假数据会把"按列名取值"这件事的价值整个盖掉——按列序
取也能跑通。

## 8. 验证到哪一步

这个工具是纯 TCP 的，**没有前面那些内核特性的限制，所以协议行为与故障
处理全部实测**（真 socket、真服务端）：

- runtime socket "一次连接只服务一条命令"——实测服务端在两条命令上各收到
  一次连接。复用长连接会读到空回包，表现为"这台机器时好时坏"；
- 一台超时/连不上/权限被拒/回包无列头，都只让那一台失败，不中断整轮；
- `show info` 解析失败不影响那台机器的流量数据（次要链路独立容错）；
- 10 台各睡 0.3 秒，并发采集总耗时 < 1.5 秒（串行的话监控几十台就不可用）。

合并规则做过变异验证：把峰值改成求和、空闲率改成求和、加权平均退化成
简单平均、取不到的列当成 0、状态取最好、失败机器不计入总数——**六种改法
全部被测试逮住**。

**没有验证过的**：真实 HAProxy 的回包。所有解析用例的样例都照真实格式
写，但本仓库的开发机上没有 HAProxy 可连。上线前先用一台真机跑
`hapagg node -t <IP:9999>` 确认能连上、能解析。
