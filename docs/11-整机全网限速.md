# 本机全网限速（netlimit）

把**这台机器发出去的全部流量**合起来限在一个总额度内，不管它从哪张网卡
出去、源地址是哪个 IP。与 HAProxy、LVS 都没有关系——`netlimit` 是一个
独立工具，不共享本仓库其它部分的任何代码与配置，可以单独拿走。

```bash
netlimit status            # 看网络长相与限速实况（只读）
netlimit doctor            # 体检：内核/工具/权限够不够（只读）
netlimit plan  -r 1000     # 干跑：只打印将要执行的命令，一条都不执行
netlimit apply -r 1000     # 下发：整机出向总共 1000 Mbps
netlimit off               # 关掉限速，拆掉队列树
```

---

## 1. 限的是什么、不限什么

| | |
| --- | --- |
| **限** | 本机**出向**（发出去的）全部流量，所有网卡、所有 IP 合计一份额度 |
| **不限** | 入向。见 §7 |
| **不区分** | 源 IP、目的地址、端口、进程。整机一个总闸门，不做任何分类 |
| **例外** | 免限端口（默认 SSH 22），走一条不整形的旁路 |

"不做任何分类"是这套方案最大的省事之处：按端口/按 IP 分类会带来一整串
麻烦（分类器的进制、临时端口撞车、每增删一个对象就要重建队列树），
而整机限速一个都不沾——受限流量就是 HTB 的兜底类，没被免限规则挑走的
全部落进去。

---

## 2. 两种机器形态

需求里点名要对付的两种，处理方式差别很大：

### 2.1 单网卡多 IP

一张物理网卡上绑了一堆地址（云主机加弹性 IP 的常态）。

**地址有几个对限速树毫无影响。** 整机限速不按 IP 分类，10 个地址和 1 个
地址走的是同一个闸门，生成的命令一模一样。所以这种形态就是最简单的那条
路：HTB 直接挂在那张网卡上，没有任何额外机制。

```
eth0 (10.0.0.5, 10.0.0.6, 10.0.0.7, 2001:db8::5)
  └── HTB root
        ├── 1:1  免限类（100 Gbit，实际不整形）← SSH
        └── 1:2  整机限速类 = 总额度        ← 其余全部（htb default）
```

### 2.2 多网卡多 IP

几张网卡，每张各带若干地址。**这里有一个必须说清楚的坑：**

> **每张网卡各挂一棵 HTB = N 份额度，总量变成 N 倍。**
> 而且每张网卡单独看都限得好好的，`tc -s class show` 一切正常——
> 这是最难在生产上发现的那类错。

把总额度除以 N 也不行：流量在网卡之间从来不是均分的，除完的结果是某张
网卡先被掐死，而整机总带宽远没用满。

正确做法是把各网卡的出向**先汇聚到一个 IFB 虚拟设备**，HTB 挂在 IFB 上，
这样是**一份令牌桶服务所有网卡**：

```
eth0 ─┐
eth1 ─┼─ clsact egress + matchall + mirred redirect ─> ifb0 ── HTB ──> 各自的线路
eth2 ─┘
```

- `clsact` 只提供收发两侧的钩子，**不接管排队**——原网卡上仍然是默认的
  `pfifo_fast`，整形只发生在 IFB 上；
- `matchall` 匹配一切，不看任何字段，**因此与源 IP 无关**——多 IP 在这
  一层同样是透明的。

工具自动判断走哪条路：`netlimit status` 里那句"直接挂在网卡上 / 经 IFB
聚合"就是判断结果。**只有一张网卡时不会引入 IFB**——多一层重定向就多一处
可能出错，能不用就不用。

---

## 3. 哪些网卡会被限

自动发现，规则写死在 `netlimit/discover.py`。默认排除的每一条都有具体
理由——**限错网卡的后果不是限速不准，是把容器网络或回环流量一起掐住**：

| 排除 | 理由 |
| --- | --- |
| `lo` | 限它等于限本机进程之间的通信，纯粹的自伤 |
| `ifb*` | 我们自己用来聚合的设备。限它 = 整形后的流量再整形一遍 |
| `docker*` / `br-*` / `veth*` | 容器流量出公网时还要过物理网卡，在这里再限一次 = **同一份字节限两遍** |
| `virbr*` / `vnet*` | libvirt 的网桥与虚机 tap，同上 |
| `tun*` / `tap*` / `wg*` | 隧道内的包出去时还会过物理网卡，同上 |
| bond/team 成员口 | 调度发生在主设备上；两个成员各限一份 = 两倍额度。名字上看不出来，靠 `/sys/class/net/X/master` 判断 |
| `down` 的网卡 | 不承载流量 |
| 没有任何地址的网卡 | 同上。链路本地地址（`169.254.*`、`fe80::`）不算数——否则一张什么都没配的网卡会因为自带 `fe80::` 被判成"在用" |

自动判断再周全也有猜错的时候，所以留了手动出口：

```bash
netlimit --only eth0 --only eth1 apply -r 1000   # 只限这两张，绕过全部自动判断
netlimit --exclude eth2 apply -r 1000            # 在自动发现之外再排除
```

`netlimit status` 会把**每一张**网卡连同它被跳过的理由都列出来——不用去
猜工具到底限了什么。

---

## 4. 默认不限速

不给 `-r/--rate`（或配置文件里 `NETLIMIT_MBPS` 留空）的含义是**不限速**：
网卡上不会有任何 tc 队列树，流量按线速走。新装的机器开箱就该能跑满，
要限的时候再给一个值。

**留空与填 0 是两件不同的事**：

| 额度 | 含义 | 行为 |
| --- | --- | --- |
| 留空 | 没设 → 不限速 | 不建队列树；已有的会被拆掉 |
| 正数 | 整机闸门 | 建那棵固定的两类树 |
| 0 或负数 | **配错了** | 直接拒绝，一条命令都不发 |

为什么要把 0 单独判成错误：0 Mbps 谁也跑不动，写 0 的人显然不是想"不限
速"，而是填错了。如果用 0 兼表"没设"，那"我配了限速但把额度打错一个字"
就会**静默变成不限速**——静默不限速是这类工具最不能接受的故障。

---

## 5. 改额度不打断连接

只改额度走 `tc class change`，**不重建队列树、不打断任何连接**：

```bash
netlimit apply -r 2000     # 从 1000 改到 2000，存量连接立刻跟上
```

整机这个总闸门被调整的频率只会比单个业务更高（扩容、削峰、临时放行），
每次都重建的话就是每次调额度都抖一下全机流量。

下发是**幂等**的：已经是目标状态时**一条命令都不发**。所以让 systemd
timer 每分钟跑一次没有代价（见 §6）。

## 6. 装成开机自动生效

```bash
pip install /path/to/repo
cp deploy/netlimit/netlimit.conf.example /etc/netlimit.conf   # 改 NETLIMIT_MBPS
cp deploy/netlimit/netlimit.{service,timer} /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now netlimit.service netlimit.timer
```

服务是 `Type=oneshot` + `RemainAfterExit`：限速是**内核状态**，不是一个
要常驻的进程。下发完就退出，限速继续生效——**这个服务挂了不影响已经生效
的限速**。

`ExecStop` 刻意是空操作：机器上的限速不该因为一次 `systemctl stop` 就
消失（那等于悄悄放开了带宽）。要关就显式 `netlimit off`。

### 为什么还要配一个 timer

一次性下发有两个盖不住的洞：

1. **后插的网卡不会被限住。** 热插网卡、云上加弹性网卡、某张网卡从
   `down` 变 `up`，都会多出一条完全绕过限速的出口。
2. 有人手工 `tc qdisc del` 了，或别的工具重建了根 qdisc。

第 1 条是**本方案最危险的失效方式**：这时 IFB 上的队列树看起来一切正常，
`tc -s class show` 也正常——**看起来限着，其实漏了一整张网卡**。所以
`netlimit apply` 在多网卡形态下会**逐张网卡**核对重定向还在不在，缺了就
重建；timer 让这个核对周期性发生。

---

## 7. 为什么不限入向

入向没法真正"整形"。包已经到了本机网卡，带宽早就被占用过了；能做的只有
丢包（`police`）或者用 IFB 把入向重定向后排队——前者靠丢包触发对端降速，
精度差且对 TCP 不友好，后者的队列建在**收到之后**，省不下已经发生的
链路占用。

出向则是天然合适的：本机是发送方，`tc` 直接控制发包节奏，既准确又没有
额外损耗。

---

## 8. 口径：限的是链路层字节

tc 数的是**网卡上真实跑的比特数**，含以太网/IP/TCP 头部与重传；应用层
看到的吞吐会略低。本仓库实测过这个差值：**5.2%~5.8%**（32 MB 应用层
载荷 → 网卡上 33.66 MB / 33.87 MB）。

这与带宽采购、95 计费的口径是一致的（卖的就是链路上的比特），所以默认
不做补偿。**注意它随 MTU 与包大小变**，不是常数。

---

## 9. 未验证的部分（重要）

**本仓库的开发机内核什么都没有**，以下全部是确定的（读 `/proc/config.gz`，
不是猜）：

```
# CONFIG_NET_SCH_HTB is not set        限速本身
# CONFIG_IFB is not set                多网卡聚合
# CONFIG_NET_ACT_MIRRED is not set     重定向
# CONFIG_NET_CLS_MATCHALL is not set   匹配全部出向包
# CONFIG_NET_CLS_U32 is not set        免限端口
# CONFIG_MODULES is not set            ← 连模块机制都关了，无法事后加载
```

所以**没有经过实测**的是：

- 限额准不准（打满时的实测速率 vs 配置值）、`burst`/`cburst` 取值是否合适；
- **多网卡聚合是否真的成立**。它依赖一条内核行为：出向重定向到 IFB 之后，
  IFB 把包重新发出去时**不会再次触发同一条重定向规则**（否则就是死循环）。
  按 ifb 驱动的实现这是成立的，但本仓库没有条件验证；
- `tc class change` 改额度时存量连接的实际表现。

**已经验证过的**是：

- 生成的每一条命令都通过了 iproute2 的用户态参数解析（真 `tc` 跑过，
  只在 netlink 那步失败）——上一个项目正是在这一步逮到过 `invalid class
  ID`（tc 的 ID 按十六进制解析）；
- 网卡发现的全部排除规则、单/多网卡的架构分叉、命令生成、收敛的四条
  路径（无变化 / 只改额度 / 重建 / 拆除），单元测试覆盖，且逐条做过变异
  验证；
- 转发流量确实经过出口网卡的根 qdisc（见
  [docs/10 §8](10-LVS-IPVS可行性.md) 的实测）。

### 上线前请先做这三步

```bash
netlimit doctor                      # 内核前提。缺什么会直接说清楚
netlimit plan -r <额度>              # 干跑，看命令对不对
netlimit apply -r <额度> && netlimit status
```

然后压一次实测：打满出向，看实际速率是否贴着限额（差 3%~8% 是口径差，
正常）。**多网卡形态下务必确认总量而不是单张网卡的量**——这正是最容易
出错的地方。
