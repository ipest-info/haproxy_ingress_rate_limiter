# 限速方案：从 HAProxy bwlim 迁到内核 tc

本文说明为什么把限速从 HAProxy 的 `shared bwlim` 换成内核 tc（HTB）、
怎么实现的、行为上有哪些差异，以及**哪些部分还没被验证过**。

---

## 1. 为什么换

一句话：**bwlim 会让 HAProxy 完全失去零拷贝转发能力，同样的流量要多花
一倍 CPU。**

TCP 高带宽代理最重要的优化是内核 splice——数据在内核里从一个 socket 直接
搬到另一个，不进用户态。实测（HAProxy 2.8.16）：

| 场景 | 出向字节 | 其中走 splice 的 |
| --- | --- | --- |
| bwlim + `option splice-response` | 74867160 | **0** |
| 无 bwlim | 131073235 | 131072000 |
| 不开 splice | 131073225 | 0 |

道理说得通：限速要按字节计量并延迟发送，数据必须经过用户态。所以只要挂了
bwlim 滤镜，写不写 `option splice-*` 都没有意义——写了不报错也不生效。

代价用同吞吐对照量化（客户端限速到 2000 Mbps，两种配置传同样多的字节，
各测两次）：

| 方案 | HAProxy CPU | CPU 秒/GB | splice |
| --- | --- | --- | --- |
| bwlim 限速 | 14~16% | 0.56~0.63 | 0% |
| 无 bwlim + splice | 8% | 0.32~0.33 | 100% |

**HAProxy 侧 CPU 减半。**

> 这组数据是在**低并发**（1~16 连接）下测的。并发升高后 splice 的优势会
> 因为内核管道池的上限而衰减——必须配套调 `maxpipes`，见第 5 节。

> 口径要说清楚：上表测的是 **HAProxy 进程**的 CPU。tc 自身的整形开销发生在
> 内核 softirq 上下文里，不计入该进程，本项目**没有测过**（原因见第 9 节）。
> 因此正确的说法是"HAProxy 侧 CPU 减半"，不是"整机 CPU 减半"。

顺带还解决了 bwlim 方案一个固有的别扭之处，见第 4 节。

## 2. 怎么把"按 frontend 限速"映射到 tc

tc 作用在网卡上，不认识 frontend。但有一个天然的对应关系：**HAProxy 发给
客户端的数据包，源端口就是该 frontend 的监听端口**。于是在出方向网卡上按
源端口分类即可：

```
tc qdisc  add dev eth0 root handle 1: htb default 1
tc class  add dev eth0 parent 1: classid 1:1    htb rate 100Gbit          # 兜底类，不整形
tc class  add dev eth0 parent 1: classid 1:1f90 htb rate 40000000bit \
                                                ceil 40000000bit burst 50000
tc qdisc  add dev eth0 parent 1:1f90 handle 1f90: fq_codel                # 类内公平
tc filter add dev eth0 protocol ip   parent 1: prio 1 u32 \
                                     match ip  sport 8080 0xffff flowid 1:1f90
tc filter add dev eth0 protocol ipv6 parent 1: prio 1 u32 \
                                     match ip6 sport 8080 0xffff flowid 1:1f90
```

注意 8080 在上面出现了两种写法：**tc 的 ID（classid / handle）是十六进制**
（0x1f90 = 8080），而 u32 的 `match ... sport` 是十进制。这不是笔误，是 tc
自己的约定，下一条会讲为什么它值得单独说。

几个设计取舍：

- **classid 次要号直接取监听端口，且必须按十六进制写。** 端口在本模型里
  天然唯一（一个 frontend = 一个监听端口），因此 classid 稳定，不需要额外
  的分配表——增删 frontend 不会让别人的 classid 漂移，reconcile 才能做到
  "只改速率不重建"。次要号 1 留给兜底类，因此拒绝监听 1 端口。

  **进制这件事踩过一次，值得记下来。** iproute2 解析 classid 用的是
  `strtoul(str, &p, 16)`（`lib/utils.c` 的 `get_tc_classid`），qdisc 的
  handle 同理。按十进制拼的话：

  ```
  tc class add ... classid 1:14223 ...
  Error: argument "1:14223" is wrong: invalid class ID
  ```

  因为 14223 被当成 0x14223 = 82467，超出次要号的 16 位上限。边界正好在
  **端口 10000**：1–9999 的十进制串碰巧也是合法十六进制（0x9999 = 39321
  < 0xFFFF），所以看着"能用"——但它落到的次要号并不是端口本身，只是写进去
  和读出来恰好自洽。**10000 以上的端口全部下发失败，那些 frontend 根本
  没有限速。**

  同一个坑有两处：`classid` 和叶子 qdisc 的 `handle`。后者更阴，它是非致命
  命令，失败只记一行日志，表现为"限速在跑但类内没有公平队列"。当时的单测
  全用 8080 做样例——正好落在能蒙混过关的区间，所以一条都没红。现在的回归
  测试改成按规则断言（凡 tc 的 ID 位置都必须是 ≤4 位十六进制且能读回端口），
  并覆盖 2 / 443 / 9999 / 10000 / 14223 / 65535 这些边界端口。
- **必须有兜底类。** 没被 filter 匹配的流量（SSH、监控、连后端的方向）走
  `1:1`，按 100 Gbit 放行 = 实际不受约束。少了它，一开限速整台机器的其它
  流量都会被拖下水。
- **IPv4 与 IPv6 各一条 filter。** 只写 IPv4 的话，客户端走 IPv6 进来时限速
  会整个失效——这类"静默不生效"是本项目最不能接受的故障。
- **叶子挂 fq_codel。** 同一 frontend 内各连接公平排队，避免单条连接把该类
  的队列占满。老内核没有这个 qdisc 时**不致命**：缺了只是失去类内公平性，
  限速本身照常。

实现见 [`rl_limiter/tcshaper.py`](../rl_limiter/tcshaper.py)。

## 3. reconcile 的三条路径

按"对流量的打扰程度"从小到大：

| 情况 | 动作 | 对流量的影响 |
| --- | --- | --- |
| 完全一致 | 一条命令都不发 | 无 |
| 只有速率不同 | `tc class change` | **无**，存量连接立刻跟上 |
| 结构不同（增删 frontend、被人手工改过、首次运行）| 整棵重建 | 重建窗口内极短暂不整形 |

第一条尤其重要：周期兜底每 30 秒跑一次，如果不做"一致就不动"的判断，就会
每 30 秒重建一次队列树、每 30 秒抖一次流量。

与 enforcer 一样，空清单**拒绝执行**——那意味着撤掉全部限速，是事故而不是
配置操作。

## 4. 与 bwlim 的行为差异（都要向运维讲清楚）

### 4.1 改限额不再需要 reload —— 这是个改进

| | bwlim | tc |
| --- | --- | --- |
| 改限额的动作 | 改 cfg + reload HAProxy | `tc class change` |
| 新建连接 | 立刻按新限额 | 立刻按新限额 |
| **存量连接** | 保持旧限额，直到 `hard-stop-after` 宽限期结束被断开重连 | **立刻按新限额** |

bwlim 下"限额调整对存量长连接生效"要靠 `hard-stop-after` 把旧 worker 连同
它的连接一起强停，客户端重连才拿到新限额。tc 直接改队列的令牌速率，存量
连接无感知地跟上，连接不断。

监听端口、后端服务器的变更仍然要改 cfg + reload——那是 HAProxy 的固有约束，
与限速方案无关。

### 4.2 口径变了：链路层 vs 应用层

bwlim 数的是**应用层字节**；tc 数的是**链路层字节**，含以太网/IP/TCP 头部
与重传。同样填 40 Mbps，tc 方案的应用层吞吐会略低（头部开销典型 3%~8%）。

要抵消可以给 class 加 `overhead` / `linklayer` 参数。本项目默认不加——把
"限的是网卡上真实跑的比特数"作为口径更贴近计费与带宽采购的实际含义。

**注意**：监控侧仍然读 HAProxy 的 `bytes_out`（应用层口径），所以控制台上
的实测速率会略低于 tc 的限额值。这不是限速失效。

### 4.3 作用范围更宽

bwlim 只管这个 frontend；tc 管的是网卡出方向**按源端口匹配到的全部流量**。
如果同一端口上还有非 HAProxy 的流量（不该有），也会一起被限。

## 5. 高并发下的关键参数：`maxpipes`

第 1 节那组"CPU 减半"是在**低并发**（1~16 连接）下测的。并发升高后结论会
变，因为 splice 是"每条在传的连接借一个内核管道"，而管道来自一个有上限的
池——HAProxy 默认 `maxpipes = maxconn / 4`。

固定总吞吐 2000 Mbps、只变并发数（maxconn 1400，故默认 maxpipes 350）：

| 并发 | 不开 splice（CPU 秒/GB）| 开 splice（CPU 秒/GB）| splice 占比 | 优势 |
| --- | --- | --- | --- | --- |
| 50 | 0.74 | 0.33 | 100% | 2.2× |
| 200 | 0.83 | 0.38 | 100% | 2.2× |
| 600 | 0.89 | 0.61 | **62%** | 1.5× |

600 并发时管道池不够用了，splice 覆盖率跌到 62%，优势从 2.2× 缩到 1.5×。
注意两点：**CPU 秒/GB 本身也随并发上升**（0.74→0.89 / 0.33→0.61），说明
每连接确实有独立于字节数的成本；而 splice 的优势是随并发**衰减**的。

把管道池调大能补回来（maxconn 800、600 并发、目标 2000 Mbps）：

| `maxpipes` | 吞吐 | CPU 秒/GB | splice 占比 |
| --- | --- | --- | --- |
| 200（= 默认 maxconn/4）| **1730 Mbps** | 0.69 | 42% |
| 700 | **1995 Mbps** | 0.45 | 100% |

默认值下**连目标吞吐都跑不到**，不只是 CPU 高一点。因此本项目显式设
`maxpipes = maxconn`——带宽代理的连接绝大多数都在实打实地传数据。

代价是 FD：

```
FD 需求 = maxconn × 2 + maxpipes × 2 + 34
```

实测逐项核对（`maxconn 100000`）：`maxpipes` 25000 → 250034，
50000 → 300034，100000 → 400034。所以 compose 的 `ulimits.nofile` 设成了
524288。管道是按需从池里取的，不用就不占，上限只是上限。

**怎么判断 maxpipes 够不够**（不要靠猜）：压测峰值时看 stats socket，

```bash
echo "show info" | socat - /run/haproxy/admin.sock \
    | grep -E "TotalBytesOut|TotalSplicedBytesOut"
```

`TotalSplicedBytesOut / TotalBytesOut` 明显低于 100% 就说明池不够。

## 6. 单网卡还是两网卡？

**结论：默认单网卡就够，前提是监听端口不落在本机的临时端口范围内
（`/proc/sys/net/ipv4/ip_local_port_range`，典型 32768–60999）。**
80/443/8080 这类正常的入口端口天然满足，无需任何额外工作。

### 为什么这个前提是硬性的

本方案的分类规则只匹配**源端口**：

```
tc filter ... u32 match ip sport 8080 0xffff flowid 1:1f90
```

HAProxy 发给客户端的包，源端口确实是监听端口。但**HAProxy 连后端的包，
源端口是内核从临时端口范围里分配的**——单网卡时它们从同一张网卡出去。
一旦某次连后端抽到的临时端口正好等于某个 frontend 的监听端口，那条连接
的出向流量就会被误判进该 frontend 的限速类，吃掉本该给客户端的配额。

这个故障**随机偶发、极难排查**：表现是限速偶尔莫名收紧，重启就好一阵。
因此 rl-limiter 启动时会检查并告警（见 `tcshaper.ephemeral_conflicts`）：

```
以下 frontend 的监听端口落在本机临时端口范围内，**单网卡部署时限速可能
偶发失准**…… 两条出路：把监听端口挪到 32768 以下，或用两张网卡……
```

只告警不阻断——两网卡部署下监听端口落在临时范围内是完全安全的（后端流量
根本不经过被限速的那张网卡），一刀切拦住反而不对。

### 两网卡在什么时候更合适

| 情况 | 说明 |
| --- | --- |
| 监听端口无法避开临时端口范围 | 从物理上消除上面那个歧义 |
| 客户端下行与后端上行会互相挤 | 单网卡上两个方向共享同一份 TX 能力；限速只管客户端侧，后端流量走兜底类不受限，高负载时会争带宽 |
| 公网 / 内网需要物理分区 | 安全分区本来就该分网卡，限速口径顺带变干净 |
| 想让整机包统计只反映客户端侧 | 实例视图的 `RL_NIC` 计数是整机口径，单网卡时混入后端流量 |

两网卡时的配置：`RL_TC_IFACE` 指向**客户端侧**那张网卡即可，后端侧那张
不做任何 tc 操作。`RL_NIC` 默认跟随 `RL_TC_IFACE`，也就自动只统计客户端侧。

### 单网卡的好处（也别忘了）

- 云上大多数 ECS 就是一张弹性网卡，加网卡要动 VPC/路由/安全组；
- tc 树只有一份，`tc_check.py verify` 与排障对象唯一；
- 只要监听端口 < 32768，前面那个歧义根本不存在。

### 两网卡也解决不了的一件事

**HTB 作为 root qdisc 会把该网卡的全部 TX 串行化到一个 qdisc 锁上**，
高包速率时这是已知瓶颈。两张网卡只是把一个锁变成两个，客户端侧那张仍然
是单锁。常规的缓解手段是 `mq` 根 qdisc + 每硬件队列一个 HTB，但那样
**每个队列各有一份限额，聚合限速就不成立了**（N 个队列 = N 倍限额）——
与本项目"限的是该端口的总速率"这个核心语义直接冲突，不能用。

> 这一段是**推理，不是实测**：本沙箱内核没有 HTB，没法压出 qdisc 锁的
> 拐点在哪。32 核 + 高包速率的场景上线前值得专门压一次，见第 9 节。

## 7. 部署要求（三个前提，缺一个限速就静默失效）

1. **容器里要装 `iproute2`**（镜像已装）。
2. **容器要有 `CAP_NET_ADMIN`**：compose 里 `cap_add: ["NET_ADMIN"]`（已配）。
   裸机 systemd 下 root 运行即可，或给 `AmbientCapabilities=CAP_NET_ADMIN`。
3. **内核要有 HTB 调度器（`sch_htb`）**。装了 iproute2 不代表内核带它——
   精简内核（容器优化型发行版、部分云厂商镜像）经常把 `net/sched` 裁掉，
   届时 tc 会报 `Specified qdisc kind is unknown`，限速同样是静默失效。

这三条在容器入口脚本里**逐条实测**，缺哪个说哪个然后拒绝启动
（见 `deploy/docker/node-entrypoint.sh` 的 `tc_selfcheck`）。宁可起不来，
也不能让人以为限住了、实际没限。

相关环境变量：

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `RL_TC_IFACE` | 自动探测 | 在哪张网卡上限速。不设则取默认路由的出口网卡；多网卡机器必须显式指定；探测不出来**直接启动失败**（不装作在限速）。设 `-` 明确关闭限速，只保留监控与配置下发 |

与 `RL_APPLY_RELOAD_CMD` 同理，这一项**只能来自本机环境变量、绝不从配置库
读**——它决定了以 root 权限操作哪张网卡。

## 8. 怎么检查 tc 到底有没有在限

限速静默失效是本项目最不能接受的故障，所以配了一个专门的检查工具
[`tools/tc_check.py`](../tools/tc_check.py)，三个子命令对应三个时机：

```bash
# 上线前：只打印将要执行的 tc 命令，一条都不执行（可以直接 diff 给同事看）
python3 tools/tc_check.py plan -c /etc/rl-limiter/config.yaml -i eth0

# 部署时：逐条实测三个前提，缺哪个说哪个
python3 tools/tc_check.py doctor -i eth0

# 运行中：读回网卡实况，与配置逐条核对
python3 tools/tc_check.py verify -c /etc/rl-limiter/config.yaml -i eth0
```

`doctor` 的输出形如（这是在一台内核缺 HTB 的机器上跑出来的真实结果）：

```
限速前提体检：
  [ok]   tc 已安装
  [ok]   有 CAP_NET_ADMIN（能操作网络设备）
  [FAIL] 内核支持 HTB 调度器（sch_htb）
         → 宿主机 modprobe sch_htb；内核没编译该模块则需换内核
  [ok]   网卡 eth0 存在
体检结论：**有失败项，限速不会生效**
```

`verify` 会逐个 frontend 核对三件事：限速类在不在、速率对不对、**分类规则
在不在**。第三条容易被忽略——类建好了但 filter 丢了，流量根本进不了这个类，
`tc class show` 看着一切正常，实际等于没限速。

不装工具也能手查，就三条只读命令：

```bash
tc -s qdisc show dev eth0     # 队列树整体，-s 带统计（发送/丢弃字节数）
tc -s class show dev eth0     # 各 frontend 的类：rate/ceil 与实际发送量
tc filter show dev eth0       # 分类规则：sport → flowid 的对应
```

看 `tc -s class show` 时重点看两处：`rate` 是否等于配置的 `quota_mbps`×1e6；
类的 `sent` 计数是否在涨——不涨说明流量没被分类进来（filter 有问题）。

## 9. 未验证的部分（重要）

**本项目的开发沙箱内核只内建 `pfifo`，`htb`/`tbf`/`hfsc` 全部不可用，也没有
内核模块可加载。**因此以下内容**没有经过实测**：

- tc 的实际整形效果（限额准不准、burst 取值合不合适）；
- tc 自身的 CPU 开销（softirq 侧）；
- `tc class change` 改限额时存量连接的实际表现；
- 高并发下 HTB 的扩展性：HTB 作为 root qdisc 会把该网卡的 TX 串行化到
  一个 qdisc 锁上，**拐点在多少包速率上没有实测**（第 6 节末尾那段是推理）；
- 单网卡下临时端口撞监听端口造成的误分类：机制清楚、检查已加，但**没有
  在真机上复现过**。

已经验证过的是：

- bwlim 关闭 splice、以及移除 bwlim 后 CPU 减半（第 1 节全部数据）；
- 受管区块不再渲染任何限速指令、且能开 splice（真实 HAProxy 校验 + 实跑，
  splice 占比 100%）；
- tc 命令序列的生成与 `tc class/filter show` 输出的解析（单元测试，用假
  runner，覆盖空清单/端口冲突/只改速率/结构变化/各类失败路径）；
- 入口脚本的三项前提自检确实能识别缺失（沙箱内核缺 HTB，自检如实报错）；
- `tools/tc_check.py` 的 `plan` 与 `doctor` 已实跑（`doctor` 如实报出本沙箱
  缺 HTB）；`verify` 因为建不出 HTB 队列树，**只跑过"树不存在"这条分支**。

**上线前必须在一台有 HTB 的机器上做一次真实压测**，至少确认：限额是否准确
（打满时实测速率 vs 配置值）、burst 取值是否合适（太小达不到限额、太大则
秒级限速失真）、以及改限额时存量连接是否真的立刻跟上。

---

## 10. 回退

若 tc 方案在生产上出问题，回退到 bwlim 只需：

1. `RL_TC_IFACE=-` 关闭 tc 限速；
2. `tc qdisc del dev <网卡> root` 清掉已建的队列树；
3. 切回本次改动之前的分支（`claude/haproxy-high-throughput`），那里
   `enforcer.render_block` 仍然渲染 bwlim。

两套方案在配置模型（`quota_mbps`）上完全一致，配置库不需要任何改动。
