# 11 发布与安装（二进制）

目标机**不需要 Python**：发布物是 PyInstaller 单文件二进制
（`rl-limiter` + `rl-fleet`），连同配置模板、安装脚本打成一个 tar.gz。

## 1. 命名规则

| 对象 | 规则 | 示例 |
| ---- | ---- | ---- |
| git tag | `v<主>.<次>.<补丁>`，语义化版本，**必须等于 pyproject.toml 的 version**（CI 校验，不一致构建直接失败）；预发布加 `-rcN` | `v0.6.0`、`v0.6.0-rc1` |
| Release | 与 tag 同名（CI 自动创建，`-rc` 自动标 prerelease） | `v0.6.0` |
| 发布包 | `rl-limiter-<tag>-linux-<架构>.tar.gz` + 同名 `.sha256`；另附 `install.sh` | `rl-limiter-v0.6.0-linux-x86_64.tar.gz` |

版本号怎么升：

- **补丁**：修 bug、文案，配置与接线完全兼容；
- **次**：新功能（新页面/新字段/新进程），旧配置原样可用；
- **主**：配置或接线有不兼容变更（启动时会给迁移指引的那种）。

## 2. 发布流程（维护者）

```bash
# 1. 确认 pyproject.toml 的 version 已是要发的号；
# 2. 打 tag 推上去，CI（.github/workflows/release.yml）自动构建发布：
git tag v0.6.0
git push origin v0.6.0
```

推不了 tag 时（如受限的会话环境），在 Actions 页对 `release` 工作流
Run workflow，输入新 tag：工作流按所选分支 HEAD 构建，并在**该提交**
上创建 tag 与 Release。

CI 在 manylinux2014 容器（glibc 2.17）里构建——**CentOS 7 / RHEL 7
及之后**的发行版都能直接跑产物。Release 附件：发布包 + `.sha256`，
外加单独的 `install.sh`（下面"一条命令"用的就是它）。本地手工构建
（调试用；兼容性只到构建机同代系统）：

```bash
deploy/release/build.sh        # 产物在 dist/，版本取 pyproject.toml
```

## 3. 安装（运维）

先拿到安装脚本（从最新 Release 的附件下载）：

```bash
curl -fL -o install.sh https://github.com/ipest-info/haproxy_ingress_rate_limiter/releases/latest/download/install.sh
chmod +x install.sh
```

### 3.1 节点（每台服务器一个 rl-limiter）

```bash
sudo ./install.sh --download \
    --token <节点令牌> --client-nic ens33 --backend-nic ens34
```

| 选项 | 写到 `/etc/rl-limiter/rl-limiter.env` | 默认 |
| ---- | ---- | ---- |
| `--token <令牌>` | `RL_API_TOKEN`：节点写 API 令牌，总控登记该节点时填同一个值 | 不设 = 写 API 禁用（总控无法向它下发） |
| `--client-nic <网卡>` | `RL_TC_IN_IFACE`：客户端侧网卡 = 入向限速执行网卡 | `eth0`（出厂约定） |
| `--backend-nic <网卡>` | `RL_BACKEND_IFACE`：后端服务侧网卡 | `eth1`（出厂约定） |

安装前的硬检查（不通过则**拒绝安装、什么都不落盘**）：

- **双网卡**：本机物理网卡（`/sys/class/net/*/device` 存在的）少于两张
  不允许安装——节点形态的前提就是客户侧/后端侧两张卡（原理见
  [04 部署指南](04-部署指南.md) §2）。lo、网桥、veth 等虚拟设备不算；
- **两卡相斥**：客户侧与后端侧不能是同一张网卡（入向限速作用在客户
  侧，同一张卡会把后端回程流量一起卡住）。rl-limiter 启动时也会再校验
  一次，env 被手改成同一张卡时启动失败；
- **网卡存在**：两张卡都必须在本机存在。没给选项时按 eth0/eth1，命名
  不同（ens33/enp1s0…）的机器**必须显式指定**——不做自动猜测；
- **令牌格式**：至少 8 位，只含字母、数字与 `._~+/=-`（会写进 systemd
  EnvironmentFile）。生成一个：`openssl rand -hex 24`。

### 3.2 总控（rl-fleet，多机总量控制，见 [10 总控制台](10-总控制台.md)）

```bash
sudo ./install.sh --download --fleet --token <总控令牌>
```

`--fleet` 只装总控（`fleet.yaml`、`rl-fleet.env`、`rl-fleet.service`），
不装节点单元、**不查网卡**（总控不碰 tc）。`--token` 写进
`rl-fleet.env` 的 `RL_API_TOKEN`——这是总控**自己的**写令牌（页面改总
带宽、添加/删除节点用），与各节点令牌无关。控制台默认端口 8095。

装好后：`systemctl enable --now rl-fleet` → 打开 `http://<总控>:8095`
→ 页头填总控令牌 →「节点管理」页逐台添加节点（名称、节点控制台地址
`http://<节点内网地址>:8090`、该节点的令牌）。同一台机器既当节点又当
总控：两种安装各跑一次即可。

### 3.3 其它用法

```bash
sudo ./install.sh --download v0.6.0 ...   # 钉死版本（生产批量建议钉版本，一批机器装的一致）
sudo ./install.sh --token=<以-开头的令牌>  # 值以 - 开头时用 --opt=值 写法
./install.sh --help
```

`--download` 不带 tag 时跟随 `github.com/<仓库>/releases/latest` 的跳转
取最新版本（不走 api.github.com，没有匿名限流），只需能访问
github.com（下载会跳到 objects.githubusercontent.com）。参数与接线校验
都在下载**之前**做完；下载的临时目录用完即清。

手头已有发布包（离线环境）：

```bash
tar xzf rl-limiter-v0.6.0-linux-x86_64.tar.gz
cd rl-limiter-v0.6.0-linux-x86_64
sudo ./install.sh --token <令牌> --client-nic ens33 --backend-nic ens34
```

令牌会出现在命令行（shell 历史、`ps`）里；介意的话装完再编辑 env 文件
写令牌，然后 `systemctl restart`。

装了什么、不动什么：

| 路径 | 行为 |
| ---- | ---- |
| `/usr/local/bin/rl-limiter`、`rl-fleet` | 每次安装**覆盖**（升级就是重跑 install.sh + restart） |
| 节点：`/etc/rl-limiter/config.yaml`、`rl-limiter.env` | 首次从模板生成（网卡接线显式写入）；已存在**不覆盖**，只改命令行显式给出的项（令牌/网卡） |
| 总控：`/etc/rl-limiter/fleet.yaml`（空节点清单）、`rl-fleet.env` | 同上；`fleet.yaml` 之后由页面「节点管理」与总带宽编辑回写 |
| `/etc/rl-limiter/` 属组与权限 | 目录 `root:rl-limiter 2770`、yaml `660`、env `640`——服务用户能读配置、写 API 能原子回写；老版本装出来的 `640 root:root` 会被校正 |
| `/etc/systemd/system/rl-limiter.service`（`--fleet` 时为 `rl-fleet.service`） | 每次安装覆盖（权限模型与 venv 装法一致：专用用户 + CAP_NET_ADMIN） |

装完**不自动启动**：先核对配置（限额见 [03 配置参考](03-配置参考.md)），
再 `systemctl enable --now rl-limiter`（总控为 `rl-fleet`）。

升级：重跑 install.sh（可不带任何选项——令牌与接线保留在已有 env 里）
+ `systemctl restart`。老版本生成的 env 没有 `RL_BACKEND_IFACE` 时会
提示：加 `--backend-nic <网卡>` 重跑即写入。

### 3.4 卸载

```bash
sudo ./install.sh --uninstall                  # 卸载节点（配置保留，重装沿用）
sudo ./install.sh --uninstall --fleet          # 卸载总控
sudo ./install.sh --uninstall --purge          # 连该角色的配置一起删
```

卸载节点按这个顺序做（每步都打印做了什么）：

1. `systemctl disable --now rl-limiter`——**先停服务**，否则它的兜底
   reconcile 会把刚清掉的规则建回来；
2. **清网卡上的 tc 限速规则**：客户侧网卡的入向钩子（ingress qdisc）、
   IFB 设备（默认 `ifbrl0`，连同其上的整形树）；接了出向整形
   （`RL_TC_IFACE`）时再撤该卡的 HTB 根（只删 htb，不是我们建的不动）。
   网卡以 `rl-limiter.env` 里的接线为准。服务停了限速还在是刻意的
   （进程宕机不该让限速失效），所以卸载必须清——否则会留下一个没人管的
   冻结限速；
3. 删 systemd 单元；
4. 本机另一种角色（总控/节点）也没装了，才删 `/usr/local/bin/rl-limiter`、
   `rl-fleet`；
5. `--purge` 时删该角色的配置（节点 `config.yaml`、`rl-limiter.env`；
   总控 `fleet.yaml`、`rl-fleet.env`），目录空了一并删。

刻意保留：`/var/log/rl-limiter`（监控落盘，计费对账数据）与运行用户
`rl-limiter`，要清请手工（`rm -rf /var/log/rl-limiter`、
`userdel rl-limiter`）。卸载不查双网卡，也不需要发布包——拿单独的
`install.sh` 就能卸。

venv 装法的卸载是 `deploy/bare/rl-limiter.sh uninstall`（只删服务，tc
规则与 venv 保留，按它打印的提示手工清）。

## 4. 二进制装法与 venv 装法（deploy/bare）怎么选

| | 二进制（本篇） | venv（`deploy/bare/rl-limiter.sh`） |
| ---- | ---- | ---- |
| 目标机依赖 | 无（glibc ≥ 2.17 即可） | python3 ≥ 3.9 |
| 双网卡检查 | 有（不满足拒绝安装） | 有（前置检查 FAIL） |
| 升级 | 重跑 install.sh | 重跑装机脚本 |
| 卸载 | `install.sh --uninstall`（连 tc 规则一起清） | `rl-limiter.sh uninstall`（tc 规则手工清） |
| 适用 | 批量生产机、离线环境 | 开发机、想直接读改源码的环境 |

两种装法的配置路径、systemd 权限模型完全相同，可互相切换（配置不动，
换掉执行体即可）。
