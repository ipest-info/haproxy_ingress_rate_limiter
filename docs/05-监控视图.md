# 监控视图：可行性分析与实现说明

本文对照《监控视图说明》逐项分析**哪些指标 HAProxy 真的给得出来**，
给不出来的说清楚为什么，并记录已实现部分的数据来源与口径。

分析结论全部由**实测**得出（HAProxy 2.8.16-0ubuntu0.24.04.3，Ubuntu
24.04 stock 包），不是查文档推断的。实测手法在文末。

---

## 1. 一句话结论

需求文档共列出 22 条曲线。**18 条已实现**，4 条无数据源。

> **限速迁到内核 tc 之后，监听端口粒度的包统计从"做不到"变成了"做得到"。**
> tc 的每个 HTB 类正好对应一个 frontend，而 tc 天然统计每个类的发送包数、
> 丢弃包数与超限次数。原先判定不可行是基于 bwlim 方案（HAProxy 不统计包、
> 网卡计数无法按 frontend 拆），那个前提已经不成立了。
> 新增的两条是**监听端口每秒流出数据包数**与**每秒丢弃包数**，后者尤其
> 有价值——那正是被限速丢掉的包。

仍然无数据源的 4 条：

- **"每秒丢弃 bit 数"**（实例 2 条 + 监听端口 2 条）：tc、HAProxy、网卡
  三处都只统计"丢了多少个**包**"，没有任何地方统计"丢了多少字节"。
- **入方向的按 frontend 包统计**：tc 挂在**出**方向队列上，看不到入向；
  入向只有整机口径的网卡计数。

选择是**不画**这些曲线，页面上也不为它们保留说明块——取舍属于文档，
页面只呈现真有数据的东西。画一条恒为 0 的线比没有线更糟：看图的人会得出
"没有丢包"这个错误结论，而真相是"没有人统计过"。

## 2. 实例视图（tab 页）

### 2.1 连接视图

| 需求 | 数据源 | 状态 |
|---|---|---|
| 实例每秒新建连接数 | Σ frontend `conn_tot` 差分 | ✅ |
| 实例每秒丢失连接数 | Σ frontend (`dcon`+`dses`+`dreq`) 差分 | ✅ |
| 实例活跃连接数 | Σ frontend `h1_open_streams`（tcp 模式为 `scur`） | ✅ |
| 实例非活跃连接数 | Σ frontend (`h1_open_connections` − `h1_open_streams`) | ✅ |
| 实例并发连接数 | `show info` 的 `CurrConns` | ✅ |

**为什么"每秒新建连接数"不用 `show info` 的 `CumConns`。** `CumConns` 是
进程范围的累计连接数，它把 **rl-limiter 自己对 runtime API 的连接也算了
进去**——runtime socket 一次连接只服务一条命令，采集器每秒建两条
（`show stat` + `show info`），于是 `CumConns` 的差分恒有 +2 的底噪，
空载时曲线会稳稳停在 2/秒。实测佐证：同一时刻 `CumConns=256`，而各
frontend 的 `conn_tot` 之和只有 28，差额全部是采集器自己。改用
Σ `conn_tot` 后空载读数为 0。

**"丢失连接数"的口径。** HAProxy 没有"丢包"这个概念，一条连接要么被
它服务、要么被它主动拒绝。因此本项目把"丢失"定义为 HAProxy 明确拒绝的
连接：`dcon`（连接级拒绝）+ `dses`（会话级）+ `dreq`（请求级）。
`dresp` 是响应方向的拒绝（后端已经应答过了），不算连接丢失，不计入。

实测对应关系：`tcp-request connection reject` → `dcon`；
`tcp-request content reject` → `dreq`。

**"活跃 / 非活跃"的口径。** 有在途请求（流）的连接算活跃，建着但当前
没有在途请求的（HTTP keep-alive 空等）算非活跃。实测
`h1_open_connections` 与 `h1_open_streams` 这两列确实是**按 frontend**
统计的，可以直接相减。

只取 h1 是有原因的：stats CSV 里 h2 只有 `h2_open_connections` 和
`h2_backend_open_streams`——**前端方向的 open_streams 根本没有这一列**，
h3 连 open_connections 都没有。拿 h2 的连接数配 h1 的流数会把 h2 连接
全部算成空闲，比不算更糟。受管区块渲染出的 `bind` 不带 `alpn`，协商不到
h2/h3，因此本项目自己生成的 frontend 全部落在 h1 口径内。

`mode tcp` 下没有"流"的概念，每条连接就是一条数据通道，因此全部计为
活跃、非活跃恒为 0。

### 2.2 带宽视图

| 需求 | 数据源 | 状态 |
|---|---|---|
| 实例流入带宽 | Σ frontend `bin` 差分 | ✅ |
| 实例流出带宽 | Σ frontend `bout` 差分 | ✅ |
| 实例每秒流入数据包数 | `/proc/net/dev` `rx_packets` 差分 | ✅ 网卡口径 |
| 实例每秒流出数据包数 | `/proc/net/dev` `tx_packets` 差分 | ✅ 网卡口径 |
| 实例每秒丢失入包数 | `/proc/net/dev` `rx_dropped` 差分 | ✅ 网卡口径 |
| 实例每秒丢失出包数 | `/proc/net/dev` `tx_dropped` 差分 | ✅ 网卡口径 |
| 实例每秒丢失出 bit 数 | — | ❌ 无数据源 |
| 实例每秒丢失入 bit 数 | — | ❌ 无数据源 |

**为什么数据包统计只能来自网卡。** HAProxy 是 L4/L7 代理，它接触的是
字节流与连接，**从不接触数据包**。`show stat` 的 205 列里没有任何一列
是包计数，`show info` 也没有。唯一的来源是内核的网卡计数器。

这同时也是 rl-limiter 与 HAProxy **同机部署**（v0.4 起的形态）才拿得到
的数据——跨机监控只有一条 stats socket，看不到对端的 `/proc`。

**网卡口径必须标注清楚**（控制台上也标了）：

- 网卡计数是**整机**的，包含 HAProxy 之外的一切流量（SSH、备份、其它
  进程）；
- 网卡计数是**链路层**的，含以太网/IP/TCP 头部与重传，因此比 HAProxy
  的应用层字节数偏大（典型 3%~8%）；
- 网卡计数**无法按 frontend 拆分**（见第 3 节）。

因此实例视图上"HAProxy 带宽"与"网卡带宽"是两个数，本就不该相等；控制台
把它们分别标注为「HAProxy 应用层口径」与「网卡口径（整机）」。

**为什么"每秒丢弃 bit 数"做不了。** `/proc/net/dev` 的 drop 列只有
*包数*，没有字节数；HAProxy 侧连包都不统计，更没有"被丢弃的字节"。
唯一能凑出一个数的办法是"平均包长 × 丢包数"，那是编出来的估算值，不适合
放进运维面板。

多网卡机器上用环境变量 `RL_NIC` 指定要采样的网卡；不设则自动选默认路由
的出口网卡；设为 `-` 则明确禁用包统计（此时这几条曲线为空，其余监控
不受影响）。

## 3. 监听端口（frontend）视图

### 3.1 连接视图

| 需求 | 数据源 | 状态 |
|---|---|---|
| 监听每秒新建连接数 | `conn_tot` 差分 | ✅ |
| 监听每秒丢失连接数 | (`dcon`+`dses`+`dreq`) 差分 | ✅ |
| 监听活跃连接数 | `h1_open_streams`（tcp 模式为 `scur`） | ✅ |
| 监听非活跃连接数 | `h1_open_connections` − `h1_open_streams` | ✅ |
| 监听并发连接数 | `scur` | ✅ |

### 3.2 带宽视图

| 需求 | 数据源 | 状态 |
|---|---|---|
| 监听流入带宽 | `bin` 差分 | ✅ |
| 监听流出带宽 | `bout` 差分 | ✅ |
| 监听每秒流出数据包数 | tc 类的 `packets` 差分 | ✅ **tc 方案新增** |
| 监听每秒丢弃包数 | tc 类的 `drops` 差分 | ✅ **tc 方案新增** |
| 监听每秒流入数据包数 | — | ❌ tc 只看出方向 |
| 监听每秒丢失入包数 | — | ❌ tc 只看出方向 |
| 监听每秒丢失出/入 bit 数 | — | ❌ 只有丢包数，没有丢字节数 |

额外提供（文档没要求但对限速运维很有用）：**每秒触发限速次数**
（tc 类的 `overlimits` 差分）——限额吃不吃紧的最直接信号，比看带宽曲线
贴不贴限额线更灵敏。

**出方向的包统计怎么来的。** 限速迁到 tc 之后，每个 frontend 在网卡上
都有一个专属的 HTB 类（按源端口分类，见
[06-tc限速方案.md](06-tc限速方案.md)），而 tc 对每个类都统计发送字节、
发送包数、丢弃包数与超限次数。于是"按监听端口统计包与丢包"这件事第一次
成立——**这是限速方案换成 tc 之后白捡的监控能力**。

口径：链路层字节（含 IP/TCP 头），因此 tc 报的字节数会比同一 frontend 的
HAProxy `bytes_out` 略高，那是正常的，不是对不上。

**入方向仍然拆不了。** tc 挂在出方向队列上，看不到入向；要按 frontend 统计
入向包数得在 ingress 上挂 ifb 重定向，那会引入一整套与限速无关的复杂度，
本项目不做。入向包统计只在**实例**页按整机口径提供。

除文档要求外，监听端口的带宽图还额外画了两条本项目自有的曲线：**流出
10s 滑动均值**（计费与超限告警的承诺口径）与**限额参考线**。曲线被压在
限额线下即是限速生效的直接证据。

## 4. 采集链路与容错

每拍（1 秒）走三条独立的链路，**分开容错**：

| 链路 | 内容 | 失败时 |
|---|---|---|
| `show stat` | 各 frontend 的字节/连接/拒绝计数 | 主链路，整拍 fail-static + degraded |
| `show info` | 整机并发连接数、上限、空闲率 | 沿用上一拍，**不影响限速判定** |
| `/proc/net/dev` | 网卡包/丢包/字节计数 | 沿用上一拍，**不影响其余监控** |

分开的理由很实际：监控视图是"看"的，限速是"管"的。不能因为多画了几条
曲线，就让限速的判定链路多出几种失败方式。副链路的失败日志按错误内容
去重，只在首次出现时记一条 warning——它们每秒都会重试，不去重会把日志
刷没。

所有累计计数的差分都遵循同一套时序规则（与限速链路一致）：

1. **首拍只建基线**——只有一个累计值时无法差分；
2. **计数回绕沿用上一拍**——HAProxy reload 后计数从零重来，差分为负
   不可用，沿用上一拍的值并用新值重建基线；
3. **采样失败 fail-static**——沿用上一拍而不是骤降为零；
4. **frontend 确实不存在时归零**——"采不到"与"确实没有"必须区分，后者
   的真实值就是 0。

## 6. 实测记录

结论的实测依据（HAProxy 2.8.16）：

**stat 列集合**：`show stat -1 1 -1` 的表头共 205 列。逐列检查确认无任何
包计数列；`mode`、`conn_tot`、`dcon`、`dses`、`h1_open_connections`、
`h1_open_streams` 均存在，h2 只有 `h2_open_connections` 与
`h2_backend_open_streams`，h3 两者皆无。

**拒绝计数**：起一个 `tcp-request connection reject` 的 frontend，连
10 次 → `dcon` = 10；换成 `tcp-request content reject` → `dreq` = 10。

**活跃/空闲**：`mode http` 的 fe_a 上开 8 条 keep-alive 连接、其中 4 条
有在途请求 → `scur=8, h1_open_connections=8, h1_open_streams=4`；
另一个 3 条全在途的 fe_b → `3, 3, 3`。

**端到端**（本次实现后的整链验证）：两个受管 frontend（http 40 Mbps /
tcp 16 Mbps）+ 一个手写的 reject frontend，压测下读数为

```
实例 并发=23 活跃=18 非活跃=5 新建/s=… 丢失/s=40.0 出=55.19 Mbps
网卡 lo 入包/s=2049 出包/s=2049 丢包 0/0
fe_http 并发=17 活跃=12 非活跃=5 出=39.78 均值=39.87 限额=40.00
fe_tcp  并发=6  活跃=6  非活跃=0 出=15.41 均值=15.88 限额=16.00
```

其中：活跃/非活跃的拆分与实际开的 5 条空闲 keep-alive 连接吻合；
tcp 模式的非活跃恒为 0 符合预期；丢失连接数来自那个**不受管**的
reject frontend，验证了实例汇总确实覆盖全部 frontend 而不只是受管的
那些；两个受管 frontend 的实测带宽都被压在限额之下。
