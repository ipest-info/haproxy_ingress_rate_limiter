# 双网卡形态：请求方向（入向）限速

本分支在原有"响应方向限速"（quotas → 出向 tc/HTB）之外，增加**请求
方向**的限速：客户端打进 HAProxy 的流量，在**客户端侧网卡的入向**用
tc police 按监听端口限制。部署前提是**双网卡**：一张面向客户端
（请求进、响应出），一张面向后端。

## 1. 它限的是什么

| 配置项 | 限的东西 | 内核机制 |
| --- | --- | --- |
| `request_limits.<名>.mbps` | 该端口**入向字节速率**（客户端上行/请求体） | ingress + u32 按 `dport` 分类 + police，超额丢包 |
| `request_limits.<名>.conn_rate` | 该端口**每秒新建连接数**（SYN 速率） | ingress + flower 匹配 TCP SYN + police 包速率 |

两点口径上的诚实说明：

- **入向没有整形队列**。出向 HTB 是"排队慢放"，入向 police 只能
  "超了就丢"，靠 TCP 重传与拥塞控制把发送端压下来——曲线会比出向
  限速毛糙，这是内核入向机制的本质，不是实现缺陷；
- **conn_rate 数的是连接建立，不是 HTTP 请求**。L4 上数不出请求，
  tc 能表达的最接近"请求速率"的口径就是 SYN 速率。真正按 HTTP 请求
  数/会话数限速是 HAProxy 自己的能力（stick-table、`http_req_rate`
  等，写在 haproxy.cfg 里），与本模块互不冲突、可以叠加。

## 2. 双网卡与配置

拓扑：

```
客户端 ──> [网卡A 客户端侧] HAProxy [网卡B 后端侧] ──> 后端
            ▲ 入向 police（本模块）
            ▼ 出向 HTB（quotas，原有）
```

两张网卡、两个环境变量，各管一个方向：

| 环境变量 | 方向 | 取值 |
| --- | --- | --- |
| `RL_TC_IFACE` | 响应方向（出向 HTB） | 客户端侧网卡（原有行为不变） |
| `RL_TC_IN_IFACE` | 请求方向（入向 police） | **客户端侧网卡，必须显式指定**；`-` = 明确不做入向限速 |

`RL_TC_IN_IFACE` **绝不自动探测**：入向 police 放错网卡会误伤后端
流量。配置了 `request_limits` 却没设它，服务启动失败——宁可起不来，
也不要"以为限了请求方向其实没有"。通常两个变量填同一张网卡
（客户端侧那张）。

YAML：

```yaml
quotas:                      # 响应方向（下行），原有
  fe_main: 40
request_limits:              # 请求方向（入向），本分支新增
  fe_main:
    mbps: 10                 # 入向带宽上限（0 = 不限带宽）
    conn_rate: 200           # 每秒新建连接上限（0 = 不限）
```

与 quotas 相互独立：只配一边、两边都配都行。热更新同一套机制
（5s 轮询，改了即生效）；登记了、cfg 里没有的名字告警并忽略。

## 3. 行为细节

- **重建式收敛**：入向过滤器没有出向 rate-change 那样的就地改路径
  ——任何变化（含只改 conn_rate）都是"删两组 prio → 重加"，瞬间完成，
  police 无队列状态可丢；
- **幂等**：每轮先读回实况（`tc filter show … parent ffff:`）比对
  字节速率规则，一致就一条命令都不发；周期兜底（30s）纠正手工改动；
- **清空 = 撤掉**：request_limits 清空后删除 ingress qdisc，网卡入向
  恢复原状；
- **SYN 速率是尽力而为**：flower + `pkts_rate` 需要较新内核
  （cls_flower、act_police 的包速率支持，RHEL9/Rocky9 的内核满足）。
  缺了只是没有连接速率限制，**字节限速照常生效**，失败记在日志里；
- 权限仍只需 `CAP_NET_ADMIN`（systemd unit 不用改）。

## 4. 未验证的部分（重要）

- 开发沙箱内核没有 `act_police`/`cls_flower` 模块，入向路径**没有在
  沙箱里端到端跑过**；命令序列与 `tc filter show` 的解析按 iproute2
  的源码打印路径写成并被单元测试钉住。**首次上线请人工核对一次**：
  `tc filter show dev <网卡> parent ffff:` 的输出若与解析不符，表现为
  日志里每轮都在 rebuild——看到连续 rebuild 就是解析对不上的信号；
- police 的丢包行为对长肥管道（高 RTT）客户端的体验影响没有实测过；
  入向限速想要平滑曲线需要 IFB + HTB 整形，那是复杂度高一档的方案，
  本分支刻意先用 police 验证需求。
