# 双网卡形态：请求方向（入向）限速 + 闭环动态调节

本分支的限速形态：**出向不做 tc 整形**，限速全靠**入向**——客户端打
进 HAProxy 的流量在**客户端侧网卡的入向**用 tc police 按监听端口限制，
而入向的带宽上限由控制器根据**实测出向带宽**动态调节（见 §4 闭环）。
部署前提是**双网卡**：一张面向客户端（请求进、响应出），一张面向后端。

为什么不在出向上 HTB：HTB 把超速流量排队，响应延迟全体抬高；入向
police 只掐请求流（体量远小于响应流），响应路径零排队。代价是控制
是间接的、有滞后，所以闭环算法刻意平缓（§4）。

## 1. 它限的是什么

| 配置项 | 限的东西 | 内核机制（按 RL_TC_IN_MODE） |
| --- | --- | --- |
| `request_limits.<名>.mbps` | 该端口**入向字节速率**（客户端上行/请求体） | **ifb（默认）**：ingress 重定向到 IFB 虚拟网卡 + HTB 排队整形（平稳慢放）；**police**：ingress police 超额丢包 |
| `request_limits.<名>.conn_rate` | 该端口**每秒新建连接数**（SYN 速率） | 两种模式相同：ingress + flower 匹配 TCP SYN + police 包速率 |

两种字节限速模式的取舍：

- **ifb（默认，平稳整形）**：内核入向路径本身没有队列，所以把入向包
  用 mirred 整段重定向到 IFB 虚拟网卡的出向路径，在那里用与出向同款
  的 HTB **排队慢放**——客户端看到的是平稳的慢，不是丢包重传；完全
  复用出向 tcshaper，动态闭环调速走 rate **就地变更**（不清统计）。
  内核需 ifb/act_mirred/sch_htb，均为发行版通用内核标配；
- **police（备选，超额丢包）**：无队列、无额外设备，超额直接丢，靠
  TCP 重传与拥塞控制把发送端压下来——曲线毛糙，但依赖最少
  （act_police）。老内核或禁用 IFB 的环境用它；
- **conn_rate 数的是连接建立，不是 HTTP 请求**。L4 上数不出请求，
  tc 能表达的最接近"请求速率"的口径就是 SYN 速率。真正按 HTTP 请求
  数/会话数限速是 HAProxy 自己的能力（stick-table、`http_req_rate`
  等，写在 haproxy.cfg 里），与本模块互不冲突、可以叠加。

## 2. 双网卡与配置

拓扑：

```
客户端 ──> [网卡A 客户端侧] HAProxy [网卡B 后端侧] ──> 后端
            ▲ 入向 police（本模块）
            ▼ 出向 HTB（quotas，原有）
```

两张网卡、两个环境变量，各管一个方向：

| 环境变量 | 方向 | 取值 |
| --- | --- | --- |
| `RL_TC_IFACE` | 响应方向（出向 HTB） | 本分支推荐设 `-`（出向不整形，闭环压入向）；设网卡名则出向 HTB 照常可用 |
| `RL_TC_IN_IFACE` | 请求方向（入向） | **客户端侧网卡，必须显式指定**；`-` = 明确不做入向限速 |
| `RL_TC_IN_MODE` | 入向字节限速的机制 | `ifb`（默认，IFB+HTB 排队整形）或 `police`（超额丢包） |
| `RL_TC_IFB` | ifb 模式的虚拟网卡名 | 默认 `ifbrl0`（避开教程惯用的 ifb0，防撞运维手工设备） |

`RL_TC_IN_IFACE` **绝不自动探测**：入向 police 放错网卡会误伤后端
流量。配置了 `request_limits` 却没设它，服务启动失败——宁可起不来，
也不要"以为限了请求方向其实没有"。通常两个变量填同一张网卡
（客户端侧那张）。

YAML：

```yaml
quotas:                      # 出向带宽**目标**（闭环的设定值）
  fe_main: 40
request_limits:              # 请求方向（入向），本分支新增
  fe_main:
    mbps: 10                 # 入向带宽上限 = 闭环的起点与封顶（0 = 不限带宽）
    conn_rate: 200           # 每秒新建连接上限（0 = 不限；静态，不参与闭环）
dynamic_ingress:             # 闭环开关与参数（见 §4）
  enabled: true
```

闭环关闭（`dynamic_ingress.enabled: false`，默认）时 request_limits
就是静态入向限速，与 quotas 相互独立：只配一边、两边都配都行。热更新
同一套机制（5s 轮询，改了即生效）；登记了、cfg 里没有的名字告警并
忽略。`dynamic_ingress` 段本身启动时定型，改了需重启。

## 3. 行为细节

- **ifb 模式的收敛**：字节整形完全复用出向 tcshaper（只是分类按目的
  端口）——幂等 reconcile、速率不符走 class change 就地变更；管路
  （IFB 设备/up/重定向过滤器）每轮核对，手工删了会被周期兜底补回；
  request_limits 清空撤掉 ingress 钩子与 IFB 整形树（IFB 设备 down
  掉留着）；
- **police 模式的收敛（重建式）**：入向过滤器没有就地改路径——任何
  变化（含只改 conn_rate）都是"删两组 prio → 重加"，瞬间完成，
  police 无队列状态可丢；
- **幂等**：每轮先读回实况（`tc filter show … parent ffff:`）比对
  字节速率规则，一致就一条命令都不发；周期兜底（30s）纠正手工改动；
- **清空 = 撤掉**：request_limits 清空后删除 ingress qdisc，网卡入向
  恢复原状；
- **SYN 速率是尽力而为**：flower + `pkts_rate` 需要较新内核
  （cls_flower、act_police 的包速率支持，RHEL9/Rocky9 的内核满足）。
  缺了只是没有连接速率限制，**字节限速照常生效**，失败记在日志里；
- 权限仍只需 `CAP_NET_ADMIN`（systemd unit 不用改）。

## 4. 闭环：按出向带宽动态调整入向限速

静态入向限速有个两难：设紧了误伤（请求与 ACK 被丢，出向到不了目标），
设松了没用（出向还是会超）。闭环把这个参数交给控制器：

```
quotas（出向目标 40Mbps）
      │  对照
实测出向带宽（mean10，与超限告警同口径）
      │  决策（每 interval_s 一轮）
入向 police 上限（在 [floor, request_limits.mbps] 区间内活动）
```

算法刻意**平缓**（对照动态 maxconn 分支的 AIMD 乘性急砍，这里两个
方向都是小步；宁可收敛慢，也不要振荡）：

- **死区**：出向/目标 ∈ [low_ratio, high_ratio]（默认 [0.85, 1.0]）
  → 不动。目标附近的波动不折腾 tc；
- **超了**：下调，降幅 = 超出比例×0.5、**封顶 step_down_max**（默认
  单次最多 -10%），下限 floor_ratio×上限（默认 10%）；
- **低了**：上调小步（step_up×**当前值**，默认 +5%/次，乘性；绝对
  步长下限 0.1Mbps），封顶回到 request_limits.mbps——流量退潮后入向
  逐步爬回全开。上调锚当前值而不是上限：入向因 ACK 杠杆比出向小
  一两个数量级，动态值收敛在上限的几十分之一刻度，step_up×上限在
  那个刻度上是一步翻倍的巨步——上冲过头→出向猛涨→猛降回来，稳定
  的极限环（页面上带宽一会高一会低，实测抓到过）。两个方向都乘性
  锚当前值后步长对称，流量稳定时动态值收敛进死区不再折腾；
- **变化 <apply_epsilon（默认 2%）不下发**：入向规则整组重建、统计
  清零，琐碎变化不值得；
- **采样失联冻结**：degraded 轮次不动作，陈旧数据不配驱动调整。

观测用 10s 均值、调节周期默认 15s：mean10 要 10s 才能反映一次调整的
效果，调得更快只会追着噪声跑。参数与校验见
`rl_limiter/ingressgov.py` 与 `deploy/config/limiter.example.yaml`。

**实例级环**：`instance_quota_mbps` 在本形态下 = **实例出向总带宽
目标**（页面"实例总限速"卡填的就是它——填的值是对出向带宽的判断
基准，出向本身不整形）。观测 = 全部 frontend 出向 mean10 之和，
执行 = IFB 上的 HTB **入向总闸**（层级模式：全部端口类挂进 1:ffff
聚合类，聚合速率即动态值；登记了入向上限的端口在总闸内保留各自
ceil，没登记的只受总闸管）。算法与单端口环同一套（死区/小步/封顶/
下限），总闸上限 = 登记的 request_limits.mbps 之和（一个都没登记时
退化为目标值本身）。**起调点 = 实测流入带宽**：首次需要收紧时总闸
直接落位到"客户端侧网卡实测 RX 速率 × 1.1"（落位本身不掐流量），
再小步细调——入向因 ACK 杠杆比出向小一两个数量级，从上限/目标值
起步爬降的话前几十步全是空转。实测读的是**真实网卡**而不是 IFB
（没登记 request_limits、只设实例目标时，首次收紧那一刻重定向管路
还没建，IFB 上读不到数）；实测暂缺（差分基准刚建立）等一轮再落位，
连续两轮都没有才回退从上限爬降。两个环可同时在跑、互不覆盖——HTB 层级天然执行
min(端口 ceil, 总闸)。仅 ifb 执行模式支持（police 没有层级），police
模式下设实例总限速会被写接口 409 拒绝。

控制台的"tc 实况（调试）"面板会把动态当前值标出来（如
`fe_main@:8080=7.3Mbps（动态，上限 10、出向目标 40）+150conn/s; 实例
出向目标=60Mbps→入向总闸 8.2Mbps（动态）`），运行日志里每次调整一行
INFO（从哪调到哪、当时的出向均值）。

实例页还有一张**"调节视图（闭环动态限速）"**卡（闭环没在工作时
隐藏），把调节相关的数据全部摆在一处、随时间走曲线：

- 指标条：实例出向目标 / 出向总观测（10s 均值，控制环的观测值）/
  入向总闸当前值（全开时标出上限）/ 实测流入 / 调节状态（全开、
  已落位调节中等）；
- 三张曲线：**出向总带宽 vs 目标参考线**（看收敛与平稳性）、**入向
  总闸与实测流入**（看执行值怎么动、落在流入的哪个刻度上）、**网卡
  带宽**（链路层口径的流入/流出，整机范围）；
- 按监听端口的表：每个受调端口的出向目标 / 出向观测 / 入向上限
  （动态当前值）/ 入向登记上限 / 状态。

数据来自控制器本身（快照里的 regulation 字段，单位一律 Mbps），与
日志/tc 面板同源——判断"调没调、调到哪、稳不稳"看这张卡就够。

## 5. compose demo 怎么跑（双网卡拓扑 + 闭环）

`docker-compose-demo.yml` 已经就是双网卡拓扑，`make demo-up` 直接起：

```
loadgen ──frontnet(10.211.1.0/24)──> 节点 ──backnet(10.211.2.0/24)──> web
                客户端侧网卡                      后端侧网卡
```

- 每台节点接两个网络 = 容器里两张网卡。**网卡名不能写死**（compose
  接两个网络时 eth0/eth1 的先后顺序不可靠），入口脚本按
  `RL_FRONT_SUBNET`（默认 `10.211.1.`）匹配 IP 网段定位客户端侧网卡，
  再导出 `RL_TC_IFACE` 与 `RL_TC_IN_IFACE`——出向 HTB 与入向 police
  都落在这张网卡上；
- compose 已把出向整形关掉（节点 env `RL_TC_IFACE: "-"`）——限速全靠
  入向闭环；入向网卡仍按网段定位（入口脚本里 `RL_TC_IFACE=-` 只关出向，
  不再连带关入向）；
- **端口默认不限速**：节点的 `limiter-node.yaml` 默认不登记
  quotas/request_limits（起来就是纯监控），`dynamic_ingress` 开着但
  没有可调对象。要观察闭环，进容器解开 YAML 里的示例行（quotas
  fe_main: 40 + request_limits fe_main: {mbps: 10, conn_rate: 150}，
  两样都要），5s 内热生效。之后压测默认是短连接场景（每请求一条新
  连接），每节点 200~300 conn/s 的供给下，conn_rate=150 的闸会明显
  生效：`docker compose logs -f loadgen` 可见错误/延迟上升、
  `tc -s filter show dev <网卡> parent ffff:` 的 police 丢包计数在涨；
  rl-limiter 日志里能看到"入向动态限速调整"在工作；
- 生产机同理：两张物理网卡各接客户端/后端网段，`RL_TC_IN_IFACE` 直接
  写客户端侧网卡名即可（裸机没有"按网段定位"的入口脚本，env 文件里
  写死名字更直白）。

**内核前提**：ifb 模式（默认）要 `ifb`、`act_mirred`、`sch_htb`；
police 模式要 `sch_ingress`、`act_police`；conn_rate（两种模式皆同）
还要 `cls_flower` + police 包速率。RHEL9/Rocky9、Ubuntu 22.04+ 的通用
内核都满足；容器优化型精简内核可能缺——入口脚本的 tc 自检只验 HTB，
入向模块缺失会表现为 rl-limiter 日志里入向下发报错。

**Docker Desktop（Mac/Win）注意**：容器共享的是其精简虚拟机内核，
可能没有 ifb 模块。这属于**启动即失败**：入口脚本预检 + rl-limiter
启动时创建真实设备，建不出来直接退出并写明原因与处置（与"宁可起
不来，也不要以为在限速"的铁律一致，容器会进 restart 循环、
`docker ps` 一眼可见）。处置：设 `RL_TC_IN_MODE=police` 改用丢包式
入向限速（实例总闸在该模式下不可用），或换带通用内核的 Linux 主机
跑 demo。

### 生产形态：host 网络

demo 的 bridge 双网络只是用来在一台机器上**模拟**双网卡；生产上双
网卡就是宿主机的两张物理网卡，推荐 **host 网络 + NET_ADMIN** 的容器
形态（性能与宿主机直跑一致，没有 veth/NAT 的数据面开销）——样例见
仓库根目录 `docker-compose-host.yml`，本分支的默认接线已经是闭环
形态（`RL_TC_IFACE=-` + `RL_TC_IN_IFACE=<客户端侧物理网卡>`）。要点：

- `RL_TC_IN_IFACE` 填客户端侧**物理网卡名**（或 `RL_FRONT_SUBNET`
  按网段定位）；IFB/HTB 规则直接作用于宿主机内核，`modprobe ifb`
  先验证模块在；
- HAProxy 监听端口与控制台端口直接占宿主机（无 ports: 映射），
  控制台保持只绑 127.0.0.1；
- host 网络下 compose 的 `sysctls:` 不可用，内核参数在宿主机上执行
  `deploy/sysctl/tune-kernel.sh` 或按 docs/08 固化。

## 6. 未验证的部分（重要）

- 开发沙箱内核没有 `act_police`/`cls_flower` 模块，入向路径**没有在
  沙箱里端到端跑过**；命令序列与 `tc filter show` 的解析按 iproute2
  的源码打印路径写成并被单元测试钉住。**首次上线请人工核对一次**：
  `tc filter show dev <网卡> parent ffff:` 的输出若与解析不符，表现为
  日志里每轮都在 rebuild——看到连续 rebuild 就是解析对不上的信号；
- police 的丢包行为对长肥管道（高 RTT）客户端的体验影响没有实测过；
  入向限速想要平滑曲线需要 IFB + HTB 整形，那是复杂度高一档的方案，
  本分支刻意先用 police 验证需求；
- **ifb 模式（默认）已在沙箱真实 e2e 验证**：重定向、HTB 整形、
  速率就地变更、动态闭环收敛（900 并发压测下出向从 ~155Mbps 平缓
  收敛到目标 40Mbps 的死区内稳定）均在真实流量下确认。police 模式
  仍只有单元测试（沙箱缺 act_police）；conn_rate 的 SYN 闸两种模式
  下都依赖 act_police + cls_flower，沙箱未验证；
- **floor_ratio 的量级要按 ACK 杠杆来定**（e2e 实测教训）：下载型
  业务的入向主要是 ACK，GRO/stretch-ACK 下一个 ACK 能确认几 KB 数据
  ——实测入向 1Mbps 的 ACK 就能驱动约 70Mbps 的出向。闭环的均衡点
  因此可能远低于直觉（本 demo 收敛在 ~0.6Mbps），floor 设太高会
  出现"压到下限、出向仍高于目标"（面板上一眼可见：动态值停在下限、
  出向均值仍在死区上方）。遇到就把 floor_ratio 调低（demo 用 0.05）
  或把 request_limits.mbps 上限本身设小；
- 首次上线建议盯一段"tc 实况"面板：出向均值应收敛进 [low_ratio,
  high_ratio]×目标 的死区并停住，入向动态值不应持续振荡——持续来回
  摆说明 interval_s 或步长需要调大/调小。
